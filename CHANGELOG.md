# Changelog

All notable changes to `pharn` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Releases 0.4.0 and older are in [CHANGELOG-ARCHIVE.md](CHANGELOG-ARCHIVE.md).

## [Unreleased]

### Added

- **`pharn update` and `pharn status` now name the files upstream stopped shipping.** `update` never deletes, so a file pharn-oss dropped — a `pharn-*` command (still a live slash command), a hook, a floor checker, a trusted doc, or one file inside a capability you still have — stayed in your project, and because its entry in `pharn.records.json` was pruned on that same run, no command ever mentioned it again. Such a file is now an **orphan**: both commands list it in an `ORPHANED` note, grouped as `UNCHANGED` (still the bytes pharn wrote), `EDITED` (changed since — review before deleting) or `UNREADABLE` (with the reason), at most 20 per group, with a reminder to delete what you no longer need by hand. `update` keeps the orphan's entry in `pharn.records.json` until the file is gone (a re-run `init` keeps it too), so it stays listed on every later run, and a path upstream ships again later is a clean upgrade instead of an `unrecorded` skip. Once you delete an orphan, the next `update` at the same skills version reads its recorded path as missing and runs once: it restores nothing, drops the entry, and the header now says a missing path is restored only "if upstream still ships it". Orphans are never a skip, never withhold the version bump, and are **not** a `pharn status --strict` input. `update --dry-run --json` gains `plan.orphans` (present only when there is one) and `status --json` gains `orphans` (`null` under `--no-drift`, without a usable records store, or when the clone is at another layout); `schemaVersion` stays 1. Only files `pharn` recorded writing, at paths an install can write, are listed — a hand-added record for any other path is never read. The files of a capability `update` drops are not orphans. The floor `fixtures/` copies earlier installs left behind (see the floor `fixtures/` entry under Fixed) are listed this way too, as `UNCHANGED` unless you edited them. See [`pharn update`](docs/commands/update.md#orphaned-files).
- **`pharn init --dry-run` previews a fresh install and writes nothing.** It runs the same checks and the same selection as a real `init` — detection, the fetch, `MIN_CLI`, the capability index, what a re-run would carry over, the destination check — then prints the plan: the summary the interactive run would ask about, every existing file it would overwrite (marked `(edited)`, `(no pharn record)`, `(differs from upstream)` or — for an existing `pharn.config.json` — `(will be rewritten — backed up first)`, exactly as the overwrite prompt marks them), how many files it would create, what it would back up, the `pharn.config.json` it would write and which of your own keys it would keep, whether your `.claude/settings.json` would be preserved and the `HOOKS` note a real run would print, and whether `pharn init --yes` would install. It exits 0 and leaves the project byte-identical (no `.pharn.lock`, no `.pharn-backup/`, no config or records). It needs no terminal and never prompts; a refusal (a symlink in the way, a `MIN_CLI` newer than your pharn, a failed fetch) still exits 1. See [`pharn init`](docs/commands/init.md#preview-the-install---dry-run).
- **`pharn init --dry-run --json`: the install plan as one machine-readable object.** One JSON object (`schemaVersion: 1`) on stdout and nothing else — every write target with its `action` (`create`/`overwrite`) and backup `label` (`rewritten` for an existing `pharn.config.json`, which is always backed up), the backups, the counts, the selected, skipped and carried capabilities, unreadable upstream capabilities, settings and hook wiring, the `models` outcome, the names of your own config keys, and `yesWouldProceed`. Diagnostics and failures go to stderr with stdout empty and exit 1, as in `update --dry-run --json`. `--json` needs `--dry-run`: `pharn init --json` — and a bare `pharn --json` — is refused with an `Incomplete option for` error, exit 1. See [`pharn init`](docs/commands/init.md#json-output).
- **`pharn init --yes` / `-y` installs without prompts — only into a project where none of its files exists yet.** It skips the summary's confirmation (the summary still prints) and works without a terminal, so a fresh project can be set up from CI, a devcontainer or an agent. It never answers the overwrite confirmation: if any file it would write already exists, `pharn.config.json` included, it exits 1 having written nothing, lists the files, and points at `pharn init` in a terminal, `pharn init --dry-run` or `pharn update`. A re-install therefore always refuses `--yes`. The check runs again under the project lock, immediately before the install. `pharn init --yes` was previously refused as an unsupported option. See [`pharn init`](docs/commands/init.md#install-without-prompts---yes).
- **`pharn uninstall` removes PHARN from a project, and only what `pharn` can prove it wrote.** There was no uninstall command and no documented way to remove PHARN, so projects were left with hooks wired to deleted scripts, or lost work `pharn` never wrote (your own `pharn/features/<feature>/` folders) to an over-eager `rm -rf`. `uninstall` reads `pharn.records.json` and deletes a recorded file only when it is a path a `pharn` install writes, is a regular file reached without a symlinked directory, and still matches its recorded hash; it then removes the directories that leaves empty (never one that still holds anything, never the project root) and deletes `pharn.records.json` and, last, `pharn.config.json` — backed up first to `.pharn-backup/<timestamp>/`. Files you changed and files `pharn` has no record of stay where they are, and the changed ones are listed. `.claude/settings.json`, `.claude/settings.local.json` and every `.pharn-backup/` directory are left untouched; instead, a `HOOKS` note lists the hook entries still wired to a script `uninstall` removed. It shows its plan and asks once (default No); `--yes`/`-y` skips the question, and off a terminal without `--yes` it refuses. With no usable `pharn.records.json` it refuses and deletes nothing — the manual procedure is in [Troubleshooting](docs/troubleshooting.md#removing-pharn-by-hand). With no `pharn.config.json` at all it says PHARN is not installed and exits 0. Offline: no clone, no network. See [`pharn uninstall`](docs/commands/uninstall.md).
- **`pharn init --archetype <list>` installs for the archetypes you name.** `--archetype` used to be accepted and ignored, so a misdetected project could only be corrected by hand-editing `archetypes` in `pharn.config.json`. It now replaces detection: `pharn init --archetype backend` or `--archetype ssr,backend` resolves, installs and records exactly those archetypes, and `pharn update` keeps them. The value must be a comma-separated list of `ssr`, `backend` and `spa`, or `lib` alone, each at most once and spelled exactly; anything else (including a bare `--archetype`, `--no-archetype` or the flag given twice) exits 1 before anything runs. It works with `--dry-run`, `--dry-run --json` and `--yes`; the JSON plan gains `archetypeSource` (`detected` or `flag`), `detectedArchetypes` (what detection found when the flag overrode it) and `archetypeEvidence` (schemaVersion stays 1). A re-run `init` detects again unless the flag is passed again, and its summary says when the result differs from what the replaced config recorded (`previously recorded: ssr, backend — pass --archetype ssr,backend to keep them`). See [`pharn init`](docs/commands/init.md#choosing-the-archetypes-yourself---archetype).
- **The `init` summary shows why each archetype was detected.** Each archetype is followed by the dependency or the first path that triggered it — `ssr ← next (package.json)`, `backend ← src/app/api/` — or `no framework signal found` for `lib`; with `--archetype`, what detection found is shown and marked `(not used)`. Paths have terminal control characters removed and are cut at 120 characters.
- **`pharn <command> --help` shows one command and only the options it takes.** `pharn status --help` used to print the same ~2 KB page as `pharn --help`, every command and every option. It now prints the command's usage line and the options that command accepts (plus `--help` and `--version`), described for that command alone; `pharn --help` still prints everything. The full page now also lists the `rm` alias of `remove`, and an `Environment` block naming what `pharn` reads: `PHARN_DEBUG=1` (the full error on a failed download or install), `NODE_USE_ENV_PROXY=1` (let Node's fetch use your `https_proxy`/`HTTPS_PROXY`; without it `pharn` connects directly) and `NO_COLOR`/`FORCE_COLOR`.

### Changed

- **`pharn update` names what it will add, drop and delete before it asks.** The confirmation used to come before the download, so the capabilities an update added or dropped — and, since dropped capabilities' directories are deleted, the directories it removed — were applied after a question that could not name them, and `--yes` applied them with nothing in the log saying which. `update` now downloads and plans first, lists every capability it would add or drop in a `CAPABILITIES` note with the directory each drop deletes, and then asks `Apply this update?` (`Apply this update and overwrite your changes?` with `--force`). When it deletes a capability directory the question says how many and **defaults to No**; otherwise the default is still Yes. `--yes` prints the same note and skips only the question. After you answer, `update` takes the lock and plans again from the same download (no second download); if the capabilities it would change or the directories it would delete are no longer exactly what you were shown, it stops with exit 1 and changes nothing. A failed download, a `MIN_CLI` refusal or a directory that cannot be deleted safely now stops the run before the question instead of after it (still exit 1). The cost: declining — or a run refused because another pharn process holds the lock — has already downloaded the repo (it is removed again). Off a terminal without `--yes`, `update` still refuses before any network call. `--dry-run` and `--dry-run --json` are unchanged. See [`pharn update`](docs/commands/update.md#before-you-confirm).
- **The required `Test` check now runs the shipped bundle (contributors).** `tests/dist-smoke.test.ts` builds the esbuild bundle with `scripts/build.mjs` into a temporary directory laid out like the published package and runs it with `node`: `--version` must print the `package.json` version, `--help` must list every command, `status` with no `pharn.config.json` must exit 1 with the "Run `pharn init` first." message and no stack trace, and an unsupported or unknown option must be refused with exit 1. Before this, every test imported `src/`, so a regression only the bundle has (the `package.json` lookup in `src/version.ts`, an external dependency that no longer resolves) stayed green in `Test`. `scripts/build.mjs` takes an optional output path for this; `npm run build` is unchanged. No network access, and nothing is written inside the repository.
- **Every command now has one end-to-end test with nothing in `src/` mocked, and the suite no longer times out on a loaded machine (contributors).** The command suites replace the modules between them (the capability copy, the install manifest, the config read/write, the fetch) with stand-ins, so a bug that sits between two modules, such as `add` installing a capability at one layout while `remove` and `status` look for it at another, passed all of them. `tests/commands-integration.test.ts` runs `init --yes`, `add`, `update --yes` (a 1.0.0 to 2.0.0 upgrade that keeps an edited file and upgrades a clean one), `remove`, `status --json` and `uninstall --yes` against a real temporary project, with only `fetch` replaced to serve a real tarball, and checks the files, `pharn.config.json` and `pharn.records.json` on disk. Separately, `tests/lint-gate.test.ts` gets an explicit 60-second budget per case (each case starts eslint, which took 5 to 10 seconds per start during a full `--coverage` run and hit vitest's 5-second default), the signal tests in `tests/project-lock.test.ts` wait for the signal to be handled instead of sleeping 3 seconds, and the four-request registry case in `tests/publish-workflow.test.ts` gets an explicit budget. No user-facing behavior changes.
- **`update`'s notes, `add`'s picker and the older CHANGELOG entries each moved to a file of their own (contributors).** The functions that print `pharn update`'s PLAN, SKIPPED, CAPABILITIES, MODELS, HOOKS, ORPHANED and NOT SHIPPED notes, its layout warnings, backup pointer and closing summary moved unchanged from `src/commands/update.ts` to `src/lib/update-render.ts`, and the multi-select behind a bare `pharn add`, with the loop that installs each pick, from `src/commands/add.ts` to `src/steps/add-picker.ts`. The command keeps the terminal check, the lock, the download and the version and layout checks, which still run before the list is shown. The entries for 0.4.0 and older moved to `CHANGELOG-ARCHIVE.md`, with their compare links; `tests/release-consistency.test.ts` checks the links across both files, and that each file defines the links of its own headings. No user-facing behavior changes.
- **Dead code removed and four duplicated helpers shared (contributors).** Removed: `warnAndConfirm` and `detectArchetypes` (only tests called them), the `packageJsonFound` field of the archetype detection result (nothing read it; the package.json read still decides it, through `readPackageFacts`), the legacy `Constitution`, `InstalledModule` and `InstalledSkill` types (those legacy `pharn.config.json` fields still load, typed `unknown`), and four `..` checks that could never fire because the name allowlist checked just before them admits no `..` (a test now pins that). Shared: one symlink walk that returns a value the caller chooses when the walk throws (`findSymlinkComponentOr`, replacing three private copies), one control-character range (`CONTROL_CHARS_RE`), one bounded read plus JSON parse (`readJsonBounded`, used by five readers), and `pharn list` now loads its config through the same `loadArchetypeConfigOrExit` as the other commands. The only visible difference is in `pharn list --json`: a config error is now printed through the same plain-stderr reporter the other `--json` commands use, which strips terminal control characters. Messages and exit codes are unchanged. `pharn init` still writes `"modules": []`, because every released CLI (0.3.0 to 0.12.0) treats a `pharn.config.json` without it as no install at all.
- **Archetype detection no longer reads every `app/` folder as Next.js, or every `migrations/` folder as a JavaScript backend.** Route handlers under `app/`, and `api/` folders under `app/` or `pages/`, now count only in a Next.js app (a `next` dependency or a `next.config.*` at the project root, or a `next.config.*` in that `apps/<name>/` or `packages/<name>/` package), and only in the router folders Next reads (`app/`, `pages/`, `src/app/`, `src/pages/`). `next.config.*` counts only at the project root or directly in `apps/<name>/` or `packages/<name>/`. A root `api/` folder, a `migrations/` folder and `.sql` files in a database folder count only when the project has a root `package.json`. Before, an Angular, Vue or RTK Query `src/app/` detected as `backend`, a library with a Next.js docs site detected as `ssr` (hiding its `spa` signal), and Flask, golang-migrate, sqlx, Rails and Laravel projects detected as `backend`, contrary to the documentation — each installing capabilities that did not fit. A project that relied on one of those signals without the new evidence now detects differently; `pharn init --archetype` restores any choice. A non-JS project that has a root `package.json` (a Vite frontend, or tooling only) still resolves `backend` from its migrations. See [`pharn init`](docs/commands/init.md#3-detect-archetypes).
- **A refused command prints one line, not the whole usage text.** An unknown command, an unknown or unsupported option, an incomplete option pair or an extra argument printed its error followed by the full ~2 KB usage text, which scrolled the error itself off the screen. Each now prints the one error line and ``Run `pharn --help` for usage.`` on stderr; the exit code (1) is unchanged.
- **`pharn remove <name>` exits 1 when `<name>` is not installed.** It warned and exited 0, while `pharn add <name>` for a name it does not know exits 1 — so a script that removed the wrong name read success. It still writes nothing and lists the capabilities you can remove; only the exit code (and the stream: stderr) changed. The interactive `pharn remove` is unchanged.
- **Every backup notice now says `.pharn-backup/` is not gitignored.** `init`, `add`, `remove` and `uninstall` each printed their own `Backed up … to .pharn-backup/<timestamp> …` line, and only `pharn update --force` followed it with the advice to add `.pharn-backup/` to your `.gitignore` or delete it once you are happy — so a backup made by any other command was easy to commit by accident. All five commands now print the same notice, with the same advice line; the first line of each is unchanged.
- **Release links and stale docs corrected.** The compare links at the foot of `CHANGELOG.md` named tags that never existed (`v0.8.0`, `v0.3.1`, `v0.1.0`) and returned 404; each now names a real tag, 0.8.0 (never tagged or published), 0.2.0 and 0.1.0 have none, and `tests/release-consistency.test.ts` fails a link to a tag that does not exist. The docs say plainly that pharn-oss has not published a release yet, so `--ref latest` exits 1 today and `main` is the channel that works; that `THREAT-MODEL.md` and `LIMITS.md` land at the project root even in the `pharn/` layout, so a same-named doc of yours is replaced (after the overwrite prompt and a backup); and the docs index, roadmap and issue templates describe today's commands, archetypes and capabilities instead of the old wizard, modules and versions.
- **Archetype detection recognizes more frameworks, and a dev-only server no longer makes a project `backend`.** React Router v7 framework mode (`@react-router/dev`, `@react-router/node`, `@react-router/serve`), TanStack Start (`@tanstack/react-start`, `@tanstack/solid-start`, `@tanstack/start`), SolidStart (`@solidjs/start`), Qwik City, Analog, Vike (and `vite-plugin-ssr`) and Angular Universal now detect as `ssr`; before, these apps detected as `spa` through their UI library and received the wrong capabilities. `elysia`, AdonisJS, `h3`, tRPC's server, Apollo Server, GraphQL Yoga and the common database clients (`typeorm`, `sequelize`, `mongoose`, `knex`, `kysely`, MikroORM, `pg`, `mysql2`, `mongodb`, `better-sqlite3`) now detect as `backend`: a runtime database driver dependency is a server-side data surface. Server and database packages now count **only under `dependencies`**: one listed only in `devDependencies` — an Express mock server, a test database — used to add the backend capabilities and no longer does. A backend bundled so that its framework is only a devDependency needs `pharn init --archetype backend`. SSR and UI frameworks still count from `devDependencies` (the SvelteKit and React Router templates list them there), and the summary now says so: `ssr ← @sveltejs/kit (package.json devDependencies)`; `init --dry-run --json` reports such evidence with `"source": "devDependency"` (`schemaVersion` stays 1). `peerDependencies` and `optionalDependencies` are still not read, deliberately. React Router library mode (`react-router` alone) stays `spa`. See [Troubleshooting](docs/troubleshooting.md#detection-picked-the-wrong-archetype).

### Security

- **`pharn.config.json` and `pharn.records.json` can no longer be redirected through a symlink committed beside them.** Both files are written to a temporary file next to them and then renamed into place. That temporary file had a predictable name (`pharn.config.json.<pid>.tmp`) and was opened in a way that followed a symbolic link, so a repository that committed a link at that name could make any `pharn` command that writes the config (or the records store) overwrite a file outside the project that you can write to, and leave `pharn.config.json` itself as a link. The temporary file now gets an unpredictable random name and is created exclusively: an existing entry at the name, a link included, is never opened or followed, and `pharn` tries a fresh name instead (after 8 taken names it stops with an error and writes nothing). File contents and permissions are written exactly as before.
- **`pharn remove` re-checks for a symbolic link under the lock, right before it deletes.** `remove` refused a capability directory whose path crossed a symbolic link — but only before taking the project lock and, on the picker path, before its confirmation. A folder such as `pharn-review/` replaced by a link while the confirmation was open was deleted through, removing files outside the project (unless a file there needed a backup, which then refused by accident). The same check now runs again under the lock, before the backup and the first delete; the early check stays, so a selection that would be refused is still never asked about.
- **Resolving the tip of pharn-oss `main` now reads at most 1 KiB.** Before downloading, `pharn` asks the GitHub API which commit `main` points at. It asked for the full commit object — whose size grows with the files the last merge touched — and read the answer with no size limit, the one network read without one. It now asks for the bare commit id (as `--ref latest` already does) and stops reading past 1 KiB. An oversized answer is treated like any other failed lookup: the install continues from the tip of `main` and records no commit, as documented in `LIMITS.md` §3b.
- **`pharn update` no longer overwrites a file outside your project through a hard link.** `update` refused to write through a symbolic link, but a hard link is a second name for the same file and looks like an ordinary file, so no check could see it: if an installed file was a hard link to a file elsewhere, `update` wrote the new contents into that shared file, changing it outside the project too. `update` now writes each file to a new temporary file beside it and renames it into place, so only the name inside your project gets the new contents and the other file keeps its own. File contents and permissions are the same as before. One visible difference: an installed file you made read-only is now replaced like any other, as `init` already did — what `update` needs is write permission on its folder. `init` and `add` were already safe from hard links: the copy method they use replaces an existing file rather than writing into it (a test now pins that).

### Fixed

- **`pharn add` and `pharn remove` no longer move `installedAt`.** `installedAt` in `pharn.config.json` is documented as the time of the install or last update, but `add` and `remove` rewrote it with the moment they ran, so after adding one capability the field no longer said when PHARN was installed or updated. Both now keep the recorded value; `pharn init`, and `pharn update` when it writes the config, still set it. See [`pharn.config.json`](docs/reference/pharn-config.md).
- **`pharn update` repairs a `pharn.records.json` left behind by an interrupted run.** `pharn add` and `pharn update` write `pharn.records.json` before `pharn.config.json`, so a run interrupted between the two left a store stamped for a state the config never reached. `update` rightly ignores such a store, but at the same skills version it still answered "Already up to date", so nothing repaired it and the next version bump read every file that differed from upstream as `unverifiable` and skipped it. A store that is readable but stamped for another state now re-opens the run: the header names it, the files are decided as usual (your edits are kept), and the store is written again with the config's stamp, after which `update` is up to date again. An absent or unreadable store does not re-open it. `update --dry-run` and `--dry-run --json` take the same branch (the JSON `status` is `planned`). See [`pharn update`](docs/commands/update.md#a-records-store-from-an-interrupted-run).
- **`pharn init` says when archetype detection stopped early.** The file-tree scan examines at most 50,000 entries, 24 directories deep, in sorted name order, and when it reached a bound it just stopped: a project with 50,000 files in `public/` and its UI in `src/App.tsx` detected as `lib`, and nothing said that most of the tree was never looked at. The install summary — in an interactive `init`, `init --yes` and `init --dry-run` alike — now adds `detection stopped early: it examines at most 50,000 entries, 24 directories deep, so these archetypes may be incomplete — pass --archetype <list> if they are wrong`, and `init --dry-run --json` adds `"detectionTruncated": true` (absent otherwise, so other reports are byte-identical; `schemaVersion` stays 1). Directories the scan always skips (`node_modules`, build output, caches) still do not count, and an empty directory past the depth bound is no alarm. The scan also stops as soon as nothing more can change its result — once an `ssr` and a `backend` signal are both found, counting `package.json` — so a Next.js + Express project no longer walks its tree at all, and such a project is never reported as stopped early. See [Troubleshooting](docs/troubleshooting.md#detection-stopped-early).
- **`pharn update` now restores a deleted file at the version you already have.** When your recorded `skillsVersion` already matched upstream, `update` answered "Already up to date" without looking at your project, so a deleted PHARN file — or a whole capability directory — stayed missing until pharn-oss published a new version or you ran `pharn update --force`, which also overwrites your edits. `update` now first checks, locally and without any extra download, whether a capability listed in `pharn.config.json` has lost its directory or a file listed in `pharn.records.json` is gone; if so it runs normally, names the first missing path, and restores what is missing without touching your edits. A path behind a symbolic link is never followed and does not count as missing. `update --dry-run` and `--dry-run --json` take the same branch (the JSON `status` is `planned`). **`pharn remove`'s warning about an auto-selected capability is now accurate:** it used to say the next `pharn update` would reinstall it, but at the same version `update` stops at "Already up to date" and leaves it removed (nothing in your project still records it); the warning now says it comes back with the next update that re-applies your install — at the latest the one that moves to a new pharn-oss version — or now with `pharn update --force`. See [`pharn update`](docs/commands/update.md#missing-files-at-the-same-skills-version).
- **`pharn update` no longer silently downgrades an install when pharn-oss `main` moves back.** If `main`'s `SKILLS_VERSION` was reverted to an older version than the one you installed from it, `update` showed `v2.0.0 → v1.0.0` and applied the older files over every file you had not edited. The release channel already refused this; the default `main` channel now does too: `update` prints `Your install (skills v2.0.0) is newer than pharn-oss main (v1.0.0) — main has moved back to an older version. Nothing changed.`, changes nothing and exits 0. `pharn update --force` downgrades, backing up your edits first as usual; `--yes` does not skip the check. A `pendingSkillsVersion` counts as well, and the check runs before everything that re-opens the "Already up to date" return (so a refused `--ref main` switch is not recorded either). `update --dry-run` reports the same, and `update --dry-run --json` reports it as the new `status` value `ahead-of-main` with `plan: null` (`schemaVersion` stays `1`). `pharn status` now reports such an install as **ahead**, not outdated, so `status --strict` no longer fails demanding an update that would be a downgrade, and `pharn add` names the real ways out instead of sending you to `pharn update`. See [`pharn update`](docs/commands/update.md#an-install-ahead-of-its-source).
- **A re-run `pharn init` now backs up `pharn.config.json` before rewriting it.** `init` rebuilds the config from its own fields, which resets `seam` to pharn's default and `models` to pharn-oss's current block — so a hand-tuned `seam` or `models` block was lost with no copy anywhere, from the one command the docs name for recovery, while the docs said what you could lose was backed up. An existing `pharn.config.json` (a regular file) is now always copied to the same `.pharn-backup/<timestamp>/` as the other files `init` saves, before anything is written — even when it is the only file there — and the overwrite prompt marks it `pharn.config.json (will be rewritten — backed up first)`, listed right after the backed-up files so the 10-path cap cannot hide it. What `init` carries over is unchanged. A first install has no config, so it backs none up. See [`pharn init`](docs/commands/init.md#6-summary).
- **The floor's `fixtures/` are no longer installed into your project.** pharn-oss added a second test-apparatus directory to its floor, `pharn/floor/fixtures/` (13 cost-ledger transcript files), read only by the floor's `*.test.mjs` files — which `pharn` already leaves out. `pharn` excluded only `test-fixtures/` by name, so every install copied these 13 files, `pharn status` drift-tracked them as product, and `pharn update` restored them if you deleted them. `fixtures/` is now excluded exactly like `test-fixtures/`: on the copy side and the expected-file side together, matched only as the floor directory's direct child, so a file merely named `my-fixtures.mjs` or a deeper `lib/fixtures/` directory is unaffected. **Already-installed copies stay** — `pharn update` never deletes — but they drop out of the tracked set: deleting `fixtures/` under your installed floor is safe, and `pharn` will neither restore it nor report it missing.
- **`pharn init` over an existing `.claude/settings.json` now says which PHARN hooks it does not wire.** The file is still preserved, never overwritten or merged, but `init` used to print only "compare it against pharn-oss to wire the PHARN hooks if needed" and then delete the fetched copy, leaving nothing to compare against: in a project already using Claude Code every PHARN hook stayed unwired and `pharn status --strict` failed from the first run. `init` now prints the same `HOOKS` note as `pharn status` and `pharn update` — each missing hook as one line of paste-ready JSON, and that `pharn status --strict` fails until they are wired. When every hook is already wired it prints no note; an unreadable settings file is named with the reason, and the install still completes. See [`pharn init`](docs/commands/init.md#an-existing-claudesettingsjson).
- **A checkout with Windows line endings no longer makes every PHARN file look edited.** When a project is committed and checked out again with `core.autocrlf=true` (the usual Windows setting), git rewrites every installed text file with CRLF line endings. `pharn` compared raw bytes, so every file read as changed: `pharn status` reported every file as differing and `--strict` failed, `pharn update` skipped every file as `modified` and never recorded the new version, and `pharn remove` and `pharn add` backed up files nobody had touched. Every comparison (and every hash written to `pharn.records.json`) now ignores CRLF vs LF in text files: each `\r\n` counts as `\n`. A file is treated as binary, and compared byte for byte, when one of its first 8000 bytes is a NUL byte; a lone `\r` still counts. Existing `pharn.records.json` files stay valid. The cost: an edit that only changes line endings is invisible to `pharn`, so such a file can be updated, overwritten or deleted without a backup (any other change is still detected). This is tested on Linux, including a real `core.autocrlf=true` checkout, but CI does not run on Windows. See [Line endings](docs/troubleshooting.md#line-endings-windows-coreautocrlf).
- **`pharn remove` no longer deletes your files unrecoverably.** `remove` deletes a capability's whole directory, and anything you had put inside it — a notes file, an edit to a persona file — was gone with it, with no prompt and no copy. It now checks every regular file in the directory against `pharn.records.json` first: a file still at the hash `pharn` recorded writing is deleted as before, and every other file (one you added, one you edited, or every file when the store is absent, unreadable or stamped for a different install state) is copied to `.pharn-backup/<timestamp>/` — the same directory `update --force` and `add` use — before anything is deleted, with the directory printed as soon as it exists (`Backed up N file(s) to .pharn-backup/<timestamp> before removing.`). If nothing needs saving, no backup directory is created. If the backup cannot be made, `remove` exits 1 having deleted nothing. Symbolic links inside the directory are deleted as links and not backed up (their targets are never touched). The picker makes one backup for its whole selection, after the confirmation. On a project without a usable `pharn.records.json`, most removals will now write a backup. See [`pharn remove`](docs/commands/remove.md#what-is-backed-up-before-the-delete).
- **A hand-edited `archetypes` in `pharn.config.json` is now reported by name instead of crashing or being silently ignored.** `"archetypes": "ssr"` (a string, not an array) made `pharn list`, `status` and `update` fail with a raw `TypeError` and a stack trace; an unknown entry such as `"bogus"` was silently ignored, so `update` selected capabilities for fewer archetypes than the file listed; and control characters in an entry were printed to the terminal as-is. `list`, `status`, `update`, `add` and `remove` now check `archetypes` when they load the config: it must be an array of `"ssr"`, `"backend"`, `"spa"` or `"lib"`. Anything else exits 1 before any download, naming the field or entry and the value found, with terminal control characters shown as `\uXXXX` escapes; under `--json` the message goes to stderr and stdout stays empty. An absent `archetypes`, an empty array and a repeated entry are still accepted, so every config `pharn` writes keeps loading. See [`pharn.config.json`](docs/reference/pharn-config.md#archetypes--checked-when-the-config-loads).
- **A hand-edited `skillsVersion`, `commit` or `capabilities` in `pharn.config.json` is now reported by name.** `skillsVersion` and `commit` were never checked when the config loaded: a value such as `"1.0"` or a short SHA was compared and recorded as if real, and control characters in `skillsVersion` reached the terminal through `pharn list`, `status` and `update`. In an archetype config, `skillsVersion` must now be a version such as `"3.0.2"` (a prerelease suffix is allowed) and `commit` a full 40-character lowercase hex commit SHA or `null`; anything else exits 1 before any download, naming the field and the value found (escaped and cut short, on stderr under `--json`). An absent `commit` is still accepted, every value `pharn` writes still loads, and a pre-archetype config is not checked. Separately, a `capabilities` that is present but not an array (`"capabilities": "x"`) was read as a pre-archetype install and answered with "Re-run `pharn init`" — which overwrites the file; it is now the same named error as an invalid capability entry. See [`pharn.config.json`](docs/reference/pharn-config.md#skillsversion-and-commit--checked-when-the-config-loads).
- **A product surface pharn-oss does not ship is now named, not silently skipped.** Every fixed surface `pharn` installs — the commands, the hooks, each trusted doc, its `LICENSE` copy, `features/README.md`, and the contracts, `pharn-core` and floor directories — is copied only if the fetched pharn-oss has it, and until now only the trusted docs were reported when one was missing: if pharn-oss moved or renamed any other surface, `init` and `update` installed without it and said nothing, and `pharn status` could not see it either (it only compares the files it expects). Now `init` warns once, naming every such surface by path and kind (and its closing summary no longer says "PHARN commands + hooks written" when either was not); `update` prints a `NOT SHIPPED` note (also under `--dry-run`, and as `plan.absentUpstream` in `--dry-run --json`, present only when there is one; `init --dry-run` prints the same warning, and `init --dry-run --json` carries `absentUpstream`); and `pharn status` lists it under `NOT SHIPPED UPSTREAM` in its DRIFT note, and `--strict` exits 1 while it lasts (`--json`: `drift.absentUpstream`). It is a warning, never a refusal, and it never holds back `update`'s version bump. "Not shipped" means pharn-oss has no file for the surface at its own layout; an install still recorded at the other layout gets a separate `LAYOUT` note from `status` instead (run `pharn update` to move it), which is not a `--strict` input (`--json`: `layout: {recorded, upstream}`). Remaining gaps: the list of surfaces is pharn's own, so a surface pharn-oss adds is neither installed nor reported, and it is checked per surface, not per file — one missing hook script in a hooks directory that still ships others is not reported. See [`pharn status`](docs/commands/status.md) and [`pharn init`](docs/commands/init.md#a-surface-pharn-oss-does-not-ship).
- **Hooks shipped as `.mjs` are installed.** `init` and `update` copied only `.cjs` hooks, so an ES-module hook pharn-oss wires in `settings.json` was never installed and the wiring pointed at a missing script. Hooks are now copied as `.cjs` or `.mjs` (never `*.test.cjs` / `*.test.mjs`), and `pharn status` compares both. An `.mjs` hook's name is held to the same filename allowlist as a `.cjs` one, so an upstream `.mjs` hook named outside it (an uppercase letter, an underscore) now refuses `init`/`update`/`status`, where it used to be skipped in silence.
- **`pharn update` deletes the directory of a capability it drops, so a removed capability stops running.** When your archetypes no longer select an automatically installed capability, or upstream no longer ships one you added by hand, `update` drops it from `pharn.config.json` and reported it as `REMOVED` — but left its directory on disk. PHARN's commands find the grillers and lenses they run by scanning those directories, not by reading the config, so a "removed" capability kept running, `pharn list` no longer showed it, and `pharn remove` could no longer reach it. `update` now deletes that directory in the same run, the way `pharn remove` does: every file in it that `pharn` cannot prove it wrote (one you added, one you edited, or every file without a usable `pharn.records.json`) is first copied to `.pharn-backup/<timestamp>/` — one directory per run, shared with `--force` (`Backed up N file(s) to … before removing.`). The run refuses with nothing changed (exit 1) when the path to the directory crosses a symbolic link or a file in it cannot be read. The deletes happen before any file is written. The confirm says that dropped capabilities are deleted and points to `pharn update --dry-run`, which lists each directory under `WOULD DELETE`; `--dry-run --json` adds `plan.capabilities.removals` (`{role, name, reason, dir, present, backups}`), present only when a capability is dropped — read it as `?? []`; `schemaVersion` stays `1` and a report without a drop is byte-identical to before. This is the only thing `update` deletes; it still never deletes a file upstream stops shipping or a tree left by a layout change, and never touches `.claude/settings.json`. Directories an earlier `pharn` already left behind have no config entry and are not found: delete them by hand. A re-run `pharn init` does the same (below). See [`pharn update`](docs/commands/update.md#dropped-capabilities-are-deleted).
- **A re-run `pharn init` deletes the directory of a capability it drops, after asking.** `init` drops from `pharn.config.json` a hand-added capability upstream no longer ships, and — without saying so — every automatically selected (or pre-`source`) capability your archetypes no longer select; their directories stayed on disk and kept running. Every drop is now named before the summary, the overwrite prompt lists each directory under "will be DELETED" with how many of its files would be backed up (and asks, default No, even when nothing would be overwritten), and on confirm `init` copies every file in it that `pharn` cannot prove it wrote into the run's one `.pharn-backup/<timestamp>/` before deleting the directory and then installing. Declining deletes nothing; a directory behind a symbolic link refuses the install with nothing written. `init --yes` refuses a re-install that would delete a directory (it never deletes without the interactive confirm). `init --dry-run` lists them under `WOULD DELETE`, and `--dry-run --json` adds `capabilities.removals`, present only when there is one. See [`pharn init`](docs/commands/init.md#dropped-capabilities-are-deleted).
- **A refused `pharn init` no longer prints the PHARN banner first.** The logo and the intro line were printed to stdout before the Node version, the `.git` check and the terminal check ran, so `pharn init` in a directory without `.git`, on too old a Node, or in a pipe printed the banner above its error. They are now printed only once those checks pass; `pharn init --dry-run --json` still prints nothing but its JSON object.
- **A capability pharn-oss's own checks accept is no longer skipped as unreadable.** `pharn` reads each upstream capability's `role` and `applies` itself, and its reader was stricter than pharn-oss's validator in three places, so a capability pharn-oss shipped could be listed as one this pharn cannot read and never installed: `applies: universal` written without brackets, `applies` mixing `universal` with archetypes (`[universal, ssr]`), and a field written twice. These now read the way pharn-oss reads them — a single value counts as a one-item list, any `universal` means the capability is always selected, and a repeated field keeps its last value, which must still be a valid role or `applies` token. Three shapes pharn-oss refuses are now refused here too, where `pharn` used to install them: a quoted list (`applies: "[ssr]"`), a repeated field whose last value is empty, and a field that follows a carriage return in the middle of a line. The reader is checked against a pinned copy of pharn-oss's validator.
- **Colour follows one rule, so a piped CI log no longer carries raw escape codes.** The colour in `pharn`'s own text (the banner, headings and highlighted names inside its notes) was decided separately from the prompts and boxes around it: it came on whenever `CI` was set or `FORCE_COLOR` held any non-empty value, `FORCE_COLOR=0` included, even with stdout piped, while the rest of the output stayed plain, so a CI log showed stray `\x1b[…m` sequences in otherwise plain text. Both now follow Node's own rule, the one the prompts already used: `FORCE_COLOR` set to `1`, `2`, `3`, `true` or the empty string turns colour on even in a pipe, and `0` or `false` turns it off; with `FORCE_COLOR` unset, colour is used only on a colour terminal, and `NO_COLOR` or `TERM=dumb` turns it off there. `CI` by itself no longer turns colour on.
- **A project lock with a start time in the future no longer blocks every writer.** A `.pharn.lock` is cleared once it is six hours old or names a pid on this machine that is no longer running. A lock whose start time lay in the future never reached six hours, so if its pid belonged to any running process (a reused pid, or pid 1 in a hand-edited or committed lock) every `pharn add`, `remove`, `update`, `init` and `uninstall` in that project refused forever. A start time more than five minutes ahead is now treated like an unreadable lock and cleared once the file is 10 seconds old.
- **A directory named `.pharn.lock` is no longer moved aside.** `pharn` never creates such a directory, but when one existed it was renamed to `.pharn.lock.<pid>.<hex>` without a word, contents and all. It is now refused with a message naming it and telling you to remove it; nothing is moved. The troubleshooting guide also now explains that a reused pid can keep a dead run's lock looking alive for up to six hours, and corrects the claim that a waiting `pharn init` prompt holds the lock (it takes it only after both prompts; bare `pharn add`'s picker is the one prompt that holds it).

### Added

- **`pharn status` and `pharn update` report the PHARN hooks upstream wires and your project does not.** Upstream re-wired its hooks twice (6.1.0 and 6.12.0). `update` installs the hook scripts but never writes `.claude/settings.json`, so an existing install could keep dead or broken wiring with no signal. `status` now prints a `HOOKS` section, and `status --strict` exits 1 while an upstream hook is unwired; `update` prints the same note and still never writes the file.   - a symlinked `settings.json` file, managed from dotfiles for example, is read through, as Claude Code does. A symlinked `.claude/` directory is refused;
  - a FIFO at a settings path cannot block `status` or `update`.

  Each missing hook is printed as the hook itself, in JSON (an exec-form hook with its `args`), so a pasted line satisfies the check.

### Changed

- **Node 20.13.0 or newer is now required (`engines.node: ">=20.13.0"`; 0.5.0 declared `>=20`).** On Node 20.0–20.11 even `pharn --version` failed at load time with a `SyntaxError`, because the prompt library imports `util.styleText`. On 20.12.x, cancelling a `pharn` confirmation (Esc or Ctrl-C), or a picker after selecting something, crashed with `ERR_INVALID_ARG_VALUE`, exit 1 and a stack trace, instead of "Cancelled" and exit 0: the library passes `styleText` an array of formats, which Node accepts only from 20.13.0, although it declares `>= 20.12.0`. No project was ever changed at that point, so the new floor drops no working setup. `tests/engines.test.ts` fails if a runtime dependency declares a higher floor than ours, or if its shipped code calls a Node API newer than ours. A separate smoke job, `Smoke (node floor)`, starts the packed CLI on exactly the floor.

### Fixed

- **Releases could not publish: the `Pack` step wrote into a directory nothing had created.** Since the release workflow was split into an unprivileged `build` job and a `publish` job, `build` ran `npm pack --pack-destination "$RUNNER_TEMP/pkg"` without creating `pkg/`, and npm does not create it (`ENOENT` on npm 10 and 11). Every Release run would have failed at `Pack` and never reached `publish`. The step now runs `mkdir -p` first, and a live test pins that every workflow's pack destination is created earlier in the job that packs.
- **A re-run `pharn init` no longer destroys your edits.** It used to overwrite every file it installs with no copy anywhere, and its prompt listed 10 of about 400 paths. It now copies to `.pharn-backup/<timestamp>/`, before the first write, every file `pharn update` would have skipped, names that directory as soon as it exists, and lists those files first in the prompt, marked:
  - `(edited)`: the file changed since pharn wrote it;
  - `(no pharn record)`: it differs from upstream and `pharn.records.json` has no entry for it;
  - `(differs from upstream)`: there is no usable records file, so every difference counts.

  A file still exactly as pharn wrote it is a clean upgrade: not marked, not backed up. `PHARN-LICENSE` / `pharn/LICENSE` is compared with upstream's `LICENSE`, like every other file with its source.

- **A re-run `pharn init` keeps what you added by hand.** It used to rebuild `capabilities` from your archetypes alone, dropping every capability you added with `pharn add` while its files stayed. It now applies `update`'s own rules to the config it replaces:
  - A capability you added by hand is installed again and stays `manual`, even when your archetypes now select it too.
  - A capability upstream still ships but this pharn cannot read is left as it is, however it was added. Its config entry, files and records are untouched, and it is listed in `frozenCapabilities`.
  - A hand-added capability upstream no longer ships is dropped from the config, and named; its files stay.
  - Carried entries show as "added by hand" in the install summary, not also under SKIPPED.
- **A re-run `pharn init` dropped the `pharn.config.json` keys you added by hand.** Upstream PHARN reads top-level keys that users add themselves: `testResults` (without it `/pharn-loop` stops with `blocked: no-test-runner`) and `ship.requireAttestation`. `add`, `update` and `remove` kept them, but `init` rebuilt the config from its own fields alone. It now copies every top-level key pharn does not own across from the config it replaces, unchanged. It does so from any file that parses as a JSON object, including one the other commands refuse. Keys pharn owns are still written fresh.
- **No `pharn` command overwrites a config another `pharn` command wrote while it waited.** `add`, `update`, `remove` and `init` read `pharn.config.json` before taking the project lock, and `update`, the `remove` picker and `init` prompt in between. A concurrent run could therefore be overwritten from a stale copy: a `remove` confirmed after a concurrent `add` dropped the added capability while its files stayed. Each now re-checks the file under the lock and refuses, writing nothing, if it changed. And a lock another run is still writing is no longer mistaken for a stale one and broken.
- **A project `init` cannot finish installing into is refused before the first write, and before the overwrite prompt.** A directory where `init` writes a file, or a file where it needs a directory — `pharn.config.json` and `pharn.records.json` included — used to surface part-way through the copy, leaving hundreds of new files with no config and no records. `init` now checks every path first and refuses, naming each one. It does so before asking **Continue and overwrite?**, so you are never asked to confirm an install that could not finish; the check runs again just before the first write. A refused install writes nothing, `.pharn-backup/` included.
- **`pharn add` no longer dead-ends after an `update` that kept your edits.** `update` withholds the `skillsVersion` bump while any file is skipped, so a user keeping one local edit could never finish the upgrade, and `add`'s version gate kept sending them back to `pharn update`. When the bump is withheld only because of your own kept edits (`modified` / `unrecorded`), `update` now records a `pendingSkillsVersion`, and `add` accepts a download at that version while keeping the config's own version. Other skip kinds still refuse, and the refusal names the real ways out.
- **`pharn update` keeps re-checking a capability it had to keep.** When pharn cannot read a capability upstream, `update` keeps it, skips its files, and moves the skills version on. The next run then stopped at "Already up to date" before fetching, so the capability was never checked again, and its files stayed stale even after a pharn upgrade that could read it. `update` now lists such capabilities in `frozenCapabilities` in `pharn.config.json` and fetches while any is listed. One stays listed until none of its files is skipped (for example because you edited it), so each run checks it again.
- **An interrupted run exits non-zero, releases the lock and names the backup.** Ctrl-C while a spinner was running exited 0 and ran no cleanup: `pharn update --force` said "Canceled", left `.pharn.lock` behind, and never named the `.pharn-backup/` it had already made. A real signal did the same (`pharn update --yes` cancelled in CI, or stopped by `timeout` or `docker stop`), and a machine sharing the directory (a container bind mount) had to wait out the six-hour staleness window. An interrupted run now exits 130 (143 for `SIGTERM`), releases the lock and removes the temporary download first, and says the project may be partially updated. `update` names its backup directory the moment it creates it, and again on stderr if the run then fails. A hangup (`SIGHUP`) is deliberately not handled: listening for it would override `nohup`, so a `nohup pharn update` would stop mid-write.
- **A slow download can no longer hang `pharn`.** On Node 20 and 22, a fetch whose time limit had passed could keep reading a slowly dripping response indefinitely, because the abort stopped reaching the body after a garbage collection. `init`, `add`, `update` or `status` could hang, `add` and `update` while holding the project lock. Every fetch now has a hard deadline that holds either way.
- **A slow or failed GitHub API response no longer keeps `pharn` running after it has finished.** When the commit-SHA lookup got an error response (for example a 403 rate limit), or a success whose body was still arriving at the 8-second limit, the command carried on without the SHA as designed, but it left that response unread. The open connection kept the process alive until the server finished sending. It was measured at 30 seconds after `pharn status` had printed its last line. Such responses are now released at once.
- **A capability whose `<name>.md` is not a regular file no longer stops every command.** A directory at that path made `init`, `add`, `update` and `status` abort, so one oddly shaped upstream capability broke every deployed CLI at once. It is now reported as a capability pharn cannot read, like any other. A symbolic link there is never followed, and a FIFO cannot block the read.
- **The capability index reads frontmatter exactly as upstream's validator does.** A closing line that merely starts with `---` (`----`, `--- note`) made pharn skip a capability upstream's own CI accepts, and an empty block (`---` then `---`) was read from the document body instead. A `role` or `applies` key given twice is now reported as unreadable rather than pharn picking one of them, since upstream keeps the last.
- **Archetype detection copes with unusual projects.** A FIFO at `package.json` hung `init`, a symlink to `/dev/zero` was read without bound, and a UTF-8 byte-order mark made the parse fail, so a Next.js app detected as `lib`. `package.json` is now read once, as a regular file of at most 4 MiB, with a leading byte-order mark ignored. Large non-JS trees no longer exhaust the walk before it reaches your source: `__pycache__/` and `.yarn/` are skipped, and so are these, where they are another ecosystem's tree: `target/` beside a `Cargo.toml`, `pom.xml` or `build.sbt`, `vendor/` beside a `go.mod`, `composer.json` or `Gemfile`, and `venv/` or `.venv/` holding a `pyvenv.cfg`. A folder of your own with one of those names, such as the route at `app/target/route.ts`, is still scanned.
- **The proxy notice now says what Node's `fetch` actually does.** It said pharn would never use a configured proxy, which is false once you opt in on a Node that supports it (measured on 22.22.2 and 24): `fetch` then goes through the proxy variables with `NODE_USE_ENV_PROXY=1` or `--use-env-proxy`. The notice now says whether this run uses the proxy, and names the opt-in where your Node has one. It follows Node's measured rules:
  - on Node 24.0–24.4, any non-empty `NODE_USE_ENV_PROXY` turns it on;
  - the `--use_env_proxy` spelling and `--no-use-env-proxy` are recognised;
  - `https_proxy` wins over `HTTPS_PROXY`;
  - a mixed-case name such as `Https_Proxy`, which Node never reads, is not reported;
  - `HTTP_PROXY` alone carries https requests once the opt-in is on.

  Only the notice changes; the network behaviour is Node's.

- **The test suite no longer depends on the proxy settings of the machine running it.** With `NODE_USE_ENV_PROXY=1` set, 15 tests failed that pass in CI. With `HTTPS_PROXY` exported, 1 did. A setup file now clears the proxy variables before every test file.

### Security

- **A hand-edited `pharn.config.json` can no longer make `pharn remove` delete outside a capability directory.** An entry such as `{"name":"../..","role":"lens"}` made `pharn remove ../..` delete the project root, `.git` included. Every `capabilities[]` entry is now validated when the config is read (a capability name and a known role), and a bad one is named, with exit 1. `remove` also deletes only a single directory directly under its role's subtree.
- **`init` and `remove` no longer write or delete through a symbolic link in your project.** With `.claude/commands` or `pharn/` linked to another directory, `init` wrote its files outside the project, overwriting what was there without a prompt. `pharn remove a11y` with `pharn -> ../shared` deleted `../shared/pharn-review/a11y`. Both now refuse, naming each linked component, before writing or deleting anything. A link at a file `init` writes is refused too, since the copy would replace it. `.claude/settings.json` is the exception while its link points at an existing file: `init` never writes an existing settings file, so the link is left alone. A link there that points at nothing is refused.
- **Only a release job that installs nothing can mint the npm publish token.** The release workflow ran `npm ci` and every build and test script in the same job that held `id-token: write`, so any of about 280 dev dependencies could have requested the token and published a malicious version with valid provenance. Releases now build and test in a job with no token, and publish the tested tarball from a job that checks out and installs nothing.
- **Text from upstream never reaches your terminal raw.** Extractor errors printed raw entry names and type bytes, which a hostile archive could use to fake output, erase lines or set the clipboard (OSC 52). The unknown-capability list let Unicode format characters, such as a right-to-left override, through. Every such message now goes through one sanitizer for control and format characters, and so does the fatal-error output. The `HOOKS` note, which asks you to copy hooks by hand, shows those characters and the two Unicode line separators as `\u` escapes, and caps each line at 300 characters.
- **The extractor refuses a tar entry name it cannot write faithfully.** Names are decoded once, as strict UTF-8, and the check, the path rules and the write all use that one string. A name that holds a control or format character, is not valid UTF-8, or starts with a byte-order mark is refused. A raw C1 byte (such as `0x9B`, the terminal CSI) used to land on disk as that control character, where `pharn status` and `pharn update` then printed it raw, and every non-ASCII name was written garbled.
- **A hostile archive can no longer exhaust memory or CPU, or be read leniently.** A 192 KB archive whose pax header inflated to about 128 MB took about 13 s and over 1 GB of memory to parse, and ran out of memory under a 512 MB heap, leaving the temporary download behind. Pax headers are now capped at 64 KiB each, and across all global headers in the archive together, and every header counts toward the entry limit. Framing is strict: a zero block mid-archive, a missing end marker, anything after it, a non-ustar header, and empty or `.` path segments are refused.
- **A malformed numeric header field no longer reaches the error output raw.** It is shown with non-printable bytes escaped, so an archive cannot add a line of its own to the fatal message.
- **A FIFO or a device in place of a pharn file can no longer hang `pharn` or exhaust its memory.** A FIFO at `pharn.config.json`, `pharn.records.json` or `.pharn.lock` made every command that read it wait forever — `pharn update` and a re-run `pharn init` while holding the project lock, so every other `pharn` command in the project was refused too — and a symlink to `/dev/zero` there was read until memory ran out. These files are now read through one bounded, non-blocking reader: anything other than a regular file of at most 16 MiB is treated as unreadable, the way a directory or a permissions problem already was.

## [0.5.0] - 2026-09-10

### Changed — BREAKING

- **Product artifact root relocation (pharn-oss SKILLS_VERSION 5.0.0).** A `pharn`-layout install now writes the product-loop boundary contract to `pharn/features/README.md` instead of the project root. The legacy flat layout is unchanged (`features/README.md`). A pre-relocation clone probe keeps the release-ordering window working.
- **`pharn update` migration advisory** when the records store still tracks the old root path and the resolved install path differs.

### Security

- **`smol-toml` forced off the vulnerable range with an npm `overrides` entry.**
  [GHSA-7w5x-hrqm-74c2](https://github.com/advisories/GHSA-7w5x-hrqm-74c2) / CVE-2026-85730 reports an
  infinite loop in `smol-toml`'s `parse()` for versions `<= 1.7.0`: a value inside an array or inline
  table followed by an unterminated comment resets the parser's cursor instead of ending the scan, and
  `parse()` never returns. `package.json` now declares `overrides: { "smol-toml": "~1.7.1" }`, which
  resolves to `1.7.2`.

  There was **no upstream upgrade path**. `smol-toml` arrives transitively through
  `markdownlint-cli2@0.23.2` — the latest release — which pins it to **exactly `1.7.0`**, so
  `npm audit fix --force` proposed `markdownlint-cli2@0.21.0`: a downgrade across two minors of the
  tool behind `npm run lint:md` and the required CI check `Markdown lint`. The override keeps
  `markdownlint-cli2` at `0.23.2`. The range **permits** future `1.7.x` patches without a
  `package.json` edit, but a range pins nothing: the committed lockfile still fixes `1.7.2` until
  something regenerates it, which is a Dependabot pull request rather than a property of the
  specifier.

  **Scope, stated honestly.** `smol-toml` is a transitive **dev** dependency, and npm never installs a
  published package's `devDependencies` for its consumers — `@pharn-dev/pharn` ships only `dist/`
  (`files`). This clears the alert for **contributors' installs and CI**; it is not a fix to anything
  users of the published CLI ever ran. This repo's markdownlint config is `.markdownlint-cli2.jsonc`,
  so `parse()` was never invoked on any input here and the practical exposure was already nil — the
  change removes a known-vulnerable version from the toolchain rather than closing a live path.

- **The override is pinned by a test, because nothing else enforces it.** There is no `npm audit` step
  in CI, so a `markdownlint-cli2` bump or a regenerated lockfile could drop back below the patch line
  with every gate still green. `tests/dependency-overrides.test.ts` asserts the declared range cannot
  admit a vulnerable version and that **every** `smol-toml` entry in the committed lockfile resolves at
  or above `1.7.1`, reusing `compareVersionCore` (`src/lib/semver.ts`) rather than re-deriving a
  comparator. Both checks are pure functions over a parsed lockfile, so the suite also plants a `1.7.0`
  tree — including one nested under another package — and demonstrates the check **rejects** it; a
  matcher that silently stopped matching, or a comparator read in the wrong direction, would otherwise
  leave every assertion green.
