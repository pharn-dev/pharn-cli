# Changelog

All notable changes to `pharn` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Releases 0.4.0 and older are in [CHANGELOG-ARCHIVE.md](CHANGELOG-ARCHIVE.md).

## [Unreleased]

## [0.21.6] — 2026-11-25

### Fixed

- **`pharn init`, `add`, `update` and `status` work again against pharn-oss v7.25.3 and later.** Those releases commit seven symlinks under `.claude/skills/`, and `pharn` refused any symlink anywhere in the downloaded archive, so every install and update failed on every channel. `pharn` now unpacks only the files pharn-oss's `pharn-install.json` lists, plus the four it reads itself (`pharn-install.json`, `SKILLS_VERSION`, `MIN_CLI`, `.claude/settings.json`); every other archive entry is skipped and never written. A symlink, hard link, pax header, long or `:` name elsewhere in pharn-oss, or pharn-oss growing past 20,000 entries or 128 MB, no longer stops an install. The archive is decompressed as a stream, so the 128 MB cap now applies to the bytes `pharn` writes, not to the whole repository. What is installed is unchanged.

### Security

- **Nothing outside pharn-oss's install list reaches your disk, even in the temporary download directory.** A listed file keeps every rule it had: it must be a regular file with a safe UTF-8 path (no `\`, `:` or `..`, one root), it may appear only once, and a symlink or any other entry type at a listed path is refused. A listed file preceded by a pax extended or GNU long-name header is refused, because `pharn` does not honour those records; a listed file such a header renamed is missing, and the sha256 check of every listed file still refuses the release. New bounds replace the entry and decompressed-size caps: 200,000 archive headers and 1 GiB of decompressed stream (a compression-bomb bound), beside the 32 MB download cap.

## [0.21.5] — 2026-11-24

### Changed

- **The README and the docs now match what the CLI does.** The README names `init --ref main` (the tip of pharn-oss's `main`, against the default `--ref latest`), says that `update --ref latest` or `update --ref main` switches the recorded channel, and mentions the `remove` alias `rm`. The troubleshooting exit-code table, `init`, `status`, `uninstall`, the `pharn.config.json` and `pharn.records.json` references and the roadmap were corrected to the code: a plain `uninstall` exits 1 off a terminal like `init` and `update`, `--yes` and `--dry-run` need none, and `NODE_USE_ENV_PROXY=1` makes Node's `fetch` use a proxy. No command behaviour changes.

## [0.21.4] — 2026-11-23

### Fixed

- **`pharn update --dry-run` now escapes the file names in its `WOULD BACK UP` list.** That list names every file in the directory of a capability dropped from your config that a real run would back up before deleting the directory, and those names come from your project, not from `pharn`. They were printed as they were, so a file name holding a terminal control sequence (for example an ANSI colour code) reached your terminal raw. Each name now goes through the same escaping as every other list in the preview: unsafe characters are removed and a name is cut at 300 characters. Which files are backed up, and what a real run does, is unchanged.

## [0.21.3] — 2026-11-23

### Fixed

- **`pharn update` on the `main` channel no longer erases the recorded `commit` when GitHub will not say which commit `main` is at.** When that lookup failed (an unauthenticated rate limit or a 403), an up-to-date install was re-applied with `updated 0` and `pharn.config.json` and `pharn.records.json` were rewritten with `commit: null`, losing the commit your files were installed from. An unresolved tip now keeps the recorded `commit`: an up-to-date run reports `Up to date.` and writes neither file, and a run that applies a new version records the new version with the previous `commit`. Installs on verified releases were not affected.

- **`pharn update --dry-run --json` no longer reports an install held back by your kept edits as up to date.** When a plan changed nothing only because an edit of yours was kept (the text run ends `Nothing to change.`), the JSON said `status: "up-to-date"` with `plan: null`, so `version.withheld` and `version.pending` were `null` and a script concluded the install was current while `pharn status --json` said it was outdated. `up-to-date` now follows the text outro's rule: nothing changes, nothing is skipped and the recorded version is the one upstream ships. Otherwise the status is `planned`, with a plan that writes nothing and names the skipped file and the version withheld. A truly up-to-date install reports the same bytes as before; `schemaVersion` stays `1` and no key is added. See [`pharn update --dry-run --json`](docs/reference/json-output.md#pharn-update---dry-run---json).

- **An `update` interrupted while it was copying files is now always finished by a plain `pharn update`.** A Ctrl-C or crash after the files landed but before `pharn.records.json` was rewritten left every changed file matching neither its record nor the next release, so if upstream released again before the re-run, those files were reported `modified` and only `--force` finished. `update` now writes the hashes it is about to copy into the store's new optional `incoming` map before the first copy and drops it when it finishes; the next run treats a file whose bytes equal its `incoming` hash as written by `pharn`. The key is additive (`schemaVersion` stays 1), absent when empty, ignored by `pharn` 0.21.2 and older, and a malformed one is ignored rather than making the store unusable. A file you edit after the interruption is still skipped as `modified`. See [A records store from an interrupted run](docs/reference/update-advanced.md#a-records-store-from-an-interrupted-run).

## [0.21.2] — 2026-11-23

### Fixed

- **A pharn-oss release whose manifest names a path outside what `pharn` installs is now refused with a way forward.** `init`, `add`, `update` and `status` still refuse the whole release, but the message now names the path, says the problem is in the pharn-oss release and that nothing in your project was changed, that an existing install keeps working, and to report it at <https://github.com/pharn-dev/pharn-oss/issues> and, once pharn-oss has fixed `main`, to move to it with `pharn update --ref main` (`pharn init --ref main` for a new install). Which paths `pharn` installs into is unchanged. See [A pharn-oss release was refused](docs/troubleshooting.md#a-pharn-oss-release-was-refused).

## [0.21.1] — 2026-11-17

### Changed

- **`pharn --help` no longer says each option belongs to one command.** `--json`, `--yes`, `--ref` and `--dry-run` are taken by several, as the lines below the header already showed. The header now reads "Options (each names the commands that take it; any other command refuses it):".
- **`pharn status --help` now names every condition `--strict` fails on.** The `--strict` line said "exit 1 on any outdated/modified/missing file"; it now reads "exit 1 on an outdated install, a modified, missing or unreadable file, a surface upstream no longer ships, or an unwired hook (under --no-drift, only outdated is checked)", on both `pharn --help` and `pharn status --help`. What `--strict` checks is unchanged. The one full list, including what is never a `--strict` input (orphans, the `PRETTIER`, `NODE` and `MODELS` notes, a hook wired only in `settings.local.json`), is the new "Strict conditions" section of `docs/commands/status.md`, and `docs/README.md`, the troubleshooting exit-code table, the `status --json` summary and the JSON output reference link to it.

### Fixed

- **The `ORPHANED` note no longer says "pharn never deletes them".** `pharn uninstall` deletes an orphan that still equals its record, so `pharn update` and `pharn status` now print "`pharn update` never deletes them" instead. Every delete a `pharn` command makes, the check behind each, and what is never deleted are now listed on one page, [What PHARN deletes](docs/reference/deletes.md), which the command pages link to.

## [0.21.0] — 2026-11-17

### Changed

- **New configs no longer carry `modules`; pharn 0.20.0 is the oldest CLI that can read them.** `pharn init` wrote `"modules": []` into every archetype `pharn.config.json` only because `pharn` 0.3.0 to 0.19.x reads a config without a `modules` array as no config at all. It no longer does, and every write (`init`, `add`, `remove`, `update`) now also drops the fields only older CLIs wrote (`modules`, `constitution`, `installedSkills`, `stackAnswers`, `isMultiTenant`) when it finds them. A config that still carries them loads in every command as before. If a teammate runs `pharn` 0.19.x or older, upgrade it first: it reports _"No pharn.config.json found"_ for a config 0.21.0 wrote, and running `pharn init` there would replace the file.

### Removed

- **The `flat` layout is removed; 0.20.x is the last `pharn` that handles a `flat` install.** It was deprecated in v0.20.0 and announced for removal in v0.22.0; the maintainer shortened that to v0.21.0. A project still recorded at it (`"layout": "flat"` in `pharn.config.json`, or no `layout` key) is now refused by `pharn update` (including `--dry-run` and `--json`), `add`, `remove`, `list`, `status` and `uninstall` with one message: re-run `pharn init`. `init` reinstalls at the `pharn/` layout, keeps the capabilities you added with `pharn add`, and never moves or deletes the old top-level copies: the ones pharn recorded stay listed under `ORPHANED` until you delete them, and `pharn uninstall` removes the unchanged ones. `update` no longer moves an install between layouts, `status` no longer prints a `LAYOUT` note (and `status --strict` no longer fails on a layout mismatch, which can no longer occur), and the `DEPRECATED` note is gone. (A pharn-oss in the flat layout ships no `pharn-install.json`, so the fetch already refuses it.) The `--json` reports keep their keys: `status --json`'s `layout` is always `"pharn"`, and `update --dry-run --json`'s `plan.abandonedLayout` is always `null`. For contributors: `configLayout`, `flatDeprecationLines`, `layoutMismatch`, `add`'s layout gate and the `flat` member of `Layout` are gone.
- **The root-footprint migration is removed; 0.20.x is the last `pharn` that ran it.** Announced for v0.22.0 and moved up to v0.21.0. `pharn update` and a re-run `pharn init` no longer delete a root `THREAT-MODEL.md` or `LIMITS.md` an install from a pharn-oss before 7.0.0 left, print no `ROOT MIGRATION` note, and give no hints about a root `memory-bank/`, `pharn.spec-template.md`, `.pharn/` or an old `.pharn` line in `.gitignore`. A recorded root doc is now an ordinary orphan: listed under `ORPHANED` with its state, its record kept, never deleted by `update` (`pharn uninstall` removes it while it still equals its record). `update --dry-run --json` keeps `plan.rootMigration` as the constant `null`. For contributors: `src/lib/root-migration.ts` is gone.
- **`pharn` no longer writes `"modules": []` or keeps the module-era and wizard fields of `pharn.config.json`; 0.20.x is the last CLI that wrote `modules`.** They still load, and leave the file at its next write. For contributors: `PharnConfig.modules` and `LegacyConfigFields` are gone from `src/types.ts`; `LEGACY_CONFIG_KEYS` in `src/lib/pharn-config.ts` keeps the five names pharn-owned.
- **`pharn` no longer installs from a pharn-oss older than 7.21.0; 0.20.x is the last `pharn` that does.** Such a tree ships no `pharn-install.json`, and `pharn` used to derive the install from pharn-oss's internals instead: the capability list from each capability's frontmatter, the file set by walking the tree, the `models` defaults from its root `pharn.config.json`, and `.claude/settings.json` by probing for it. That derivation is gone. `init`, `update`, `add` and `status` now refuse such a tree right after the download (exit 1, nothing written, the temporary clone removed), with a message that names the tree's `SKILLS_VERSION` and 7.21.0 and says to re-run on the latest release (the default) or with `--ref main`. This also ends installing from a pharn-oss in the `flat` layout or one older than 7.0.0 (trusted docs at the root), since both predate the manifest. An existing install made from one is still updated from the latest release (a `flat` one is asked to re-run `pharn init` instead; see the `flat` layout entry above). pharn-oss's `models` rules stay a pinned copy in `pharn`, because `status` and `update` check your `models` block without a clone; the manifest's `models.rules` is still not read. The support policy had scheduled this removal for v0.22.0; it ships in v0.21.0, one minor after the manifest install (0.20.0), by the maintainer's decision. In `pharn update --dry-run --json`, `plan.rootMigration` is now always `null` (see the root-footprint entry above); `schemaVersion` stays 1 with the same keys.

## [0.20.0] — 2026-11-17

### Added

- **A `pharn` older than the one that last wrote `pharn.config.json` now warns, and still goes ahead.** The config records `pharnVersion`; when your `pharn` is older at major.minor (0.19.x against a config written by 0.20.x, say), `init` over an existing install, `add`, `remove`, `update` and `uninstall` print one line on stderr naming both versions and saying to upgrade (`npm install -g @pharn-dev/pharn@latest`) so teammates on different versions don't undo each other's changes, then carry on as before: nothing is refused and exit codes are unchanged. `pharn status` and every `--dry-run` print it too. It is never on stdout, so every `--json` report is byte-identical. A patch or prerelease difference, or a missing or malformed `pharnVersion`, does not warn. Only a `pharn` with this check can warn: 0.19.x and older never do ([support policy](docs/support-policy.md#teammates-on-different-pharn-versions)).

- **A published support policy.** [`docs/support-policy.md`](docs/support-policy.md) says which installs `pharn` supports (those made by the current minor version and the previous one: from v0.20.0, installs from 0.19.x and 0.20.x), that an older install is answered with one message to re-run `pharn init`, that every `--json` report stays additive within `schemaVersion: 1`, and what is retired when: the root `.pharn.lock` and the `.pharn-backup/` notice and the pre-0.7.0 `models` conversion in v0.20.0, writing `"modules": []` in v0.21.0, and the `flat` layout (deprecated in v0.20.0), pharn-oss trees older than 7.0.0 with the root-footprint migration, and trees without `pharn-install.json` in v0.22.0. The maintainer rules and the list of compatibility shims with their removal versions are in `docs/contributing.md`. Its two notices ship in this release too, each in its own entry: a `pharn` older than the config's `pharnVersion` warns before it writes (above), and `status` and `update` say the `flat` layout is deprecated (under **Deprecated**). The policy itself changes no behaviour.

- **`pharn` installs what pharn-oss declares in `pharn-install.json`, after checking every file's SHA-256.** From pharn-oss 7.21.0 on, the fetched tree carries a manifest of every file an install receives, with its destination, copy policy and SHA-256, plus the selectable capabilities and the `models` defaults. `init`, `update`, `add` and `status` now read it: the files to install, the capability list, whether `.claude/settings.json` is copied (only when you have none, as before) and the `models` block all come from it, so a surface pharn-oss adds under a `pharn-*` name (a new `.claude/skills/pharn-*` directory, say) is installed, recorded, updated, reported when orphaned and removed by `uninstall` with no new `pharn` release. Before anything is written, every declared file's SHA-256 is checked against the downloaded bytes; a mismatch stops the command (exit 1, the file named, nothing written). The manifest is refused as a whole, writing nothing, when its `schemaVersion` is not one this pharn reads (the message says to upgrade pharn), when a destination falls outside the paths pharn may write (anything outside `pharn/` and the `pharn-*` entries of `.claude/`, `.claude/settings.local.json`, a `.git` path, or user data such as `pharn/memory-bank/`), or when any field fails its check. A tree without the manifest (every pharn-oss release before 7.21.0) is installed by `pharn`'s own derivation, exactly as before; that fallback is removed in v0.22.0. No `--json` report changes.

- **`pharn update --force` now lists every file it will overwrite before it asks.** The question reads "Apply this update and overwrite your changes?", but the files were named only by `--dry-run`. An `OVERWRITE` note now precedes it, grouped by why each file needs `--force` (`modified`, `unrecorded`, `unverifiable`), with `pharn.config.json` when your `models` block is replaced. `--yes` prints it too. The dry run's `WOULD OVERWRITE (--force)` groups come from the same code and now also name `pharn.config.json` in that case.

### Changed

- **`pharn update` always checks upstream.** It had a same-version shortcut: when your recorded `skillsVersion` matched upstream it answered "Already up to date" without downloading anything, unless one of eight local checks (a missing file, a missing agent, a root doc an older pharn left, a missing `.gitignore` or `.prettierignore` line, an old `models` block, a `--ref` switch, a capability it kept unread) said otherwise. Anything those checks did not see, such as a capability you removed with `pharn remove`, a layout move, or a file a newer pharn installs, needed `--force`, which also overwrites your edits. Now every run downloads pharn-oss (about 2.5 MB) and plans, at the current version too, and "up to date" means the plan changes nothing: it prints `Up to date.` (or `Nothing to change.` when it keeps an edit of yours), asks nothing, writes nothing, and exits 0. So one plain `pharn update` restores missing files, adds ignore-file lines, converts an old `models` block, records a channel switch, finishes a root migration, moves a layout and reinstalls a removed auto-selected capability, with no `--force`. A run at the current version with no usable `pharn.records.json` now rebuilds it from the files that match upstream. The header note (version, source, archetypes) prints only when the plan changes something. In `update --dry-run --json`, `status: "up-to-date"` now means a plan that changes nothing, still with `plan: null` and the same bytes; a dry run at the current version that would restore a file is `planned`. The ahead-of-source refusal is unchanged and still downloads nothing. `pharn status` (`MISSING`, `LAYOUT`) and `pharn remove` no longer point at `--force` as the way past "Already up to date". A root `THREAT-MODEL.md` or `LIMITS.md` that `update` or a re-run `init` would retire is now re-checked against its record at the delete: one you edit while the prompt is open stops `update` before any write (naming the file) and is kept by `init`, never deleted.

- **A second pharn command is refused while another waits for input.** `init`, `add`, `remove`, `update` and `uninstall` now take the project lock (`pharn/.lock`) before they read `pharn.config.json` or touch the network, and hold it across their prompts to their last write, so each plans once and what you confirm is what is written. A second `pharn` writer started meanwhile refuses with exit 1, naming the waiting command and its pid and saying it may be waiting for input in another terminal; before, `init`, `update`, `uninstall` and the `remove` picker took the lock only after their prompts and re-planned under it. A held lock now refuses `update` and `init` before they download anything. Edits made while a prompt is open are still never lost: `init` backs up a file you edited meanwhile before overwriting it; **`update` now stops before writing anything when a file it was about to write changed while it waited for your answer** (exit 1, with or without `--force`; the file is named and your edit kept, and re-running `update` plans it as yours), where it used to skip that file and carry on; a hand-edit of `pharn.config.json` refuses any of the five commands. `pharn list`, `pharn status` and every `--dry-run` still take no lock.

- **`pharn init` now refuses a project where the features README cannot be written, instead of skipping it.** When the fetched pharn-oss ships `features/README.md` (or `pharn/features/README.md`) and your project has a file named `features`, or a directory at the README's path, `init` used to skip that one file without a word, and every later `pharn update` and `pharn status --strict` reported it as unreadable. Now the pre-flight names the path that is in the way, says to move or rename it, writes nothing and exits 1, as it does for every other file it installs.

- **`pharn init` and `pharn add` now write each file through the same writer as `pharn update`, and name the files already written when a write fails part-way.** Every file is replaced by name (a temporary file, then a rename) after a symlink check of its own path, so a hard-linked or symlinked destination is never written through; `.claude/settings.json` is created only when absent, in one exclusive step. A file edited between the backup scan and its write is backed up first. A write that fails part-way now prints how many files landed and which (the first ten, then a count); as before, no `pharn.records.json` or `pharn.config.json` is written, and the next run backs up any of those files that differ from upstream.

- **`pharn status` no longer compares your files across layouts, and `status --strict` now fails when the install is at another layout than upstream ships.** When `pharn.config.json` records one layout (`flat` or `pharn`) and the fetched pharn-oss uses the other, `status` used to diff your files at the recorded layout's paths: whole capability directories dropped out of the check without being reported as missing, and pharn-oss's own dev floor was compared as if it were the product floor. Now neither the file drift nor the not-shipped-upstream check runs on a mismatch; the `LAYOUT` note takes the `DRIFT` note's place and says that `pharn update` moves the install, and that drift is checked after the move. `status --json` reports `drift: null` with `layout.recorded` and `layout.upstream` set, so `drift: null` now also means a layout mismatch, not only `--no-drift`. Matching layouts are unchanged. `--no-drift` fetches no clone and still cannot see a mismatch.

- **A `pharn.records.json` stamped for another install state is now used, not ignored.** The store records the `skillsVersion` and `commit` of the config it was written with, and every command used to ignore it whenever those disagreed with `pharn.config.json`. `pharn add` and `pharn update` write the store before the config, so a run interrupted between the two left exactly that store, and if upstream released before the next `update`, every file that differed from upstream was skipped as `unverifiable`, lost its record, and was then skipped as `unrecorded` on every later run, until `--force` backed up and overwrote files you never edited. A path whose current hash equals its recorded hash holds bytes `pharn` wrote, whatever the stamp, so the stamp no longer gates: after an interrupted run and an upstream release, your unedited files upgrade, your edited ones are skipped as `modified`, and no `--force` is needed. `update`, `add`, `remove`, `uninstall` (which no longer refuses over a mismatched stamp), `status`'s orphan check and a re-run `init` all use such a store. Every overwrite and every delete still requires the file's hash to equal its record. The stamp is still written, and an absent or unreadable store is still not used. The `pharn.records.json is stamped for a different install state` header line, and the same-version re-run it announced, are gone, since there is nothing left to repair. Two edge cases follow (see `docs/reference/pharn-records.md`): a store left by an older `pharn` that rewrote the tree without updating it labels a file upstream has changed `modified` instead of `unverifiable` (still skipped), and a file you deliberately reverted to bytes such a store recorded is upgraded.

- **`pharn update` and a re-run `pharn init` no longer move a root `memory-bank/` or `pharn.spec-template.md`; they print how to move it yourself.** On a `pharn`-layout install fetching pharn-oss SKILLS 7 or newer, the root-footprint migration used to rename `memory-bank/` to `pharn/memory-bank/` and `pharn.spec-template.md` to `pharn/spec-template.md`, with nothing to prove they were PHARN's: `memory-bank/` is also the folder other tools use, such as Cline's Memory Bank. `update --yes` moved it without asking, declining the prompt did not stop the next run from trying again, and when `pharn/memory-bank/` already existed (`/pharn-memory-promote` writes there) every update that planned changes exited 1. Now neither path is moved, copied, backed up or deleted. The `ROOT MIGRATION` note says it is at the root and gives the command when the `pharn/` path is free (`git mv memory-bank pharn/memory-bank`, or `mv` if git does not track it), or says to merge it by hand when the `pharn/` path already exists, never a `git mv` that would nest the folders. Both copies present no longer fails the run: it exits 0. A root `memory-bank/` or template alone no longer makes an already-current install ask or write anything. The record-proved deletion of the root `THREAT-MODEL.md` / `LIMITS.md` is unchanged. In `update --dry-run --json`, `plan.rootMigration.moves` stays in the report and is always `[]`, and `plan.backups` no longer lists the user data's files; the hint is in the text output only, and `schemaVersion` stays 1. A first `init` still prints no note.

- **A `seam` block in `pharn.config.json` no longer stops any `pharn` command; `pharn` neither checks nor writes it.** `pharn` refused, in every command (`list`, `status --strict` in CI, `update`, `add`, `remove`, `uninstall`), a `seam` block that pharn-oss's own checker accepts, such as one with an extra key (`"note": "…"`) or a repeated step (`["model", "ask", "ask"]`). The block is pharn-oss's: its schema is the `pharn-contracts/seam-config.md` contract, and pharn-oss fills in its default order when the block is absent. `pharn` reads nothing in it, so it now treats it like `models`, passing it through as it is: no command checks it, `add`, `remove` and `update` write it back unchanged (same keys, same order), and a re-run `pharn init` carries it across like any key `pharn` does not own instead of resetting it. A fresh `pharn init` no longer writes a default `seam` block. `init`'s overwrite prompt and its `--dry-run` now say only `models` is reset, and `init --dry-run` lists `seam` among the keys it would keep. An existing block is left exactly as it is.

- **`--json` now implies `--dry-run`, and `--compact` implies `--json`; argv is parsed by Node's `util.parseArgs`.** `pharn update --json` runs `pharn update --dry-run --json`, `pharn update --compact` runs `pharn update --dry-run --json --compact`, and `pharn init --json` (or a bare `pharn --json`) runs `pharn init --dry-run --json`; the `Incomplete option for` refusal is gone, and so is the `minimist` dependency. Argv that used to be accepted is now refused with exit 1: a value on an on/off option (`--json=false`, `--dry-run=false`: `Option takes no value`), and `--no-dry-run`, `--no-yes` and `--drift` (`Unknown option`: `--no-drift` is the only negated option). Two refusals change their message: a repeated `--ref` or `--archetype` now says `Repeated option`, and `--no-ref` / `--no-archetype` say `Unknown option` (both were `Invalid value for`). `Unknown command` escapes control characters in the word it echoes. Every other refusal, `-y`/`-h`/`-v`, `--no-drift` and each command's `--help` page are unchanged apart from the `--json` and `--compact` lines.

- **Internal: commands end through one error type and one exit point.** Exit codes and output are unchanged, except that an unexpected internal error now prints `⚠ <message>` and the `PHARN_DEBUG=1` hint instead of a stack trace (`PHARN_DEBUG=1` still prints the stack).

- **CodeRabbit now skips internal workflow and asset directories during review.** Its repository configuration excludes `.agents/`, `.claude/`, `.codex/`, `.dev/`, `.phargus/`, `.pharn/`, `pharn/` and `assets/`. The Phargus logo asset was also refreshed.

- **Internal: every network read goes through one bounded GET.** The release and commit resolves, the `SKILLS_VERSION` check and the tarball download share `fetchCapped` (`redirect: 'error'`, the deadline and the byte cap) instead of three body readers. An oversized `SKILLS_VERSION` now reads `SKILLS_VERSION too large (over 262144 bytes)`.

- **Internal: the bundle is built for Node 24** (`target: 'node24'`), the floor `engines` already requires, instead of Node 20.

- **`pharn --version`, `--help` and a refused option start faster.** The CLI now loads only the command it runs: the published `dist/` holds `index.js` plus one chunk per command and shared chunks, so `--version` loads neither a command nor `@clack/prompts`.

- **Internal: `pharn status` gathers once and renders its text from the `--json` report.** The text notes and `--strict` verdict now come from the same `StatusReport` object that `--json` prints; the `--json` output is unchanged.

- **The fields only older CLIs wrote leave the documented config type (contributors).** `constitution`, `installedSkills`, `stackAnswers` and `isMultiTenant` are no longer part of `PharnConfig`; the [config reference](docs/reference/pharn-config.md#fields-older-clis-wrote) lists them, with `modules`, under "Fields older CLIs wrote". `pharn init` still writes `"modules": []`, because 0.19.x reads a config without it as no config; it stops in v0.21.0, when 0.20.0, the first CLI that reads a config without `modules`, is the oldest supported one. No behavior changes: an old config with these fields still loads in every command, and `add`, `update` and `remove` still write them back as found.

### Deprecated

- **The `flat` layout is deprecated, and `pharn status` and `pharn update` now say so.** An install recorded at the `flat` layout (PHARN's files at the project root: `"layout": "flat"` in `pharn.config.json`, or no `layout` key) gets a `DEPRECATED` note in `pharn status` (with and without `--no-drift`) and, once per run, in `pharn update` (on `--dry-run`, on an up-to-date run and on the run that moves it). It names v0.22.0, which removes the layout (the code that handles it is marked for removal in v0.22.0), and the way off it: `pharn update` moves the install to the `pharn/` layout, and you delete the old top-level copies it leaves behind. The note is text only and never fails `status --strict`. `--json` output is unchanged. See the [support policy](docs/support-policy.md#the-flat-layout-is-deprecated).

### Removed

- **`pharn update` no longer converts a `models` block in the format releases up to 0.6.0 wrote.** 0.19.x is the last CLI that converted one (a top-level `default`, and the ids `opus-4-8`, `sonnet-5`, `fable-5` and `haiku-4-5` mapped to `opus`, `sonnet`, `fable` and `haiku`), and the last that replaced one of those old defaults with no record of writing it. Any install updated with 0.7.0 or later was already converted. An old-format block is now a block pharn-oss's rules reject, like any other: `pharn status` names what they reject, and `pharn update` replaces it only when its record proves pharn wrote it, and otherwise keeps it as yours. Its `MODELS` note says how to replace it: edit the block by hand, or delete the `models` key so the next `pharn update` writes pharn-oss's; `--force` also works, but overwrites every other file you edited. The JSON reports stay at `schemaVersion` 1 with the same keys: `pharn status --json` `models.conversionNeeded` is always `false` (its verdict is never `old-format`), and `pharn update --dry-run --json` `plan.models.replacedLegacyDefault` is always `false` and `plan.models.conversion` always `null`.

- **The root `.pharn.lock` and `.pharn-backup/` of pharn 0.13.0 and older are no longer read; 0.19.x is the last CLI that honoured them.** From 0.14.0 the lock is `pharn/.lock` and backups go to `pharn/.backup/`, but every writing command still checked for a live root `.pharn.lock` (refusing the run) or a stale one (breaking it), and `init` and `update` (with or without `--dry-run`) printed a reminder while a root `.pharn-backup/` existed. Both are gone, as are `pharn update`'s `.gitignore` hints that suggested `pharn/.backup/` for a `.pharn-backup` line and `pharn/.lock*` for a `.pharn.lock` line (the `.pharn/` → `pharn/.run/` hint stays). A leftover root `.pharn.lock` is now ignored, so do not run pharn 0.13.0 or older in the same project at the same time as a newer one; delete the file, and move what you still need out of `.pharn-backup/` before deleting it. The lock also stops sweeping `pharn/.lock.<pid>.<hex>` files that a run killed while breaking a stale lock can leave behind: nothing reads them, and they are safe to delete when no `pharn` command runs. The lock's other rules, messages and exit codes are unchanged. In `update --dry-run --json`, `plan.rootMigration.gitignoreHints` no longer lists `pharn/.backup/` or `pharn/.lock*`; the shape and `schemaVersion` 1 are unchanged.

### Fixed

- **`pharn uninstall` now removes the `.claude/settings.json` that `pharn init` created, while you have not changed it.** A fresh `init` copies pharn-oss's `settings.json` when your project has none, but never recorded it in `pharn.records.json`, so `uninstall` treated it as yours and left it behind, still wiring hooks to the scripts it had just deleted (the `HOOKS` note listed them). `init` now records the file's hash when it creates it. `uninstall` deletes it while it still matches, removes `.claude/` when that leaves it empty, and keeps the file — listed with your changed files, with the `HOOKS` note as before — once you have edited it. A `settings.json` that existed before `init` is never recorded, so it is never deleted. `update` still never writes the file; it, `add`, `remove` and a re-run `init` keep the record while the file exists. Deleting the file does not make an up-to-date `update` re-run, and the next `update` that has work to do drops the record once. The record is never reported as an orphan or added to `.prettierignore`. The `PLAN` and `UNINSTALLED` notes stop calling the file "left untouched" when it is recorded. Installs made before this release have no record and behave as before; `docs/commands/uninstall.md` says how to check and delete the file by hand.

- **`pharn status` now advises a plain `pharn update` for missing files, not `--force`.** Its `MISSING` note said to run `pharn update --force` at the current version, because a plain `update` used to exit early there. A plain `update` now restores a provably missing file and keeps the files you edited, while `--force` also overwrites every edited file (after backing it up), so following the old advice moved your edits to `pharn/.backup/`. The note, and `docs/commands/status.md`, now read: "Run `pharn update` to restore them (files you edited are kept)." `pharn update`'s warning after skipped files also no longer says "to finish the upgrade" when the install is already at the current skills version: it says there is no upgrade to finish, and offers `--force` only when it can clear a skipped file (real run and `--dry-run`).

- **`pharn init` and `pharn update` now install the review lens agent, `.claude/agents/pharn-review-lens.md`.** pharn-oss ships it from skills version 6.64.0 on, and `/pharn-review` asks for it as the subagent each lens runs in. `pharn` never copied it, so every installed project ran its lenses as a general-purpose agent with more tools, and the review report said so. `.claude/agents/` is now an install surface at the same path in both layouts, under the command name rule (`pharn-*.md`, not `pharn-dev-*`): `init` copies and records it (its closing summary now reads `PHARN commands + hooks + agents written` when an agent landed, and is unchanged otherwise), `update` restores or upgrades it per file and keeps your edits, `status` reports it as missing (and `--strict` fails) when it is gone, `uninstall` deletes it when unchanged and keeps an edited copy, orphan detection and `.prettierignore` cover it. It is not part of the executable unit. A pharn-oss older than 6.64.0 ships no agent, and that is not reported as not shipped upstream. An install already at 6.64.0 or newer with no `pharn-*.md` agent no longer waits for the next version: a plain `pharn update` adds it. An edited agent, or a `.claude/agents` that is a symbolic link or a file, is left alone.

- **A `pharn.config.json` without a `commit` key no longer makes `pharn.records.json` unusable.** An archetype config with no `commit` (a hand-edit, or an older tool) loaded with the key missing, which never matched the record store's `"commit": null` stamp. `pharn update` then ignored the store, so every unedited file that differed from upstream was skipped as `unverifiable` instead of upgraded, and a run that withheld its version bump wrote the store without a `commit` key, after which the store read as invalid for good and only `--force` could finish the upgrade. An absent `commit` in the config is now read as `null`, and so is an absent `commit` in `pharn.records.json`, so stores written by the bug are usable again. A pre-archetype config is unchanged.

- **A `pharn update` with nothing to change no longer asks to confirm or rewrites `pharn.config.json`.** Once a kept edit withheld the version bump (or a capability pharn cannot read was kept), every later run downloaded, asked "Apply this update?" for zero writes, and rewrote `pharn.config.json` with a new `updatedAt` and `pharnVersion`, leaving a diff in a committed file on every run. `update` now checks the plan first. When it would write or restore no file, delete no directory or root doc, move nothing, add no `.gitignore`/`.prettierignore` line, and leave `pharn.records.json` and every other config field as they are, it prints its notes (the `SKIPPED` note still names your edit), asks nothing, writes nothing, and ends with `Nothing to change.`. It ends with `Up to date.` instead when nothing is skipped and the recorded version is current. `updatedAt` and `pharnVersion` now change only on a run that writes something. The comparison uses the config as pharn reads it, so a missing `layout` (the flat layout), a missing `commit` (`null`) or a `ref` other than `"latest"` never forces a write by itself. `update --dry-run` prints `Nothing would be written.` for exactly these plans. When only the state files would change, it now says `Would rewrite only pharn.config.json` (or `pharn.records.json`) instead of the old, wrong `Nothing would be written.`. `update --dry-run --json` reports such a plan as `status: "up-to-date"` with `plan: null`; `schemaVersion` stays 1. Running off a terminal without `--yes` is still refused before any download.

- **An update held back only by your own edits no longer locks out `pharn add`.** When `pharn update` moves to a new skills version and a floor checker, hook or `pharn-*` command was skipped, it holds that whole executable unit at the old version. It then recorded no `pendingSkillsVersion`, so `pharn add` refused with "run `pharn update` first", and running `update` again only held the unit again. Now, when every file that blocked the update is one you edited (`modified` or `unrecorded`), the version the run applied is recorded as `pendingSkillsVersion`, and `pharn add` installs at it, keeping the recorded `skillsVersion` and `commit` as before. `add` writes capability directories only, which are outside the unit and were upgraded anyway. When a blocker is something else (a file `pharn` cannot verify because there is no usable record store, or one it cannot read), nothing is recorded, and `add`'s refusal now says how to see what blocks the update (`pharn update --dry-run`) and names the two ways out: revert those files, or `pharn update --force`. The `EXECUTABLE UNIT` note now also lists held files that are not on disk, such as a hook you deleted: they stay missing until the hold ends. `update --dry-run --json` carries them as `plan.executableUnit.missing`, present only when non-empty; `schemaVersion` stays 1. The note's last line now reads "revert the skipped files" instead of "revert the files above". `pharn update --dry-run --json` now reports a `version.pending` value for such a hold where it reported `null`.

- **`pharn add` with no argument now exits 1 when a pick fails.** A refused pick (for example, its capability directory in your project sits under a symbolic link) was reported, and then the picker ended with `Added N capabilities.`, where N could be 0, and exit code 0. The other picks still install, and the closing line now names every failed pick (`Added 1 capability; 1 failed: griller:a11y.`, or `No capabilities were added; …`) before exiting 1. When every pick lands, the output and exit code are unchanged.

- **`pharn init` in a subdirectory of a git repository no longer suggests `git init`.** In a monorepo's `apps/web` it said `git not found. Run: git init …`, which creates a repository nested inside yours. When a parent directory has `.git`, it now says the directory is inside that repository and to run `pharn init` from the repository root, naming it. Outside any repository the message is unchanged.

- **`pharn init --yes` over an existing install now refuses before downloading anything.** An existing `pharn.config.json` is always one of the files `init` would overwrite, so the refusal was certain, but it came only after the pharn-oss download. It now comes right after the prerequisite checks, with no banner and no network request, naming only `pharn.config.json` (listing the other files needs the download), with the same exit code 1 and the same three ways forward (`pharn init` in a terminal, `pharn init --dry-run`, `pharn update`). The separate "`--yes` never deletes" refusal, which only a re-install could reach, is gone with it, and `init --dry-run`'s `--yes` line now gives the overwrite count in that case. `init --dry-run --yes` still previews, and `yesWouldProceed` in `init --dry-run --json` is unchanged.

- **`pharn init`'s summary prints the archetypes once, keeps long names apart from their values, and no longer says "detected" for `--archetype`.** The archetypes appeared twice, in a note before the summary and again inside it; only the summary shows them now. A capability name long enough to fill the column ran into its value (`missing-error-handling (lens)universal`); every such row, in every note, now keeps at least two spaces. A skipped capability's reason now reads `applies to [backend]; archetypes [ssr]` instead of `…; detected [ssr]`, which was wrong when the archetypes came from `--archetype`. `init --dry-run --json` carries the same new text in `capabilities.skipped[].reason`, and `pharn update` resolves through the same function.

- **A `pharn.config.json` with no `modules` key now loads, and a re-run `pharn init` no longer drops your manual capabilities without saying so.** `modules` is no longer read, but a config without a `modules` array was still treated as absent: every other command said "No pharn.config.json found. Run `pharn init` first.", and the re-run `init` it prescribed carried nothing over. Capabilities you added with `pharn add` were dropped without the usual "Not keeping" warning, and the directories of capabilities it dropped were left on disk, still running, where `pharn remove` could no longer reach them. A config with a string `skillsVersion` and a `capabilities` key now loads in every command whether or not it has `modules`, so a re-run `init` keeps your manual capabilities and names and deletes the ones it drops, as with a full config. A pre-archetype config (`modules` but no `capabilities`) is still refused with the legacy message. A `capabilities` that is not an array now gets its named error with or without `modules`. `init` still writes `"modules": []`, because every released `pharn` up to 0.19.x needs it. When the previous config exists but cannot be read (not valid JSON, a value `pharn` rejects, not a JSON object, no `skillsVersion`), `init`'s summary now says so with the reason, before any prompt and in `--dry-run` (`init --yes` still refuses any existing config before downloading): "the previous pharn.config.json could not be read (…); nothing is carried over, so manual capabilities will be dropped". The reason is the first sentence of the error, cut at 200 characters. `init --dry-run --json` is unchanged.

## [0.19.0] — 2026-11-12

### Added

- **A fresh `pharn init` now lists the hooks of the `.claude/settings.json` it writes.** When your project has no `.claude/settings.json`, `init` copies pharn-oss's — the hook commands Claude Code will run in your project — and used to say nothing about them. It now prints a `HOOKS` note after the install: every hook the file wires, one line of JSON under its event and matcher; how many hook entries it could not show, if any; the file's other top-level settings by name (`It also sets: permissions`); and `Claude Code runs these commands; review .claude/settings.json.` If the file cannot be read (not valid JSON, larger than 256 KB) the note says it was written but its hooks could not be listed. `init --yes` prints the same note, and `init --dry-run` prints it as a preview, with `Would write .claude/settings.json from upstream; see HOOKS.` in its `PLAN`. `init --dry-run --json` adds a `settingsHooks` key (`status`, `hooks`, `otherKeys`, `skipped`, or `status: "unreadable"` with a `reason`), present only when the file would be written; `schemaVersion` stays 1. Over an existing `.claude/settings.json`, and when pharn-oss ships none, the output is unchanged. pharn never runs these commands; the list is for you to review.

### Security

- **A warning built from `pharn.records.json` is now escaped before it reaches the terminal, and every unsafe-character check uses one set.** When `pharn update` cannot use the record store it warns, quoting a file key or the store's `skillsVersion`/`commit` stamp. `pharn.records.json` is committed and can be edited by hand, and the quoting (`JSON.stringify`) escapes ESC but leaves an 8-bit CSI (U+009B) and a right-to-left override (U+202E) as they are, so a crafted store could move the cursor, recolour or reorder what `update` and `update --dry-run` printed. Both now print the quoted value with every unsafe character written as `\uXXXX`, as `pharn uninstall` already did. `update --dry-run --json` is unchanged: its report already escaped the note, once. The unsafe-character set used to be written out five times with drifting members; it is now defined once (C0 and C1 controls, DEL, Unicode format characters, and U+2028/U+2029), and a test fails on a second definition in `src/`. Visible side effects: messages that print the path of a broken `pharn.config.json` now escape control characters in a directory name as `\u001b` instead of `\x1b`, and also escape format characters and line separators; terminal output now strips U+2028/U+2029 like the other unsafe characters; a pharn-oss archive entry whose name contains U+2028 or U+2029 is refused; and a capability name holding a format character is refused as containing control characters rather than as an invalid format, with the name in both messages escaped. Messages for ordinary input, and the `status --json` and `update --dry-run --json` bytes, are unchanged.

- **A pharn-oss archive entry whose name contains a backslash or a colon is now refused.** On macOS and Linux an entry named `a\..\..\evil` was written as one file with that literal name; on Windows the same bytes would be read as a path, and `C:` as a drive. pharn-oss ships neither character, so its real archive installs exactly as before. pax headers are handled more simply, and one case changes: a per-file pax header (typeflag `x`) is still refused, now without reading its contents, and the pax global header every GitHub archive starts with is skipped without being parsed. A global header that sets a `path`, `linkpath` or `size` default used to be refused; it is now ignored, because pharn reads only the ustar fields, so the entries after it land at their own paths under every path rule. pharn now relies on one stated rule: the tree it downloads holds only regular files and directories, in a temporary directory only `pharn` writes. The checks that looked for symbolic links inside that downloaded tree are removed as unreachable; every check on your project's side (symbolic links where pharn writes, hard-linked files, a dangling `.claude/settings.json` link) is unchanged.

### Fixed

- **The project lock no longer breaks a running `pharn` on the same machine because its lock is old, and no longer deletes a lock file it cannot read.** A lock taken on this machine used to be broken once it was six hours old, even while its owner was still running — `pharn add`'s picker holds the lock while you choose, so a picker left open long enough let a second run write at the same time. Now a lock from this machine is broken only when its process is gone, or when it was taken before the machine last booted. A lock from another machine sharing the project directory is still retired after six hours. On release, `pharn` used to delete the lock file whenever it could not read it, which could only ever be another run's lock caught mid-write; it now deletes only a lock that names its own process and machine, and leaves anything else for the next run to judge. What you will see: a second run started while an old `pharn add` picker is still open is refused instead of proceeding. If a killed run's process number has been reused by another program, its lock now refuses until the next reboot rather than for at most six hours; check the named pid with `ps -p <pid>` and delete `pharn/.lock` if it is not `pharn` (see `docs/troubleshooting.md`). A machine with no battery-backed clock, or one whose clock jumps forward a long way after boot, can make a running `pharn` look as if it started before boot, and a clock set back by more than five minutes, or a machine whose hostname changes while `pharn` runs, can also let a running lock be broken (see `docs/troubleshooting.md`).

## [0.18.5] — 2026-11-12

### Security

- **The verified release is resolved as a tag, never as a branch of the same name.** To turn the newest release tag into a commit, pharn asked GitHub for `commits/<tag>`, a bare name. GitHub does not say whether a bare name picks a branch or a tag when both exist, so a branch named like the release tag (for example `v7.10.3`) could have stood in for the verified release. A branch can carry a matching `SKILLS_VERSION`, so the check that the tree's version equals the tag would not have caught it. pharn now asks for `commits/refs/tags/<tag>`, which answers the same commit for the latest release (checked against pharn-oss v7.10.3, an annotated tag). The `main` channel's commit lookup likewise asks for `commits/refs/heads/main`, so a tag named `main` cannot stand in for the branch. Shadowing was never reproduced: GitHub's behaviour for a bare name is undocumented, and this removes the dependence on it.

### Added

- **`pharn init` and `pharn update` keep PHARN's run state and backups out of git.** They append `pharn/.run/` (pharn-oss's runtime scratch — stage logs, gate outputs, cost markers) and `pharn/.backup/` (pharn's backups) to the project's root `.gitignore`, creating it when absent. ### Added

- **`pharn update` and `pharn status` now name the files upstream stopped shipping.** `update` never deletes, so a file pharn-oss dropped — a `pharn-*` command (still a live slash command), a hook, a floor checker, a trusted doc, or one file inside a capability you still have — stayed in your project, and because its entry in `pharn.records.json` was pruned on that same run, no command ever mentioned it again. Such a file is now an **orphan**: both commands list it in an `ORPHANED` note, grouped as `UNCHANGED` (still the bytes pharn wrote), `EDITED` (changed since — review before deleting) or `UNREADABLE` (with the reason), at most 20 per group, with a reminder to delete what you no longer need by hand. `update` keeps the orphan's entry in `pharn.records.json` until the file is gone (a re-run `init` keeps it too), so it stays listed on every later run, and a path upstream ships again later is a clean upgrade instead of an `unrecorded` skip. Once you delete an orphan, the next `update` at the same skills version reads its recorded path as missing and runs once: it restores nothing, drops the entry, and the header now says a missing path is restored only "if upstream still ships it". Orphans are never a skip, never withhold the version bump, and are **not** a `pharn status --strict` input. `update --dry-run --json` gains `plan.orphans` (present only when there is one) and `status --json` gains `orphans` (`null` under `--no-drift`, without a usable records store, or when the clone is at another layout); `schemaVersion` stays 1. - **`pharn init --dry-run` previews a fresh install and writes nothing.** It runs the same checks and the same selection as a real `init` — detection, the fetch, `MIN_CLI`, the capability index, what a re-run would carry over, the destination check — then prints the plan: the summary the interactive run would ask about, every existing file it would overwrite (marked `(edited)`, `(no pharn record)`, `(differs from upstream)` or — for an existing `pharn.config.json` — `(will be rewritten — backed up first)`, exactly as the overwrite prompt marks them), how many files it would create, what it would back up, the `pharn.config.json` it would write and which of your own keys it would keep, whether your `.claude/settings.json` would be preserved and the `HOOKS` note a real run would print, and whether `pharn init --yes` would install. ### Security

- **`pharn.config.json` and `pharn.records.json` can no longer be redirected through a symlink committed beside them.** Both files are written to a temporary file next to them and then renamed into place. That temporary file had a predictable name (`pharn.config.json.<pid>.tmp`) and was opened in a way that followed a symbolic link, so a repository that committed a link at that name could make any `pharn` command that writes the config (or the records store) overwrite a file outside the project that you can write to, and leave `pharn.config.json` itself as a link. The temporary file now gets an unpredictable random name and is created exclusively: an existing entry at the name, a link included, is never opened or followed, and `pharn` tries a fresh name instead (after 8 taken names it stops with an error and writes nothing). File contents and permissions are written exactly as before.
- **`pharn remove` re-checks for a symbolic link under the lock, right before it deletes.** `remove` refused a capability directory whose path crossed a symbolic link — but only before taking the project lock and, on the picker path, before its confirmation. A folder such as `pharn-review/` replaced by a link while the confirmation was open was deleted through, removing files outside the project (unless a file there needed a backup, which then refused by accident). The same check now runs again under the lock, before the backup and the first delete; the early check stays, so a selection that would be refused is still never asked about.
- **Resolving the tip of pharn-oss `main` now reads at most 1 KiB.** Before downloading, `pharn` asks the GitHub API which commit `main` points at. It asked for the full commit object — whose size grows with the files the last merge touched — and read the answer with no size limit, the one network read without one. It now asks for the bare commit id (as `--ref latest` already does) and stops reading past 1 KiB. An oversized answer is treated like any other failed lookup: the install continues from the tip of `main` and records no commit, as documented in `LIMITS.md` §3b.
- **`pharn update` no longer overwrites a file outside your project through a hard link.** `update` refused to write through a symbolic link, but a hard link is a second name for the same file and looks like an ordinary file, so no check could see it: if an installed file was a hard link to a file elsewhere, `update` wrote the new contents into that shared file, changing it outside the project too. `update` now writes each file to a new temporary file beside it and renames it into place, so only the name inside your project gets the new contents and the other file keeps its own. File contents and permissions are the same as before. One visible difference: an installed file you made read-only is now replaced like any other, as `init` already did — what `update` needs is write permission on its folder. `init` and `add` were already safe from hard links: the copy method they use replaces an existing file rather than writing into it (a test now pins that).

### Fixed

- **`pharn add` and `pharn remove` no longer move `installedAt`.** `installedAt` in `pharn.config.json` is documented as the time of the install or last update, but `add` and `remove` rewrote it with the moment they ran, so after adding one capability the field no longer said when PHARN was installed or updated. Both now keep the recorded value; `pharn init`, and `pharn update` when it writes the config, still set it. See [`pharn.config.json`](docs/reference/pharn-config.md).
- **`pharn update` repairs a `pharn.records.json` left behind by an interrupted run.** `pharn add` and `pharn update` write `pharn.records.json` before `pharn.config.json`, so a run interrupted between the two left a store stamped for a state the config never reached. `update` rightly ignores such a store, but at the same skills version it still answered "Already up to date", so nothing repaired it and the next version bump read every file that differed from upstream as `unverifiable` and skipped it. A store that is readable but stamped for another state now re-opens the run: the header names it, the files are decided as usual (your edits are kept), and the store is written again with the config's stamp, after which `update` is up to date again. An absent or unreadable store does not re-open it. `update --dry-run` and `--dry-run --json` take the same branch (the JSON `status` is `planned`). See [`pharn update`](docs/reference/update-advanced.md#a-records-store-from-an-interrupted-run).
- **`pharn init` says when archetype detection stopped early.** The file-tree scan examines at most 50,000 entries, 24 directories deep, in sorted name order, and when it reached a bound it just stopped: a project with 50,000 files in `public/` and its UI in `src/App.tsx` detected as `lib`, and nothing said that most of the tree was never looked at. The install summary — in an interactive `init`, `init --yes` and `init --dry-run` alike — now adds `detection stopped early: it examines at most 50,000 entries, 24 directories deep, so these archetypes may be incomplete — pass --archetype <list> if they are wrong`, and `init --dry-run --json` adds `"detectionTruncated": true` (absent otherwise, so other reports are byte-identical; `schemaVersion` stays 1). Directories the scan always skips (`node_modules`, build output, caches) still do not count, and an empty directory past the depth bound is no alarm. The scan also stops as soon as nothing more can change its result — once an `ssr` and a `backend` signal are both found, counting `package.json` — so a Next.js + Express project no longer walks its tree at all, and such a project is never reported as stopped early. See [Troubleshooting](docs/troubleshooting.md#detection-stopped-early).
- **`pharn update` now restores a deleted file at the version you already have.** When your recorded `skillsVersion` already matched upstream, `update` answered "Already up to date" without looking at your project, so a deleted PHARN file — or a whole capability directory — stayed missing until pharn-oss published a new version or you ran `pharn update --force`, which also overwrites your edits. `update` now first checks, locally and without any extra download, whether a capability listed in `pharn.config.json` has lost its directory or a file listed in `pharn.records.json` is gone; if so it runs normally, names the first missing path, and restores what is missing without touching your edits. A path behind a symbolic link is never followed and does not count as missing. `update --dry-run` and `--dry-run --json` take the same branch (the JSON `status` is `planned`). **`pharn remove`'s warning about an auto-selected capability is now accurate:** it used to say the next `pharn update` would reinstall it, but at the same version `update` stops at "Already up to date" and leaves it removed (nothing in your project still records it); the warning now says it comes back with the next update that re-applies your install — at the latest the one that moves to a new pharn-oss version — or now with `pharn update --force`. See [`pharn update`](docs/reference/update-advanced.md#missing-files-at-the-same-skills-version).
- **`pharn update` no longer silently downgrades an install when pharn-oss `main` moves back.** If `main`'s `SKILLS_VERSION` was reverted to an older version than the one you installed from it, `update` showed `v2.0.0 → v1.0.0` and applied the older files over every file you had not edited. The release channel already refused this; the default `main` channel now does too: `update` prints `Your install (skills v2.0.0) is newer than pharn-oss main (v1.0.0) — main has moved back to an older version. Nothing changed.`, changes nothing and exits 0. `pharn update --force` downgrades, backing up your edits first as usual; `--yes` does not skip the check. A `pendingSkillsVersion` counts as well, and the check runs before everything that re-opens the "Already up to date" return (so a refused `--ref main` switch is not recorded either). `update --dry-run` reports the same, and `update --dry-run --json` reports it as the new `status` value `ahead-of-main` with `plan: null` (`schemaVersion` stays `1`). `pharn status` now reports such an install as **ahead**, not outdated, so `status --strict` no longer fails demanding an update that would be a downgrade, and `pharn add` names the real ways out instead of sending you to `pharn update`. See [`pharn update`](docs/commands/update.md#an-install-ahead-of-its-source).
- **A re-run `pharn init` now backs up `pharn.config.json` before rewriting it.** `init` rebuilds the config from its own fields, which resets `seam` to pharn's default and `models` to pharn-oss's current block — so a hand-tuned `seam` or `models` block was lost with no copy anywhere, from the one command the docs name for recovery, while the docs said what you could lose was backed up. An existing `pharn.config.json` (a regular file) is now always copied to the same `.pharn-backup/<timestamp>/` as the other files `init` saves, before anything is written — even when it is the only file there — and the overwrite prompt marks it `pharn.config.json (will be rewritten — backed up first)`, listed right after the backed-up files so the 10-path cap cannot hide it. What `init` carries over is unchanged. A first install has no config, so it backs none up. See [`pharn init`](docs/commands/init.md#6-summary).
- **The floor's `fixtures/` are no longer installed into your project.** pharn-oss added a second test-apparatus directory to its floor, `pharn/floor/fixtures/` (13 cost-ledger transcript files), read only by the floor's `*.test.mjs` files — which `pharn` already leaves out. `pharn` excluded only `test-fixtures/` by name, so every install copied these 13 files, `pharn status` drift-tracked them as product, and `pharn update` restored them if you deleted them. `fixtures/` is now excluded exactly like `test-fixtures/`: on the copy side and the expected-file side together, matched only as the floor directory's direct child, so a file merely named `my-fixtures.mjs` or a deeper `lib/fixtures/` directory is unaffected. **Already-installed copies stay** — `pharn update` never deletes — but they drop out of the tracked set: deleting `fixtures/` under your installed floor is safe, and `pharn` will neither restore it nor report it missing.
- **`pharn init` over an existing `.claude/settings.json` now says which PHARN hooks it does not wire.** The file is still preserved, never overwritten or merged, but `init` used to print only "compare it against pharn-oss to wire the PHARN hooks if needed" and then delete the fetched copy, leaving nothing to compare against: in a project already using Claude Code every PHARN hook stayed unwired and `pharn status --strict` failed from the first run. `init` now prints the same `HOOKS` note as `pharn status` and `pharn update` — each missing hook as one line of paste-ready JSON, and that `pharn status --strict` fails until they are wired. When every hook is already wired it prints no note; an unreadable settings file is named with the reason, and the install still completes. See [`pharn init`](docs/commands/init.md#an-existing-claudesettingsjson).
- **A checkout with Windows line endings no longer makes every PHARN file look edited.** When a project is committed and checked out again with `core.autocrlf=true` (the usual Windows setting), git rewrites every installed text file with CRLF line endings. `pharn` compared raw bytes, so every file read as changed: `pharn status` reported every file as differing and `--strict` failed, `pharn update` skipped every file as `modified` and never recorded the new version, and `pharn remove` and `pharn add` backed up files nobody had touched. Every comparison (and every hash written to `pharn.records.json`) now ignores CRLF vs LF in text files: each `\r\n` counts as `\n`. A file is treated as binary, and compared byte for byte, when one of its first 8000 bytes is a NUL byte; a lone `\r` still counts. Existing `pharn.records.json` files stay valid. The cost: an edit that only changes line endings is invisible to `pharn`, so such a file can be updated, overwritten or deleted without a backup (any other change is still detected). This is tested on Linux, including a real `core.autocrlf=true` checkout, but CI does not run on Windows. See [Line endings](docs/troubleshooting.md#line-endings-windows-coreautocrlf).
- **`pharn remove` no longer deletes your files unrecoverably.** `remove` deletes a capability's whole directory, and anything you had put inside it — a notes file, an edit to a persona file — was gone with it, with no prompt and no copy. It now checks every regular file in the directory against `pharn.records.json` first: a file still at the hash `pharn` recorded writing is deleted as before, and every other file (one you added, one you edited, or every file when the store is absent, unreadable or stamped for a different install state) is copied to `.pharn-backup/<timestamp>/` — the same directory `update --force` and `add` use — before anything is deleted, with the directory printed as soon as it exists (`Backed up N file(s) to .pharn-backup/<timestamp> before removing.`). If nothing needs saving, no backup directory is created. If the backup cannot be made, `remove` exits 1 having deleted nothing. Symbolic links inside the directory are deleted as links and not backed up (their targets are never touched). The picker makes one backup for its whole selection, after the confirmation. On a project without a usable `pharn.records.json`, most removals will now write a backup. See [`pharn remove`](docs/commands/remove.md#what-is-backed-up-before-the-delete).
- **A hand-edited `archetypes` in `pharn.config.json` is now reported by name instead of crashing or being silently ignored.** `"archetypes": "ssr"` (a string, not an array) made `pharn list`, `status` and `update` fail with a raw `TypeError` and a stack trace; an unknown entry such as `"bogus"` was silently ignored, so `update` selected capabilities for fewer archetypes than the file listed; and control characters in an entry were printed to the terminal as-is. `list`, `status`, `update`, `add` and `remove` now check `archetypes` when they load the config: it must be an array of `"ssr"`, `"backend"`, `"spa"` or `"lib"`. Anything else exits 1 before any download, naming the field or entry and the value found, with terminal control characters shown as `\uXXXX` escapes; under `--json` the message goes to stderr and stdout stays empty. An absent `archetypes`, an empty array and a repeated entry are still accepted, so every config `pharn` writes keeps loading. See [`pharn.config.json`](docs/reference/pharn-config.md#archetypes--checked-when-the-config-loads).
- **A hand-edited `skillsVersion`, `commit` or `capabilities` in `pharn.config.json` is now reported by name.** `skillsVersion` and `commit` were never checked when the config loaded: a value such as `"1.0"` or a short SHA was compared and recorded as if real, and control characters in `skillsVersion` reached the terminal through `pharn list`, `status` and `update`. In an archetype config, `skillsVersion` must now be a version such as `"3.0.2"` (a prerelease suffix is allowed) and `commit` a full 40-character lowercase hex commit SHA or `null`; anything else exits 1 before any download, naming the field and the value found (escaped and cut short, on stderr under `--json`). An absent `commit` is still accepted, every value `pharn` writes still loads, and a pre-archetype config is not checked. Separately, a `capabilities` that is present but not an array (`"capabilities": "x"`) was read as a pre-archetype install and answered with "Re-run `pharn init`" — which overwrites the file; it is now the same named error as an invalid capability entry. See [`pharn.config.json`](docs/reference/pharn-config.md#skillsversion-and-commit--checked-when-the-config-loads).
- **A product surface pharn-oss does not ship is now named, not silently skipped.** Every fixed surface `pharn` installs — the commands, the hooks, each trusted doc, its `LICENSE` copy, `features/README.md`, and the contracts, `pharn-core` and floor directories — is copied only if the fetched pharn-oss has it, and until now only the trusted docs were reported when one was missing: if pharn-oss moved or renamed any other surface, `init` and `update` installed without it and said nothing, and `pharn status` could not see it either (it only compares the files it expects). Now `init` warns once, naming every such surface by path and kind (and its closing summary no longer says "PHARN commands + hooks written" when either was not); `update` prints a `NOT SHIPPED` note (also under `--dry-run`, and as `plan.absentUpstream` in `--dry-run --json`, present only when there is one; `init --dry-run` prints the same warning, and `init --dry-run --json` carries `absentUpstream`); and `pharn status` lists it under `NOT SHIPPED UPSTREAM` in its DRIFT note, and `--strict` exits 1 while it lasts (`--json`: `drift.absentUpstream`). It is a warning, never a refusal, and it never holds back `update`'s version bump. "Not shipped" means pharn-oss has no file for the surface at its own layout; an install still recorded at the other layout gets a separate `LAYOUT` note from `status` instead (run `pharn update` to move it), which is not a `--strict` input (`--json`: `layout: {recorded, upstream}`). Remaining gaps: the list of surfaces is pharn's own, so a surface pharn-oss adds is neither installed nor reported, and it is checked per surface, not per file — one missing hook script in a hooks directory that still ships others is not reported. See [`pharn status`](docs/commands/status.md) and [`pharn init`](docs/commands/init.md#a-surface-pharn-oss-does-not-ship).
- **Hooks shipped as `.mjs` are installed.** `init` and `update` copied only `.cjs` hooks, so an ES-module hook pharn-oss wires in `settings.json` was never installed and the wiring pointed at a missing script. Hooks are now copied as `.cjs` or `.mjs` (never `*.test.cjs` / `*.test.mjs`), and `pharn status` compares both. An `.mjs` hook's name is held to the same filename allowlist as a `.cjs` one, so an upstream `.mjs` hook named outside it (an uppercase letter, an underscore) now refuses `init`/`update`/`status`, where it used to be skipped in silence.
- **`pharn update` deletes the directory of a capability it drops, so a removed capability stops running.** When your archetypes no longer select an automatically installed capability, or upstream no longer ships one you added by hand, `update` drops it from `pharn.config.json` and reported it as `REMOVED` — but left its directory on disk. PHARN's commands find the grillers and lenses they run by scanning those directories, not by reading the config, so a "removed" capability kept running, `pharn list` no longer showed it, and `pharn remove` could no longer reach it. `update` now deletes that directory in the same run, the way `pharn remove` does: every file in it that `pharn` cannot prove it wrote (one you added, one you edited, or every file without a usable `pharn.records.json`) is first copied to `.pharn-backup/<timestamp>/` — one directory per run, shared with `--force` (`Backed up N file(s) to … before removing.`). The run refuses with nothing changed (exit 1) when the path to the directory crosses a symbolic link or a file in it cannot be read. The deletes happen before any file is written. The confirm says that dropped capabilities are deleted and points to `pharn update --dry-run`, which lists each directory under `WOULD DELETE`; `--dry-run --json` adds `plan.capabilities.removals` (`{role, name, reason, dir, present, backups}`), present only when a capability is dropped — read it as `?? []`; `schemaVersion` stays `1` and a report without a drop is byte-identical to before. This is the only thing `update` deletes; it still never deletes a file upstream stops shipping or a tree left by a layout change, and never touches `.claude/settings.json`. Directories an earlier `pharn` already left behind have no config entry and are not found: delete them by hand. A re-run `pharn init` does the same (below). See [`pharn update`](docs/commands/update.md#dropped-capabilities-are-deleted).
- **A re-run `pharn init` deletes the directory of a capability it drops, after asking.** `init` drops from `pharn.config.json` a hand-added capability upstream no longer ships, and — without saying so — every automatically selected (or pre-`source`) capability your archetypes no longer select; their directories stayed on disk and kept running. Every drop is now named before the summary, the overwrite prompt lists each directory under "will be DELETED" with how many of its files would be backed up (and asks, default No, even when nothing would be overwritten), and on confirm `init` copies every file in it that `pharn` cannot prove it wrote into the run's one `.pharn-backup/<timestamp>/` before deleting the directory and then installing. Declining deletes nothing; a directory behind a symbolic link refuses the install with nothing written. `init --yes` refuses a re-install that would delete a directory (it never deletes without the interactive confirm). `init --dry-run` lists them under `WOULD DELETE`, and `--dry-run --json` adds `capabilities.removals`, present only when there is one. See [`pharn init`](docs/commands/init.md#dropped-capabilities-are-deleted).
- **A refused `pharn init` no longer prints the PHARN banner first.** The logo and the intro line were printed to stdout before the Node version, the `.git` check and the terminal check ran, so `pharn init` in a directory without `.git`, on too old a Node, or in a pipe printed the banner above its error. They are now printed only once those checks pass; `pharn init --dry-run --json` still prints nothing but its JSON object.
- **A capability pharn-oss's own checks accept is no longer skipped as unreadable.** `pharn` reads each upstream capability's `role` and `applies` itself, and its reader was stricter than pharn-oss's validator in three places, so a capability pharn-oss shipped could be listed as one this pharn cannot read and never installed: `applies: universal` written without brackets, `applies` mixing `universal` with archetypes (`[universal, ssr]`), and a field written twice. These now read the way pharn-oss reads them — a single value counts as a one-item list, any `universal` means the capability is always selected, and a repeated field keeps its last value, which must still be a valid role or `applies` token. Three shapes pharn-oss refuses are now refused here too, where `pharn` used to install them: a quoted list (`applies: "[ssr]"`), a repeated field whose last value is empty, and a field that follows a carriage return in the middle of a line. The reader is checked against a pinned copy of pharn-oss's validator.
- **Colour follows one rule, so a piped CI log no longer carries raw escape codes.** The colour in `pharn`'s own text (the banner, headings and highlighted names inside its notes) was decided separately from the prompts and boxes around it: it came on whenever `CI` was set or `FORCE_COLOR` held any non-empty value, `FORCE_COLOR=0` included, even with stdout piped, while the rest of the output stayed plain, so a CI log showed stray `\x1b[…m` sequences in otherwise plain text. Both now follow Node's own rule, the one the prompts already used: `FORCE_COLOR` set to `1`, `2`, `3`, `true` or the empty string turns colour on even in a pipe, and `0` or `false` turns it off; with `FORCE_COLOR` unset, colour is used only on a colour terminal, and `NO_COLOR` or `TERM=dumb` turns it off there. `CI` by itself no longer turns colour on.
- **A project lock with a start time in the future no longer blocks every writer.** A `.pharn.lock` is cleared once it is six hours old or names a pid on this machine that is no longer running. A lock whose start time lay in the future never reached six hours, so if its pid belonged to any running process (a reused pid, or pid 1 in a hand-edited or committed lock) every `pharn add`, `remove`, `update`, `init` and `uninstall` in that project refused forever. A start time more than five minutes ahead is now treated like an unreadable lock and cleared once the file is 10 seconds old.
- **A directory named `.pharn.lock` is no longer moved aside.** `pharn` never creates such a directory, but when one existed it was renamed to `.pharn.lock.<pid>.<hex>` without a word, contents and all. It is now refused with a message naming it and telling you to remove it; nothing is moved. The troubleshooting guide also now explains that a reused pid can keep a dead run's lock looking alive for up to six hours, and corrects the claim that a waiting `pharn init` prompt holds the lock (it takes it only after both prompts; bare `pharn add`'s picker is the one prompt that holds it).

## [0.6.0] — 2026-09-25

### Added

- **`pharn status` and `pharn update` report the PHARN hooks upstream wires and your project does not.** Upstream re-wired its hooks twice (6.1.0 and 6.12.0). `update` installs the hook scripts but never writes `.claude/settings.json`, so an existing install could keep dead or broken wiring with no signal. `status` now prints a `HOOKS` section, and `status --strict` exits 1 while an upstream hook is unwired; `update` prints the same note and still never writes the file. Hooks you added yourself never count against you. The check reads what Claude Code reads:
  - both `.claude/settings.json` and your per-user `.claude/settings.local.json`, as one union. A hook wired only in `settings.local.json` counts as wired: `--strict` passes, and the note says it reaches neither teammates nor CI;
  - a symlinked `settings.json` file, managed from dotfiles for example, is read through, as Claude Code does. A symlinked `.claude/` directory is refused;
  - a FIFO at a settings path cannot block `status` or `update`.

  Each missing hook is printed as the hook itself, in JSON (an exec-form hook with its `args`), so a pasted line satisfies the check.

### Changed

- **Node 20.13.0 or newer is now required (`engines.node: ">=20.13.0"`; 0.5.0 declared `>=20`).** On Node 20.0–20.11 even `pharn --version` failed at load time with a `SyntaxError`, because the prompt library imports `util.styleText`. On 20.12.x, cancelling a `pharn` confirmation (Esc or Ctrl-C), or a picker after selecting something, crashed with `ERR_INVALID_ARG_VALUE`, exit 1 and a stack trace, instead of "Cancelled" and exit 0: the library passes `styleText` an array of formats, which Node accepts only from 20.13.0, although it declares `>= 20.12.0`. No project was ever changed at that point, so the new floor drops no working setup. `tests/engines.test.ts` fails if a runtime dependency declares a higher floor than ours, or if its shipped code calls a Node API newer than ours. A separate smoke job, `Smoke (node floor)`, starts the packed CLI on exactly the floor.

### Fixed

- **Releases could not publish: the `Pack` step wrote into a directory nothing had created.** Since the release workflow was split into an unprivileged `build` job and a `publish` job, `build` ran `npm pack --pack-destination "$RUNNER_TEMP/pkg"` without creating `pkg/`, and npm does not create it (`ENOENT` on npm 10 and 11). Every Release run would have failed at `Pack` and never reached `publish`. The step now runs `mkdir -p` first, and a live test pins that every workflow's pack destination is created earlier in the job that packs.
- **A re-run `pharn init` no longer destroys your edits.** It used to overwrite every file it installs with no copy anywhere, and its prompt listed 10 of about 400 paths. It now copies to `.pharn-backup/<timestamp>/`, before the first write, every file `pharn update` would have skipped, names that directory as soon as it exists, and lists those files first in the prompt, marked:
  - `(edited)`: the file changed since pharn wrote it;
  - `(no pharn record)`: it differs from upstream and `pharn.records.json` has no entry for it;
  - `(differs from upstream)`: there is no usable records file, so every difference counts.

  A file still exactly as pharn wrote it is a clean upgrade: not marked, not backed up. `PHARN-LICENSE` / `pharn/LICENSE` is compared with upstream's `LICENSE`, like every other file with its source.

- **A re-run `pharn init` keeps what you added by hand.** It used to rebuild `capabilities` from your archetypes alone, dropping every capability you added with `pharn add` while its files stayed. It now applies `update`'s own rules to the config it replaces:
  - A capability you added by hand is installed again and stays `manual`, even when your archetypes now select it too.
  - A capability upstream still ships but this pharn cannot read is left as it is, however it was added. Its config entry, files and records are untouched, and it is listed in `frozenCapabilities`.
  - A hand-added capability upstream no longer ships is dropped from the config, and named; its files stay.
  - Carried entries show as "added by hand" in the install summary, not also under SKIPPED.
- **A re-run `pharn init` dropped the `pharn.config.json` keys you added by hand.** Upstream PHARN reads top-level keys that users add themselves: `testResults` (without it `/pharn-loop` stops with `blocked: no-test-runner`) and `ship.requireAttestation`. `add`, `update` and `remove` kept them, but `init` rebuilt the config from its own fields alone. It now copies every top-level key pharn does not own across from the config it replaces, unchanged. It does so from any file that parses as a JSON object, including one the other commands refuse. Keys pharn owns are still written fresh.
- **No `pharn` command overwrites a config another `pharn` command wrote while it waited.** `add`, `update`, `remove` and `init` read `pharn.config.json` before taking the project lock, and `update`, the `remove` picker and `init` prompt in between. A concurrent run could therefore be overwritten from a stale copy: a `remove` confirmed after a concurrent `add` dropped the added capability while its files stayed. Each now re-checks the file under the lock and refuses, writing nothing, if it changed. And a lock another run is still writing is no longer mistaken for a stale one and broken.
- **A project `init` cannot finish installing into is refused before the first write, and before the overwrite prompt.** A directory where `init` writes a file, or a file where it needs a directory — `pharn.config.json` and `pharn.records.json` included — used to surface part-way through the copy, leaving hundreds of new files with no config and no records. `init` now checks every path first and refuses, naming each one. It does so before asking **Continue and overwrite?**, so you are never asked to confirm an install that could not finish; the check runs again just before the first write. A refused install writes nothing, `.pharn-backup/` included.
- **`pharn add` no longer dead-ends after an `update` that kept your edits.** `update` withholds the `skillsVersion` bump while any file is skipped, so a user keeping one local edit could never finish the upgrade, and `add`'s version gate kept sending them back to `pharn update`. When the bump is withheld only because of your own kept edits (`modified` / `unrecorded`), `update` now records a `pendingSkillsVersion`, and `add` accepts a download at that version while keeping the config's own version. Other skip kinds still refuse, and the refusal names the real ways out.
- **`pharn update` keeps re-checking a capability it had to keep.** When pharn cannot read a capability upstream, `update` keeps it, skips its files, and moves the skills version on. The next run then stopped at "Already up to date" before fetching, so the capability was never checked again, and its files stayed stale even after a pharn upgrade that could read it. `update` now lists such capabilities in `frozenCapabilities` in `pharn.config.json` and fetches while any is listed. One stays listed until none of its files is skipped (for example because you edited it), so each run checks it again.
- **An interrupted run exits non-zero, releases the lock and names the backup.** Ctrl-C while a spinner was running exited 0 and ran no cleanup: `pharn update --force` said "Canceled", left `.pharn.lock` behind, and never named the `.pharn-backup/` it had already made. A real signal did the same (`pharn update --yes` cancelled in CI, or stopped by `timeout` or `docker stop`), and a machine sharing the directory (a container bind mount) had to wait out the six-hour staleness window. An interrupted run now exits 130 (143 for `SIGTERM`), releases the lock and removes the temporary download first, and says the project may be partially updated. `update` names its backup directory the moment it creates it, and again on stderr if the run then fails. A hangup (`SIGHUP`) is deliberately not handled: listening for it would override `nohup`, so a `nohup pharn update` would stop mid-write.
- **A slow download can no longer hang `pharn`.** On Node 20 and 22, a fetch whose time limit had passed could keep reading a slowly dripping response indefinitely, because the abort stopped reaching the body after a garbage collection. `init`, `add`, `update` or `status` could hang, `add` and `update` while holding the project lock. Every fetch now has a hard deadline that holds either way.
- **A slow or failed GitHub API response no longer keeps `pharn` running after it has finished.** When the commit-SHA lookup got an error response (for example a 403 rate limit), or a success whose body was still arriving at the 8-second limit, the command carried on without the SHA as designed, but it left that response unread. The open connection kept the process alive until the server finished sending. It was measured at 30 seconds after `pharn status` had printed its last line. Such responses are now released at once.
- **A capability whose `<name>.md` is not a regular file no longer stops every command.** A directory at that path made `init`, `add`, `update` and `status` abort, so one oddly shaped upstream capability broke every deployed CLI at once. It is now reported as a capability pharn cannot read, like any other. A symbolic link there is never followed, and a FIFO cannot block the read.
- **The capability index reads frontmatter exactly as upstream's validator does.** A closing line that merely starts with `---` (`----`, `--- note`) made pharn skip a capability upstream's own CI accepts, and an empty block (`---` then `---`) was read from the document body instead. A `role` or `applies` key given twice is now reported as unreadable rather than pharn picking one of them, since upstream keeps the last.
- **Archetype detection copes with unusual projects.** A FIFO at `package.json` hung `init`, a symlink to `/dev/zero` was read without bound, and a UTF-8 byte-order mark made the parse fail, so a Next.js app detected as `lib`. `package.json` is now read once, as a regular file of at most 4 MiB, with a leading byte-order mark ignored. Large non-JS trees no longer exhaust the walk before it reaches your source: `__pycache__/` and `.yarn/` are skipped, and so are these, where they are another ecosystem's tree: `target/` beside a `Cargo.toml`, `pom.xml` or `build.sbt`, `vendor/` beside a `go.mod`, `composer.json` or `Gemfile`, and `venv/` or `.venv/` holding a `pyvenv.cfg`. A folder of your own with one of those names, such as the route at `app/target/route.ts`, is still scanned.
- **The proxy notice now says what Node's `fetch` actually does.** It said pharn would never use a configured proxy, which is false once you opt in on a Node that supports it (measured on 22.22.2 and 24): `fetch` then goes through the proxy variables with `NODE_USE_ENV_PROXY=1` or `--use-env-proxy`. The notice now says whether this run uses the proxy, and names the opt-in where your Node has one. It follows Node's measured rules:
  - on Node 24.0–24.4, any non-empty `NODE_USE_ENV_PROXY` turns it on;
  - the `--use_env_proxy` spelling and `--no-use-env-proxy` are recognised;
  - `https_proxy` wins over `HTTPS_PROXY`;
  - a mixed-case name such as `Https_Proxy`, which Node never reads, is not reported;
  - `HTTP_PROXY` alone carries https requests once the opt-in is on.

  Only the notice changes; the network behaviour is Node's.

- **The test suite no longer depends on the proxy settings of the machine running it.** With `NODE_USE_ENV_PROXY=1` set, 15 tests failed that pass in CI. With `HTTPS_PROXY` exported, 1 did. A setup file now clears the proxy variables before every test file.

### Security

- **A hand-edited `pharn.config.json` can no longer make `pharn remove` delete outside a capability directory.** An entry such as `{"name":"../..","role":"lens"}` made `pharn remove ../..` delete the project root, `.git` included. Every `capabilities[]` entry is now validated when the config is read (a capability name and a known role), and a bad one is named, with exit 1. `remove` also deletes only a single directory directly under its role's subtree.
- **`init` and `remove` no longer write or delete through a symbolic link in your project.** With `.claude/commands` or `pharn/` linked to another directory, `init` wrote its files outside the project, overwriting what was there without a prompt. `pharn remove a11y` with `pharn -> ../shared` deleted `../shared/pharn-review/a11y`. Both now refuse, naming each linked component, before writing or deleting anything. A link at a file `init` writes is refused too, since the copy would replace it. `.claude/settings.json` is the exception while its link points at an existing file: `init` never writes an existing settings file, so the link is left alone. A link there that points at nothing is refused.
- **Only a release job that installs nothing can mint the npm publish token.** The release workflow ran `npm ci` and every build and test script in the same job that held `id-token: write`, so any of about 280 dev dependencies could have requested the token and published a malicious version with valid provenance. Releases now build and test in a job with no token, and publish the tested tarball from a job that checks out and installs nothing.
- **Text from upstream never reaches your terminal raw.** Extractor errors printed raw entry names and type bytes, which a hostile archive could use to fake output, erase lines or set the clipboard (OSC 52). The unknown-capability list let Unicode format characters, such as a right-to-left override, through. Every such message now goes through one sanitizer for control and format characters, and so does the fatal-error output. The `HOOKS` note, which asks you to copy hooks by hand, shows those characters and the two Unicode line separators as `\u` escapes, and caps each line at 300 characters.
- **The extractor refuses a tar entry name it cannot write faithfully.** Names are decoded once, as strict UTF-8, and the check, the path rules and the write all use that one string. A name that holds a control or format character, is not valid UTF-8, or starts with a byte-order mark is refused. A raw C1 byte (such as `0x9B`, the terminal CSI) used to land on disk as that control character, where `pharn status` and `pharn update` then printed it raw, and every non-ASCII name was written garbled.
- **A hostile archive can no longer exhaust memory or CPU, or be read leniently.** A 192 KB archive whose pax header inflated to about 128 MB took about 13 s and over 1 GB of memory to parse, and ran out of memory under a 512 MB heap, leaving the temporary download behind. Pax headers are now capped at 64 KiB each, and across all global headers in the archive together, and every header counts toward the entry limit. Framing is strict: a zero block mid-archive, a missing end marker, anything after it, a non-ustar header, and empty or `.` path segments are refused.
- **A malformed numeric header field no longer reaches the error output raw.** It is shown with non-printable bytes escaped, so an archive cannot add a line of its own to the fatal message.
- **A FIFO or a device in place of a pharn file can no longer hang `pharn` or exhaust its memory.** A FIFO at `pharn.config.json`, `pharn.records.json` or `.pharn.lock` made every command that read it wait forever — `pharn update` and a re-run `pharn init` while holding the project lock, so every other `pharn` command in the project was refused too — and a symlink to `/dev/zero` there was read until memory ran out. These files are now read through one bounded, non-blocking reader: anything other than a regular file of at most 16 MiB is treated as unreadable, the way a directory or a permissions problem already was.

## [0.5.0] - 2026-09-10

### Changed — BREAKING

- **Product artifact root relocation (pharn-oss SKILLS_VERSION 5.0.0).** A `pharn`-layout install now writes the product-loop boundary contract to `pharn/features/README.md` instead of the project root. The legacy flat layout is unchanged (`features/README.md`). A pre-relocation clone probe keeps the release-ordering window working.
- **`pharn update` migration advisory** when the records store still tracks the old root path and the resolved install path differs.

### Security

- **`smol-toml` forced off the vulnerable range with an npm `overrides` entry.**
  [GHSA-7w5x-hrqm-74c2](https://github.com/advisories/GHSA-7w5x-hrqm-74c2) / CVE-2026-85730 reports an
  infinite loop in `smol-toml`'s `parse()` for versions `<= 1.7.0`: a value inside an array or inline
  table followed by an unterminated comment resets the parser's cursor instead of ending the scan, and
  `parse()` never returns. `package.json` now declares `overrides: { "smol-toml": "~1.7.1" }`, which
  resolves to `1.7.2`.

  There was **no upstream upgrade path**. `smol-toml` arrives transitively through
  `markdownlint-cli2@0.23.2` — the latest release — which pins it to **exactly `1.7.0`**, so
  `npm audit fix --force` proposed `markdownlint-cli2@0.21.0`: a downgrade across two minors of the
  tool behind `npm run lint:md` and the required CI check `Markdown lint`. The override keeps
  `markdownlint-cli2` at `0.23.2`. The range **permits** future `1.7.x` patches without a
  `package.json` edit, but a range pins nothing: the committed lockfile still fixes `1.7.2` until
  something regenerates it, which is a Dependabot pull request rather than a property of the
  specifier.

  **Scope, stated honestly.** `smol-toml` is a transitive **dev** dependency, and npm never installs a
  published package's `devDependencies` for its consumers — `@pharn-dev/pharn` ships only `dist/`
  (`files`). This clears the alert for **contributors' installs and CI**; it is not a fix to anything
  users of the published CLI ever ran. This repo's markdownlint config is `.markdownlint-cli2.jsonc`,
  so `parse()` was never invoked on any input here and the practical exposure was already nil — the
  change removes a known-vulnerable version from the toolchain rather than closing a live path.

- **The override is pinned by a test, because nothing else enforces it.** There is no `npm audit` step
  in CI, so a `markdownlint-cli2` bump or a regenerated lockfile could drop back below the patch line
  with every gate still green. `tests/dependency-overrides.test.ts` asserts the declared range cannot
  admit a vulnerable version and that **every** `smol-toml` entry in the committed lockfile resolves at
  or above `1.7.1`, reusing `compareVersionCore` (`src/lib/semver.ts`) rather than re-deriving a
  comparator. Both checks are pure functions over a parsed lockfile, so the suite also plants a `1.7.0`
  tree — including one nested under another package — and demonstrates the check **rejects** it; a
  matcher that silently stopped matching, or a comparator read in the wrong direction, would otherwise
  leave every assertion green.
