# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`pharn` is an interactive CLI that installs [PHARN](https://github.com/pharn-dev/pharn-oss) — a workflow for shipping features right with Claude Code — into an existing project (framework-agnostic). `pharn init` detects the project's **archetype(s)** (`ssr`/`backend`/`spa`/`lib`) and installs the applicable PHARN **capabilities** (grillers/lenses) from `pharn-dev/pharn-oss` via a codeload tarball download of the tip of `main` (or, with `--ref latest`, the newest **verified release**), copying them plus the fixed product surfaces into the mirrored layout (`.claude/` + `pharn/`) and writing `pharn.config.json`. No module catalog / `manifest.json` fetch. Published on npm as `@pharn-dev/pharn`, exposing a single `pharn` bin. Targets Claude Code today; Codex and Cursor are planned.

**Module model (removed).** Earlier releases installed by _modules_ driven by a repo-root `manifest.json` (schemaVersion 1/2 + a `wizard` block + per-module `module.json` `installs` maps), and kept a module/manifest fallback in `add`/`update`/`list`/`status`/`remove` for a pre-archetype config. **That subsystem is gone** (`lib/manifest.ts`, `install-modules.ts`, `installer.ts`, `wizard.ts` deleted) — live pharn-oss ships no `manifest.json`, so the fallback 404'd. **All commands are archetype-only.** A pre-archetype (module) `pharn.config.json` (one with `modules[]` but no `capabilities[]`) is detected by `isArchetypeConfig` and rejected up front by `loadArchetypeConfigOrExit` with a clear "re-run `pharn init`" message (`LEGACY_CONFIG_MESSAGE`) — never a fetch. **This CLI still owns the `pharn.config.json` schema — for every key EXCEPT `models`, whose schema and defaults pharn-oss owns** (maintainer decision, 2026-09-25; see the `models` paragraph below). The CLI-owned schema stays additive: a legacy config's now-unused fields (`modules`, `constitution`, `installedSkills`, `stackAnswers`) still LOAD (P7).

## Commands

```bash
npm run dev -- init          # run the CLI from source via tsx (= npx tsx src/index.ts init)
npm run build                # rm dist → tsc --noEmit (typecheck) → esbuild bundle+minify → dist/index.js
npm run build:install-local  # build + install dist/bin into every local test-*/ app's node_modules
npm run typecheck            # tsc --noEmit for src AND tests (two configs)
npm run lint                 # eslint src tests scripts --max-warnings 0 (any warning fails)
npm run lint:md              # markdownlint-cli2 over docs/**/*.md + *.md
npm run format:check         # prettier check (use `format` to write)
npm test                     # vitest run (single pass)
npm run test:watch
npm run test:coverage        # vitest run --coverage (CI runs this)
npm run check                # format:check + lint + lint:md + typecheck + test (aggregate; no build, no coverage gate)
npx vitest run tests/install-capabilities.test.ts   # single test file
```

CI (`.github/workflows/ci.yml`) runs six gates independently — format:check, lint, lint:md, typecheck, test (via `test:coverage`), and build — all must pass. Each gate is its **own job**, so each reports its **own status check** and one red gate can neither mask nor be masked by another (this replaced a single `check` job whose six steps shared one context and leaned on `if: always()`). The six job `name:` values — `Format check`, `Lint`, `Markdown lint`, `Typecheck`, `Test`, `Build` — are a **contract with the `main` branch ruleset**, which lists exactly those strings in `required_status_checks` (alongside `floor`, `gitleaks`, and `Analyze (javascript-typescript)` from the other workflows): GitHub reports a job under its `name:`, so renaming one makes a required check unreportable and blocks every PR on a context nothing produces. The ruleset also requires two checks no workflow here produces — `Socket Security: Project Report` and `Socket Security: Pull Request Alerts`, reported by the Socket GitHub App — so they are absent from the workflow-derived list and from `REQUIRED_CONTEXTS`; if Socket renames one, the ruleset must be edited. `tests/ci-workflow.test.ts` pins the names, their npm scripts, and the runner/node pair; it cannot see the ruleset, so the other half of that invariant stays advisory. Gates run on **ubuntu-latest / node 24 only**, so two support claims are wider than what is tested: `engines.node: ">=24.2.0"` (the test suite runs on Node 24's latest, never on 24.2.0 itself; a separate, non-required `Smoke (node floor)` workflow, `node-floor.yml`, starts the packed CLI on exactly the floor — its `FLOOR` is pinned equal to `package.json`'s bound — and `tests/engines.test.ts` fails if a runtime dependency declares a higher floor OR its shipped code calls a Node API newer than ours, via a measured known-API table: today `@clack/*` passes `styleText` an ARRAY of formats, which Node accepts only from 20.13.0, so it holds with room to spare). **The floor is 24.2.0 because pharn-oss's floor CLIs refuse to run below it** (their `import.meta.main` gate used to exit 0 having checked nothing on an older Node, a silent false green; pharn-oss 6.50.0 made them exit 2 with one stderr line). The CLI enforces the same number at runtime: `lib/node-floor.ts` (`NODE_FLOOR`, pinned equal to `engines.node` by `tests/node-floor.test.ts`; FAIL-CLOSED — an unparseable `process.versions.node`, or a prerelease of the floor itself, is refused, the opposite of the fail-open `MIN_CLI` gate) feeds `steps/node-prereq.ts` (`runNodePrereq`), the FIRST step of `init` and `update` (before the git prerequisite, the config load, the TTY gate and every network call; exit 1, stderr, nothing written; kept out of `steps/prereqs.ts` because the command suites mock that module wholesale), and `status`'s read-only `NODE` note (the floor, the running Node, a `MISMATCH` line — reported, never fatal, never a `--strict` input). `add`/`remove`/`list` do not check it and the absence of an `os` field (Windows implied; the `win32` branches of `toPosix`/`symlink-guard` never run in CI). Both are documented in `docs/contributing.md`. Closing either by **matrixing one of the six jobs would rename its reported context and block every PR** — a separate, additionally-named job is the only safe shape. A second workflow, `.github/workflows/publish.yml`, runs on every push to `main` and publishes to npm when that push carries a new version — see **Releasing** below. `PHARN_DEBUG=1` enables full error output for fetch/install failures.

## Releasing

Canonical npm package: **`@pharn-dev/pharn`** (org-scoped) — the **installed binary stays `pharn`**. The unscoped `pharn` is **not publishable**: npm rejects it with **E403** as too similar to existing packages (`yarn`, `charm`, `sharp`), and a scoped name sidesteps that similarity check. An earlier `@pharn-dev/pharn@0.2.0` was published then **unpublished on 2026-07-22**, so `0.2.0` is permanently burned on this name — releases resume at `0.3.0`.

Release flow: **the version bump travels in the feature PR, and merging it is the release.** The PR bumps `version` in `package.json` + `package-lock.json` (`npm version --no-git-tag-version X.Y.Z`) and moves its `[Unreleased]` entries under a new `## [X.Y.Z] — YYYY-MM-DD` CHANGELOG heading (plus the compare links); `tests/release-consistency.test.ts`, in the required `Test` check, fails the PR when the lockfile disagrees or `scripts/release-notes.mjs` finds no non-empty section for that version. **`.github/workflows/publish.yml` runs on every push to `main`** (and `workflow_dispatch`, for recovery) and publishes via **npm Trusted Publishing (OIDC)** — workflow `publish.yml`, environment `npm-publish`, node 24 (npm >= 11.5.1), `npm publish --provenance` (the flag overrides `publishConfig.provenance: false`, so releases carry a signed provenance attestation). It is **four jobs**, serialized by a workflow-level `concurrency` group (`cancel-in-progress: false`): `gate` refuses any ref but `main`, requires `package.json` `version` to be plain `X.Y.Z`, and asks `git ls-remote --exit-code` whether `v<version>` exists — exit 0 → nothing to release (the run ends green; this is every dependabot/docs merge), exit 2 → release, anything else → fail; `build` (no `id-token`) re-checks the version and that the commit is on `main`, extracts the release notes (before `npm ci`), runs `check` + `test:coverage`, packs, smoke-installs and uploads tarball + notes; `publish` is the ONLY job with `id-token: write` + the environment, checks out and installs nothing, reads the registry's HTTP status for the version (200 → skip, 404 → publish, else fail — so a re-run never double-publishes) and runs `npm publish <tgz> --ignore-scripts`; `release` is the ONLY job with `contents: write`, checks out and installs nothing, and runs `gh release create vX.Y.Z --target <sha> --notes-file` (a Release that already exists is left alone). npm before the tag, so a tag always means "on npm"; a Release created with `GITHUB_TOKEN` triggers no other workflow, which is why tagging lives in this run. So no dev-dependency code runs where the OIDC token is requestable; `.dev/floor/check-run-pins.test.mjs` pins that the grant appears once, inside the `publish` job (sliced to its own job), which installs nothing, and that `release` holds no `id-token`; `tests/publish-workflow.test.ts` pins the triggers, the job graph and the one `contents: write`, and EXECUTES the committed `Decide` and `Registry check` steps against a stub `git` and a local HTTP server. Nothing gates a merged bump on a human click while the `npm-publish` environment has no required reviewers (a GitHub setting, not code).

**No npm tokens exist anywhere** — no repo secrets, none in Actions; auth is the short-lived OIDC id-token exchanged at publish time. If a token ever seems to be "needed," the Trusted Publisher config is broken — fix it on npmjs.com, **never** add a secret.

**First-publish exception:** the very first publish of a _new_ package name is a manual, local `npm publish` (provenance off) by a maintainer, because npm only allows configuring a Trusted Publisher on an _existing_ package. Every later release goes through `publish.yml`. Full maintainer steps: [`docs/RELEASING.md`](docs/RELEASING.md).

## ESM / module conventions

ESM-only (`"type": "module"`, NodeNext). **Relative imports must use `.js` extensions** even though the source is `.ts` (e.g. `import { runInit } from './commands/init.js'`). `tsconfig.json` sets `strict` and `noUncheckedIndexedAccess` — index access is `T | undefined`, hence the `!` assertions on validated array indices.

## Architecture

`src/index.ts` parses argv with minimist and dispatches to `commands/{init,add,remove,update,list,status,uninstall}.ts`. `init` is the default command. **Options are per-command, and an option a command does not take is REFUSED** (`Unsupported option for \`status\`: "--force"`, one stderr line + a pointer at pharn --help + exit 1, never the whole usage text, which scrolled the error away) —`ALLOWED_FLAGS`is the per-command table beside the positional-arity`MAX_POSITIONALS`, a`Map`for the same reason (`cmd`is untrusted argv, and an object lookup would resolve`Object.prototype`keys), with the same absent-row-means-no-check semantics (so`pharn bogus --json`keeps the more useful "Unknown command"). Rows are derived from what each command READS:`init: archetype, ref, yes, dry-run, json`,`update: force, yes, ref, dry-run, json, compact`,`list: json`,`status: strict, drift, json`(`drift`is the canonical key, so`--no-drift`lives there),`uninstall: yes`,`add`/`remove`/`rm`: **none**;`help`/`version`are in every row. The **global`boolean:`declaration list is computed FROM that table**, so a flag declared for nobody is unrepresentable — the exact shape of the closed defect, where`list --strict`,`add --json`and (until`status`took it)`status --json`parsed, were dropped, and exited 0 (`pharn status --json | jq`got clack chrome and a success code; with no command word,`pharn --json`/`--force`/`--strict`ran a full install). The offender list comes from a SECOND minimist parse of the same argv under just that command's declarations, keeping only its`unknown`verdicts — never from`Object.keys(argv)`, which cannot distinguish passed from defaulted (minimist sets every declared boolean to`false`), nor from a value-differs test, which reads`--json=false`as absent. Only the flag NAME is checked; value shape is deliberately out of scope. A **second table,`REQUIRED_WITH`**(a`Map`, same absent-row-means-no-check semantics), answers what the first cannot: may a flag the command takes be passed ALONE. Today it has two commands:`update`, with two pairs —`--json`needs`--dry-run`, and`--compact`needs`--json`(single-level:`update --compact --dry-run`names only the`--json`gap,`update --json --compact`only the`--dry-run`one) — and`init`, with one:`--json`needs`--dry-run`(so a bare`pharn --json`, whose command defaults to`init`, is refused as an`Incomplete option for`error naming`init`).`--compact`omits the`noop`entries of the`--json`dry-run report's`plan.files`(counts stay complete) and marks itself with a top-level`compact: true`and`plan.filesOmitted: {action, count}`— both absent without the flag, so the default`schemaVersion: 1`bytes are unchanged;`runUpdate`fails closed on it without`json`. And`unmetRequirements`reads presence the way the dispatch does (`Boolean(argv[flag])`), so`--dry-run=false --json`refuses too. The refusal is an "Incomplete option for" error naming the command, with the same stderr + pointer + exit 1, at the same position (right after the unsupported-flag gate, above the short-circuits, so`pharn update --json --help`refuses). Both refusals sit **above** the`--version`/`--help`short-circuits, so a genuine`--help`licenses neither an unknown nor a misapplied sibling (`pharn status --help --force`refuses;`pharn status --help`does not); the arity gate stays below them.`refuse()`de-duplicates offenders, since minimist names a short bundle once per unknown letter. Every non-init command loads the config via`loadArchetypeConfigOrExit`(uninstall first answers an ABSENT config itself, benignly — see its note below)(which rejects a pre-archetype config, above) — except`list`, which does its own json-aware check so its error stays on stderr under`--json`.`list`is read-only (reads`pharn.config.json`only — no clone, no fetch, no writes);`--json`emits a single inventory object on stdout (diagnostics to stderr).`status`is also read-only (the read side of`update`) — see its addressing note below.`remove`(alias`rm`) is the inverse of`add`— see its addressing note below (`remove`has NO`--yes`: its NAMED path never confirms, and the bare picker's one confirm is unconditional). **The two prompting commands hard-fail off a TTY.**`init`and`update`each read`process.std*.isTTY`into the shared, already-exported`interactiveAllowed`(`lib/capability-picker.ts`— imported, never re-implemented; a static test pins that no`src/**`file reads`isTTY`outside an`interactiveAllowed({…})`argument, so this repo has exactly ONE such predicate) and`exit(1)`rather than rendering a prompt into a dead stream. Before this, the confirm cancelled on stream end through`cancelAndExit`'s **exit(0)** —`echo "" | pharn update`reported success having done nothing, and piped`init`paid for a full clone first, since`fetchRepo`precedes its first prompt. Each gate sits AFTER that command's promptless local step (`update`:`loadArchetypeConfigOrExit`;`init`:`runGitPrereq`) so the actionable error still wins, and BEFORE any network call, so a refusal costs zero round-trips.`update --yes`/`-y`is the way through: it skips **the confirm and nothing else** (the note still prints; plan/apply, drift-safe skips, the withheld version bump, and every exit code are byte-identical), works in a TTY too, and composes with`--force`— which does NOT imply it.`init --yes`/`-y`is NOT that: init's second prompt is the destructive overwrite confirmation, and auto-confirming it in a pipeline is the hazard it exists to prevent — so init's`--yes`skips only the summary confirm (the summary still prints) and installs ONLY when none of its write targets exists (`assertNoExistingTargets`,`lib/write-targets.ts`: the overwrite prompt's own target set, manifest ∪`pharn.config.json`). Anything there →`OverwriteRefusedError`, reported like a held lock (exit 1, nothing written, the targets listed with the prompt's marks, pointing at interactive`init`,`init --dry-run`and`update`); a re-install therefore ALWAYS refuses it. The check runs before the lock and again under it (after`assertConfigFingerprintUnchanged`, before`runInstallArchetype`), so it never answers the overwrite question — there is none to answer. The gate is skipped for`init --dry-run`(writes nothing) and`init --yes`; plain`init`off a TTY still refuses, naming both. The uninstall command's one confirm follows the same rule (the same predicate, exit 1 off a TTY), and its --yes / -y skips it. TTY cancel semantics are unchanged — a human choosing Cancel is still a graceful exit 0; only EOF masquerading as that choice is now unreachable.

**Help is per-command.** `pharn <cmd> --help` prints `commandUsage(cmd)` (`src/index.ts`): that command's usage line and ONLY the options in its `ALLOWED_FLAGS` row (plus `--help`/`--version`), rendered from the same `COMMANDS`/`OPTIONS` help data as the full text, so the two cannot describe an option differently. A bare `pharn --help` (no command word, although the dispatch defaults to `init`) and a command with no page (`pharn bogus --help`) print the full `USAGE`, which lists the `rm` alias and an `Environment` block (`PHARN_DEBUG`, `NODE_USE_ENV_PROXY`, `NO_COLOR`/`FORCE_COLOR`). Every refusal (`refuse()`, and the unknown-command path) prints one error line plus `USAGE_POINTER` on stderr, never `USAGE`. `init` prints its banner and intro only AFTER the Node floor, the prerequisite check and its TTY gate, so a refused init prints its one stderr error and nothing on stdout.

**`commands/init.ts` is the archetype install flow** — the only init flow (the legacy module/wizard step pipeline `runInitLegacy`/`runInitV2` and its `steps/*` were removed). `runInit` calls `runInitArchetype` unconditionally:

1. `prereqs` (`runGitPrereq`) — hard-fails if `.git` is absent (`{json}` → plain stderr for `--dry-run --json`).
2. `detectArchetypesFromProject` (`lib/detect-archetype.ts`) — merges `package.json` dependency names + a bounded, symlink-safe file-tree walk into an `Archetype[]` (`ssr`/`backend`/`spa`/`lib`). The walk skips `SKIP_DIRS` (caches, VCS, build output, `__pycache__`, `.yarn`) at zero budget, and `ECOSYSTEM_DIRS` (`target`/`vendor`/`venv`/`.venv`) only where they are that ecosystem's tree — a sibling `Cargo.toml`/`pom.xml`/`build.sbt` or `go.mod`/`composer.json`/`Gemfile` in the parent's already-read entries, or a `pyvenv.cfg` inside — because those are ordinary folder names in a JS project too and the `backend` signal is structural (`app/**/route.ts`), with no `package.json` backstop. **The structural signals are scoped** (`classifyEntry(name, isDir, segments, ctx)` in `lib/archetype.ts`, pure; `ctx` is computed by the walk): a BASE is the scan root or exactly `apps/<x>`/`packages/<x>` (`isBaseDir`); `next.config.*` → `ssr` only directly in a base; `route.*` under `app/`|`src/app/`, and `api/` directly in `app`|`pages`|`src/app`|`src/pages`, → `backend` only when that base has Next evidence (`nextBase`: a `next.config.*` among the base's already-read regular files — decided when the walk LISTS the base, before any child is classified — or, for the root, the `next` dependency); a root `api/`, `migrations/` (root or under a `SQL_HOST_DIRS` ancestor) and DB-located `.sql` → `backend` only with a usable root `package.json` (`jsProject` = `packageJsonFound`, read BEFORE the walk) — the upstream backend lenses match JS/TS only, so a Python/Go/Rust/Ruby/PHP repo resolves `lib` (a non-JS repo WITH a root `package.json` still resolves `backend`; documented). **Package names** (`packageFacts`): `backend` reads `dependencies` ONLY — a server/DB package that is only a devDependency (a mock server, a test database) adds no backend capabilities, and a bundled backend whose framework is dev-only needs `--archetype backend` (F-27; "require tree corroboration" collapses to this, since a tree backend signal counts on its own) — while `ssr`/client UI read `devDependencies` too (the SvelteKit and React Router framework templates list them there); `peerDependencies`/`optionalDependencies` are deliberately never read; `nextDependency` reads both maps. The SSR allowlist covers React Router v7 framework mode, TanStack Start, SolidStart, Qwik City, Analog and Vike; the backend one covers runtime DB drivers/ORMs (`pg`, `mongodb`, `typeorm`, …). The walk's **SETTLED short-circuit** stops once ssr ∧ backend hold over package.json ∪ tree (`RootFacts.packageSignals`) — the rule then yields `[ssr, backend]` whatever else is found (spa is suppressed), and evidence is emitted only for archetypes in the result, so the tree's `clientUi` may stay unset with no observable change. Its bounds are `WALK_LIMITS` (`maxDepth` 24, `maxEntries` 50,000; `scanFileTree`'s third `limits` parameter is for tests), checked AFTER every skip filter at an entry the walk would classify — the budget stops the walk, the depth cap only that directory — and either sets **`truncated`** (F-25), which a settled result clears. `ArchetypeDetection.truncated` → `ArchetypeOrigin.truncated` (required on both variants) → one `detection stopped early: …` line in `archetypeOriginLines` (detected origin only; the numbers come from `WALK_LIMITS`), so the real run, `--yes` and the text dry run print it identically. Detection also returns `evidence` — one `ArchetypeEvidence` per archetype (`evidenceFor`): the allowlist dependency literal (`packageFacts`, allowlist order; `source: 'dependency'`, else `'devDependency'` from `devEvidence`) over the first triggering project-relative path in sorted preorder (dirs end in `/`), `source: 'none'` for `lib`. Paths are the user's own entry names: display-only, through `terminalSafe` (capped, `archetypeOriginLines` in `steps/archetype-summary.ts`), never written or joined.
3. `resolveSource` (`lib/release.ts`) then `fetchRepo(source)` (`lib/repo.ts`) — resolve WHICH commit (the tip of `main` by default, or the newest verified release with `--ref latest`), then download pharn-oss's tarball at it from codeload and extract it with `lib/tar-extract.ts` into a temp dir (cleaned up in a `finally`; every `process.exit`/`cancelAndExit` happens AFTER it). No fetch dependency, no `git` binary, no cache.
4. `parseCapabilityIndex` (`lib/capability-index.ts`) + `resolveCapabilities` (`lib/resolve-capabilities.ts`) — select capabilities whose `applies` is `universal` or intersects the detected archetypes; skip the rest with a reason.
5. `resolveInitSelection` (`lib/init-plan.ts` — the selection plus the carry-over below; `carryOver`, `readPreviousConfig`, `reinstallBaseline` and `readCarriedEntries` live there, shared with the dry run) → `runArchetypeSummary` (selected + skipped; under `--yes` only its lines, `archetypeSummaryLines`, with no prompt) → `install` / `cancel`; on `install`, `confirmWriteTargets` (`steps/overwrite-check.ts`) warns if any of the install's actual write targets already exist in the cwd — listing them (capped), default No, silent when none; it subsumes the old `confirmOverwriteIfExists` (its set includes `pharn.config.json`) and derives the target set from `lib/install-manifest.ts` (the shared install manifest, also used by `status`'s `diff.ts`). `init` computes the install manifest ONCE (`installManifest`, `steps/install-archetype.ts`) after the summary and hands that same map to the early pre-flight, the prompt and `runInstallArchetype` — pre-flight, backup scan, copy and records keys all share it (it depends only on the clone, the selection and the layout; it used to be built five times). The early pre-flight (`preflightInstall` → `prepareInstall`) runs BEFORE `confirmWriteTargets`, so a project the install cannot finish in is refused — exit 1 through init's existing catch, the clone cleaned up first — without first being asked "Continue and overwrite?". It is the early answer only: the tree can change while the prompt is open, so the same checks run again under the lock (`runInstallArchetype`, before the backup) and in `installCapabilities` (before the copy), and those stay authoritative — keep all three. The summary prompt still comes first; a cancelled summary builds no manifest and runs no pre-flight. On a re-install the prompt lists first, and marks, exactly the files `update` would have SKIPPED: `scanDest` (`lib/dest-drift.ts`) compares each dest with its REAL source (`manifestSources` — the mapped `LICENSE` → `PHARN-LICENSE`/`pharn/LICENSE` included) and classifies a differing file through update's own `decideFileAction` (`force: true` → its `backup` bit) against the records baseline (`reinstallBaseline` = `recordsBaseline` against the replaced config's stamp): `(edited)` = `modified`, `(no pharn record)` = `unrecorded`, `(differs from upstream)` = `unverifiable` (no usable store — every difference is backed up); a file still at its recorded hash is a clean upgrade — unmarked, never backed up. The prompt's labels are ADVISORY: `runInstallArchetype` runs, in order, the destination pre-flight (`prepareInstall`) → the same scan under the lock → `createBackup` (named at creation; its set also always holds an existing REGULAR-file `pharn.config.json` — `replacedConfigBackup` in `lib/backup.ts`, shared with the prompt, which marks it `(will be rewritten — backed up first)` — because the rewrite resets `seam`/`models`; a fresh install has none) → the copy, so a refused install writes nothing, `.pharn-backup/` included, and an edit made while the prompt was open is still saved. `init` also reads the config it replaces TOLERANTLY (any failure → nothing carried over; the fingerprint is taken FIRST and re-checked under the lock by `assertConfigFingerprintUnchanged`, which refuses, writing nothing, if another run wrote the file while the prompts were open) and carries it over by `update`'s own merge rules (`carryOver`): a `source: 'manual'` entry the index still has is installed again and recorded `manual` via `manualKeys`, even when the archetypes also select it; an entry of ANY source that upstream ships but this CLI cannot parse (`index.unknown`) is KEPT verbatim — config entry, files and records (`keptRecords`) untouched — and listed in `frozenCapabilities`; a manual entry upstream no longer ships is dropped and NAMED. `carryOver` also returns `dropped` (`CapabilityDrop[]`: the gone manual entries, `auto` entries the archetypes no longer select, and source-less ones they no longer select — never a frozen or re-installed entry; the formerly silent auto/legacy drops are now named before the summary) plus `previousLayout`; `planInitRemovals` turns them into removals at that layout against `reinstallBaseline` via the shared `lib/capability-removal.ts` (`planCapabilityRemovals`, `CapabilityRemovalError` — a named refusal in the real run and the dry run). They ride `planWriteTargets` (`removals`, `removalLines`): the overwrite prompt lists them under "will be DELETED" and asks even with zero conflicts (default No); `init --yes` REFUSES any present removal (`OverwriteRefusedError`, before the lock and under it — it never deletes); `--dry-run` prints `WOULD DELETE` and `--json` adds `capabilities.removals` (absent when empty) with their files in `backups`. `runInstallArchetype` re-plans them under the lock (authoritative), makes ONE `createBackup` over drift ∪ replaced config ∪ removal backups (`before overwriting and removing.`), deletes, then copies; the records and config already omit them. Top-level config keys pharn does not own (`userOwnedConfigEntries` — every unowned key, e.g. upstream's `testResults` / `ship` / `gates` / `budget`) are copied across from any file that parses as a JSON object. Then `runInstallArchetype` (`steps/install-archetype.ts` → `lib/install-capabilities.ts`) copies the capabilities + fixed product surfaces (including the layout-resolved product-loop boundary contract (`resolveFeaturesReadme`)) into the mirrored layout (flat OR `pharn/`) and writes the archetype `pharn.config.json` (`archetypes`, `capabilities`, `layout`, `skillsVersion` read from the fetched `SKILLS_VERSION` file via `readSkillsVersion`, `modules: []`, plus pharn-oss's `models` block — copied VERBATIM from the clone's root `pharn.config.json` by `readUpstreamModels` (none when upstream ships none, and none, with the reasons warned, when the pinned copy of pharn-oss's rules rejects it) and recorded under `MODELS_RECORD_KEY` — and the `seam` default; canonical `CONSTITUTION.md` copied verbatim). **`--archetype <list>` replaces detection** (`runInit({ archetypes })`; it composes with `--dry-run`, `--dry-run --json` and `--yes`): the override is what is resolved, summarised, installed and recorded as `config.archetypes` (so `update`, which never re-detects, keeps it). Detection still runs and the summary shows it as `detection found … (not used)`; no other key is recorded. A re-run `init` re-detects; when its archetypes differ (as a set) from the replaced config's `archetypes` — read through the tolerant `readPreviousConfig`, reduced by `recordedArchetypes` to canonical members or nothing — the summary prints `previously recorded: … — pass --archetype … to keep them`. The real run, `--yes` and the text dry run all print the same block (`archetypeOriginLines`, inside `archetypeSummaryLines`); `init --dry-run --json` carries it as the additive `archetypeSource` (`detected`|`flag`), `detectedArchetypes` (the unused detection under `flag`, else `null`) and `archetypeEvidence` (`{archetype, source, value}` per detected archetype; `source` may be `devDependency`), plus `detectionTruncated: true` right after it ONLY when detection stopped early (absent otherwise, the `absentUpstream` convention; present under `flag` too) — projected from `InitPlanReport.archetypeOrigin` (`ArchetypeOrigin`, `lib/archetype.ts`), `schemaVersion` still 1.

**`init --dry-run [--json]`** (`runInitDryRun` in `commands/init.ts`) runs steps 1–4 and the selection/carry-over, then `buildInitPlan` (`lib/init-plan.ts`, read-only, never logs): the manifest, `prepareInstall` (the destination pre-flight — a refusal exits 1 as in a real run), `planWriteTargets` (`lib/write-targets.ts` — the ONE target/label/order computation `confirmWriteTargets` and `--yes` also use, so the preview's `(edited)`/`(no pharn record)`/`(differs from upstream)` marks — and F-08's `(will be rewritten — backed up first)` on an existing `pharn.config.json`, via the same `replacedConfigBackup` — are the prompt's by construction; the JSON labels that config `rewritten` and lists it in `backups`), the backup set, whether `.claude/settings.json` would be preserved (+ `diffHookWiring`), the `models` outcome and the carried user key NAMES. The real run keeps its own step-by-step order (a cancelled summary builds no manifest); the two share only the selection/carry phase and `planWriteTargets`.

**`lib/install-capabilities.ts`** is the shared capability copy core — `installCapabilityDirs` (`add`) and `installCapabilities` (`init`); `update` applies the manifest per file instead. `installCapabilityDirs(repoDir, projectRoot, capabilities, paths?)` pre-flights **every** selected capability source (validated name via `CAPABILITY_NAME_RE` + `safeJoin` + existence + symlink rejection) before any write — no partial installs — then copies each griller/lens dir into the mirrored layout. `installCapabilities` additionally copies the fixed product surfaces: product `pharn-*` commands (excluding `pharn-dev-*`), `.cjs`/`.mjs` hooks (excluding `*.test.cjs`/`*.test.mjs`; a floor-RELATIVE segment match against `FLOOR_TEST_FIXTURES_DIRS`, single-sourced as `isFloorTestFixturePath` in `install-manifest.ts`, which both the copy filter and the manifest call, and anchored at the floor root on both sides — only the root's direct child matches, so a nested `lib/fixtures/` is kept, and an unanchored absolute-path match would prune the whole floor copy under an ancestor of that name). Add a name to that list only after checking upstream that no non-test floor file, hook or command reads it. **Every fixed surface is existence-guarded, but none is silent** (F-10): `lib/install-manifest.ts` → `absentInstallSurfaces({repoDir, layout})` derives, from the SAME internal enumeration as the manifest (`collectInstallManifest`), each DECLARED surface (`commands`, `hooks`, each `trusted-doc`, `license`, `features-readme`, `contracts`, `core` — `pharn` layout only, the flat path is a documented no-op — and `floor`) that contributes ZERO files (missing, symlinked, wrong type, or nothing passing its filter), as `{surface, path}`; `init` warns once after the copy (`lib/absent-surfaces.ts` wording, replacing the old docs-only warning; never fatal — upstream's `MIN_CLI` is the lever; its outro names only the `.claude/` surfaces that landed), `init --dry-run` prints the same warning and `--dry-run --json` carries `absentUpstream` (present only when non-empty), `update` prints a `NOT SHIPPED` note (real run and `--dry-run`; additive `plan.absentUpstream` in `--json`, present only when non-empty so the 0.10.0 bytes hold; never withholds the bump), and `status` lists it in DRIFT and fails `--strict`. Always computed at the CLONE's own layout, so it means exactly "upstream ships nothing there". The list is closed and per-surface: a surface upstream adds, or one missing script inside a hooks dir that still ships others, is not reported. Copying from the untrusted clone is symlink-guarded (`isSymlink` reject / `noSymlinks` filter) and `safeJoin`-contained; file contents are copied verbatim, never executed. The DESTINATION is guarded too, by `prepareInstall` — exported so `init` runs it before its overwrite prompt (`preflightInstall`) and again BEFORE its backup, and run again by `installCapabilities` itself, over the manifest passed in (or computed when absent): it walks every path the install manifest (`collectExpectedInstallPaths`) says it writes, plus `.claude/settings.json`, with `findSymlinkComponent` and refuses the whole install, naming linked DIRECTORIES apart from linked FILES (`cpSync` follows a symlinked `.claude/commands` or `pharn/` out of the project, and `safeJoin` is lexical; at a symlinked LEAF it replaces the link — measured on Node 20.13/22/24, nothing lands outside, the user's link is lost). A LIVE `.claude/settings.json` link is allowed — `existsSync` follows it, so the file is preserved and never written — while a DANGLING one is refused. Its type walk (`findTypeCollision`) also refuses a DIRECTORY at `pharn.config.json` / `pharn.records.json`, the two files `init` writes beside the copy (their atomic `rename` fails EISDIR only on a directory). The install set is resolved by `lib/capability-index.ts` (`parseCapabilityIndex` — the untrusted-frontmatter → typed `CapabilityIndex` fetch boundary, reading only `role`/`applies` — the name is the directory's — inside a `---` fence, both by upstream's own rules, ported literally from pharn-oss's validator (`pharn/floor/validate.mjs`, vendored byte-for-byte and sha256-pinned at `tests/fixtures/pharn-oss/validate.mjs`): the fence is `parseFrontmatter`'s (the file starts with `---`, the block runs to the first newline followed by `---`, trimmed), each field is its line rule (`^([A-Za-z0-9_]+):\s*(.*)$` per `\n`-split line, a `[…]` value split on `,`, one leading and one trailing quote stripped independently, a duplicate key keeps its LAST value — F-26: it used to be refused, and last-wins is safe because that last value is the one upstream validated and is still enum-checked), and `applies` is CHECK 4b's (a non-empty scalar is a one-element list, so `applies: universal` is accepted; any `universal` in the list → `'universal'`, so `[universal, ssr]` is too). The only deliberate difference is that one trailing CR per line is dropped (more lenient on CRLF, never less); the subtree role cross-check is the CLI's own. `tests/capability-index.test.ts` differential-tests the fence and the value shapes (scalar, mixed, duplicate, quoting) against the vendored file's own functions) + `lib/resolve-capabilities.ts` (select where `applies` is `universal` or intersects the detected archetypes). The commit SHA is threaded from `fetchRepo` (`repo.sha`) — no separate GitHub fetch (closes the resolve/fetch TOCTOU).

**`lib/release.ts` decides WHICH pharn-oss commit an install takes** (0.9.0). The DEFAULT channel is `main` — the tip, whatever merged last, as every CLI before 0.9.0 installed it (`resolveSource('main')` makes no request; `fetchRepo` resolves the tip). It stays the default because pharn-oss publishes no releases: a release-only default would refuse every install (maintainer decision, 2026-10-07). The opt-in channel (`--ref latest`) is the newest pharn-oss **GitHub release** — pharn-oss is to create tag `v<SKILLS_VERSION>` only after every required post-merge check on that commit passed — resolved with two bounded GETs (`releases/latest`, then `commits/<tag>` with `Accept: application/vnd.github.sha`): `tag_name` must match `RELEASE_TAG_RE` (`v` + plain `X.Y.Z`, no prerelease) and the commit `COMMIT_RE`; a draft/prerelease is refused; `redirect: 'error'`, an 8 s `withDeadline` per request, and a byte cap on each body. **It FAILS CLOSED**: no release published (404), rate-limited (403/429 — the unauthenticated API allows 60/h per address), unreachable, or malformed → `ReleaseResolveError`, whose message names `--ref main`; it NEVER floats to the tip. `fetchRepo(source)` takes the resolved `InstallSource` as a REQUIRED argument (a forgotten one must not mean "the tip"), downloads at the release's commit without consulting the tip, and refuses (removing the tree) a release whose `SKILLS_VERSION` is not its tag. Only the `main` channel keeps `fetchCommitSha` + its LIMITS §3b float. **`--ref` and `--archetype` are the CLI's two VALUE-taking flags** (`STRING_FLAGS` in `index.ts`; declared as minimist strings in both parses, so `--ref main` / `--archetype backend` bind their values). `--archetype` is `init`'s only, validated by `archetypeOption` → `parseArchetypeList` (`lib/archetype.ts`): an exact comma-separated list of `ARCHETYPE_VALUES` members, each at most once, `lib` only alone, canonical order out; a bare/`--no-archetype`/repeated flag or any other value refuses (`Invalid value for --archetype`, exit 1) beside the `--ref` value check, before the `--help`/`--version` short-circuits. For `--ref`: `init` and `update` take it; its value must be exactly `latest` or `main` (`refOption` — a bare `--ref`, `--no-ref`, a repeated flag or any other value refuses, exit 1, before the `--help`/`--version` short-circuits). The channel is RECORDED as the additive config key `ref` — only the literal `"latest"` is ever written or kept at load (anything else is dropped → the `main` default) — by `init` (`InstallCarry.ref`, never carried from the replaced config) and by `update` (`--ref` overrides `channelOf(config)`; a switch re-opens the same-version early return so it is recorded; `--ref main` deletes the key). `add` and `status` take no `--ref` and follow `channelOf(config)`. **Ahead of the source — on BOTH channels**: an install can be NEWER than what its channel now offers — on `--ref latest`, an install made from `main` and switched before the release at its version was cut; on `main`, after pharn-oss main MOVED BACK (a revert of its `SKILLS_VERSION`; F-15 — before, `update` silently applied `v2.0.0 → v1.0.0` over every clean file). `versionStatus` (`lib/version-status.ts`) is the ONE comparison (`compareVersionCore(installed, latest) === 1`, channel-independent, so it takes no source; an unorderable version is never ahead) used by `update`'s guard, `status` (text + `--json`) and `add`'s version gate — never a second comparator. `update` then exits 0 changing nothing unless `--force` (a downgrade presented as an update is refused; `--yes` does not skip it): the guard counts a `pendingSkillsVersion` too (every unedited file is already at it), and it runs BEFORE the same-version early return and everything that re-opens it (`frozenCapabilities`, `needsModelsConversion`, a `--ref` switch — so a refused switch is NOT recorded), so none can carry the downgrade in; `--dry-run` reports the same, and `--dry-run --json` reports `status` `ahead-of-release` (release channel) or the additive `ahead-of-main` (`main`), both `plan: null`, `schemaVersion` still 1. `status` reports it as ahead, NOT outdated (so `--strict` passes), and `add`'s version gate names the real ways out (`pharn update --ref main` / wait for the release; on `main`, wait or `pharn update --force`) instead of looping the user back to `update`. On the release channel `update` and `status --no-drift` take the version from the tag (`fetchRemoteSkillsVersion` is the `main` channel's only). Until pharn-oss publishes releases, `--ref latest` refuses every install (404); the default is unaffected.

**`lib/validate.ts` is security-sensitive.** Untrusted names, versions, paths, and capability frontmatter are validated against strict regex/enum allowlists (`CAPABILITY_NAME_RE`, `VERSION_RE`, `COPY_FILENAME_RE`, `COMMIT_RE`, `RELEASE_TAG_RE`, the `role`/`applies` enums), checked for `..`, and rejected on control chars. **`safeJoin` lives here** (relocated from the deleted `install-modules.ts`) — the lexical path-containment gate that `install-capabilities.ts`, `diff.ts`, `capability-index.ts`, `layout.ts`, `skills-version.ts`, and `remove.ts` all guard their fs access with, so nothing escapes its base dir (its strict-child sibling `safeChildJoin` — exactly one segment below the base, never the base — guards `remove`'s recursive delete) (`install-capabilities.ts` adds a symlink-aware backstop at the write sites). `toPosix` (the other purely lexical primitive — separator normalization + trailing-slash strip, relocated here once `install-manifest.ts` and `symlink-guard.ts` both needed it) sits beside it. The **physical** counterpart lives in **`lib/symlink-guard.ts`** — `findSymlinkComponent(base, rel)`, the single component walk that `backup.ts` (read side), `apply-update.ts` (write side), and `install-manifest.ts` (twice, skip side) all reach for; it returns the first symlinked component below `base` or `null`, and each **caller owns its failure shape** (backup and apply throw their own `ManifestValidationError` messages, the manifest skips), which is why the core returns a value instead of throwing. Nonexistent components deliberately pass — `applyWrites` creates parents _after_ the walk. That lexical/physical split is the point: `safeJoin` contains the path _string_, `findSymlinkComponent` refuses the path _on disk_. Remote fetches (`skills-version.ts`, `release.ts`) use `redirect: 'error'`, an 8s timeout, and a 256KB body cap. Preserve these invariants.

**`lib/hash.ts` is the one content-identity primitive.** `contentHash(path)` is THE comparison hash: every drift / records comparison — `readDiskState` (`apply-update.ts`, the project side of `update` and `status`), `diff.ts`'s and `update-plan.ts`'s clone side, `dest-drift.ts` (`add`/`init`), `buildRecords` (the hashes written to `pharn.records.json`), `removal-backup.ts` (`remove`) and `uninstall-plan.ts` (`uninstall`; orphan detection reaches it through `readDiskState`) — goes through it, so the two sides of a comparison can never mix schemes. For TEXT content it folds each `\r\n` to `\n` before hashing (pharn-oss's own fold, `check-spec.mjs` `bodyHash`; a lone `\r` is byte-exact), so a project re-checked-out with `core.autocrlf=true` does not read every file as `modified` (F-16). Content is BINARY iff a NUL byte occurs in its first `BINARY_SNIFF_BYTES` (8000, git's sniff size) — hashed raw. Text with no CR hashes exactly as raw sha256, which is why stores written before the fold stay valid (pharn-oss ships no CRLF; no `pharn.records.json` scheme marker exists). The stated cost: a change that ONLY swaps line endings is invisible to pharn (`status` ok, `update` may upgrade it, `add` may overwrite it, `remove`/`uninstall` delete it — none backed up). `sha256File` is the RAW byte hash, kept for true byte pins (the vendored checker in `tests/model-config-parity.test.ts`); `tests/hash.test.ts` fails if any other `src/` file calls it. `configFingerprint` (`pharn-config.ts`) deliberately stays a raw hash — it detects a concurrent write, where any byte matters. The fold is tested with CRLF fixtures and a real `git -c core.autocrlf=true` checkout on ubuntu; it has never run on Windows (CI is ubuntu-only).

**`lib/pharn-config.ts`** reads/writes `pharn.config.json` (`pharnVersion`, `skillsVersion`, `repo`, `commit`, `installedAt`, and — for an archetype install — `archetypes[]`, `capabilities[]` (`{name, role}`), `layout`, plus the `seam` block and pharn-oss's `models` block). Every `capabilities[]` entry is validated at ingest: it must be an object whose `name` matches `CAPABILITY_NAME_RE` (no control chars) and whose `role` is in `ROLE_VALUES`, else `CapabilityEntryError` — the config is committed and hand-editable, and `name` is path-joined by `remove`'s recursive delete (a `{"name":"../.."}` entry used to delete the project root). A present-but-invalid `capabilities[].source` (anything outside `{auto, manual}`; ABSENT is legal, P7) is rejected by `CapabilitySourceError`. For an archetype config, a present `archetypes` must be an array whose every entry is in `ARCHETYPE_VALUES` (`lib/validate.ts` — the one runtime archetype list: `Archetype` in `types.ts`, `APPLIES_TOKEN_VALUES` and detection's order all derive from it), else `ArchetypesError`, its offender `escapeUnsafe`-escaped and capped (`"ssr"` used to crash `list`/`status`/`update` with a raw `TypeError`, `["bogus"]` silently narrowed selection); absent, `[]` and duplicates stay legal, and a pre-archetype config's `archetypes` is not checked (P7). Likewise, for an archetype config only, the install stamp is checked (F-18): `skillsVersion` must match `VERSION_RE` and a present `commit` must be `null` or match `COMMIT_RE`, else `ConfigStampError` (offender escaped and capped the same way; an absent `commit` stays legal, and a pre-archetype config is not checked, so its `commit: "abc123"`-style values still load). A PRESENT `capabilities` that is not an array is a `CapabilityEntryError` (F-30) — it used to fall through `isArchetypeConfig` and prescribe the config-overwriting `pharn init`; only an ABSENT `capabilities` is the pre-archetype marker. All four join `isConfigValidationError`'s union. The config's own `skillsVersion` is still passed through `terminalSafe` where `list`/`status`/`update` print it (defense in depth). A present-but-invalid `seam` block is caught by its own validator — `lib/seam-config.ts` (`validateSeamConfig`/`SeamConfigError`) — and `readPharnConfig` lets that named error PROPAGATE (never collapsing a bad hand-edit into the "run init" path); `isConfigValidationError` + `loadConfigOrExit` catch and report it, and the validated/stripped block replaces the raw one. The `models` block is NOT validated at load (it is pharn-oss's — see below): it rides the spread VERBATIM, so the pre-0.7.0 format `update` must migrate, pharn-oss's format and a newer one all load, and no command refuses to run over it. It stays in `CLI_OWNED_KEYS` because pharn still WRITES the key (a re-run `init` replaces it rather than carrying a stale one). Schema is additive — a legacy config's now-unused `modules[]`/`constitution`/`stackAnswers`/`installedSkills[]` still load (P7). `isArchetypeConfig` (= `Array.isArray(config.capabilities)`) is the deterministic discriminator; **`loadArchetypeConfigOrExit`** is the shared load-or-reject surface for `add`/`update`/`status`/`remove` (a pre-archetype config → `LEGACY_CONFIG_MESSAGE` + exit(1), never a fetch; `list` keeps its own json-aware check so `--json` stderr stays clean). `add`/`update`/`remove` update the config in place, and each calls `assertConfigUnchanged` as the FIRST step inside its `.pharn.lock` (`lib/project-lock.ts`): the config is loaded before the lock (and across `update`'s / the `remove` picker's confirm), so a concurrent run could otherwise be overwritten from a stale snapshot; a mismatch throws `ProjectChangedError` (a `ProjectLockedError`, so every catch site reports it as a named refusal, exit 1, nothing written). The lock itself treats an unparseable lock file younger than `MALFORMED_GRACE_MS` (10 s) as LIVE — `tryCreate` writes its payload after the `O_EXCL` create, so a live lock is briefly empty — and only breaks older ones. All three files pharn keeps in a project — `pharn.config.json` (`readPharnConfig`, `configFingerprint`, and init's two tolerant reads), `pharn.records.json` (`readRecords`) and `.pharn.lock` (`readRawAt`) — are read through **`lib/bounded-read.ts`** (`readBoundedFile`): one descriptor opened `O_NONBLOCK`, `fstat`-checked as a regular file of at most `MAX_LOCAL_FILE_BYTES` (16 MiB), read from that same descriptor, never throwing. A FIFO, a device or a directory there is therefore each caller's existing "unreadable" outcome (config → `null` / `unreadable:<code>`, records → a named `invalid`, lock → presumed live, then broken), never a hang in `open(2)` and never an unbounded read — the posture `hook-wiring.ts` and `detect-archetype.ts` already held for the files they read.

**`pharn add` addressing** (`commands/add.ts` + `lib/capability-address.ts`). `add <name>` or `add <role>:<name>` (e.g. `add a11y`, `add lens:n-plus-one`) installs one capability into an archetype project — a manual override of archetype auto-selection. It clones pharn-oss at the channel the config records (`channelOf`; SHA-pinned), then applies **the version gate**: a local `versionGate` helper, called ONCE per command from INSIDE each path's existing `try` (so `readSkillsVersion`'s throw still reaches the `finally` that cleans up the clone), refuses when `readSkillsVersion(repo.dir) !== config.skillsVersion` — reusing the existing `{kind:'error'}` outcome → `exit(1)`. It fires on `!==` (never `<`, so a rollback reads the same) — except that a clone at the config's additive `pendingSkillsVersion` also passes: `update` records that field only when it withheld the bump SOLELY because of `modified`/`unrecorded` skips (the user's kept edits; every other file is at that version) and clears it on the next complete run; at a pending version `add` keeps the config's own `(skillsVersion, commit)` pair (`addStamp`) so the records stamp stays consistent, fires **gate-first** (before the already-installed no-op and before the picker's `all-installed`, and before `groupMultiselect` renders), and writes nothing. A sibling **layout gate** (`layoutGate`) sits immediately after it at both call sites, `??`-chained (`versionGate(…) ?? layoutGate(…)`) so the **version** refusal wins when both mismatch — by short-circuit evaluation, not statement order: it refuses when `detectLayout(repo.dir) !== configLayout(config)`, naming both resolved layouts and `pharn update --force`. `add` copies at the CLONE's layout (`installCapabilityDirs`' default) and records at it (`mergeCapabilityRecords`), while `remove`/`status`/`diff.ts` address the project at `configLayout` — so without the gate a mismatched add lands files nothing ever looks at, and the next `remove` drops the config entry reporting "its files were already gone", orphaning the dir. `add` must NEVER record the clone's layout the way `update` does: `update` may only because it rewrites the WHOLE tree at that layout, whereas `add` writes one capability, so stamping `layout` here would re-address every other already-placed file. Comparing `configLayout(config)` (not the raw `config.layout`) is the point — agreement with the readers is the invariant, and it makes a garbage hand-edited value resolve to `flat` and fail closed. This is what keeps `update`'s `config.skillsVersion === latest` early-return honest: `add` must never stamp a newer `skillsVersion` over unchanged old bytes. `add` therefore refreshes `commit` but NEVER `skillsVersion` (the legal same-version-different-commit case). Past the gate it resolves the arg against `parseCapabilityIndex`, and if it uniquely names a not-yet-installed capability, copies it via `installCapabilityDirs` and **appends** to `capabilities` with `source: 'manual'` (never touches `archetypes`). That tag is what makes the override survive `update`, and it is written at BOTH entry-construction sites — `resolveArchetypeAdd` and the picker's threaded `cfg` mirror, which the next pick spreads into its own config write. Already-installed → no-op; unknown/ambiguous → lists the valid `role:name` addresses. **Before the copy, `add` backs up destination drift**: `capabilityCloneFiles` (`lib/install-manifest.ts`) enumerates the capability dir in the CLONE, `scanDest` (`lib/dest-drift.ts`) keeps the rels whose dest exists as a regular file and whose `contentHash` DIFFERS from the clone's, and a non-empty set goes to `createBackup` (`lib/backup.ts` — the same `.pharn-backup/<ts>/` `update --force` writes) BEFORE the first `cpSync`, logged at creation so the pointer survives a later throw. `add` was the only write path with none of the product's three edit-protections (init's prompt, update's per-file skip, `--force`'s backup), and a capability directory can outlive its config entry (left by an older `update` or `init`, or made by hand): the user edits it, and the later `add` is not a config no-op. Identical content is NOT drift (mirrors update's `identical → no-op`), so a drop-then-re-add of unedited files stays silent. The scan SKIPS an absent/symlinked/non-dir source rather than throwing, so `installCapabilityDirs`' curated `Capability "x" (griller) is missing at …` still wins — the same read-skips/write-throws split `install-manifest.ts`'s `addDir` already uses. `scanDest` returns a PARTITION, not just the drift set: a rel whose PROJECT-side path crosses a symlinked component is `unsafe`, and `add` **refuses the whole install** naming the component. That is measured, not defensive — on node v24.13.1 `cpSync` guards only the source, so a symlinked INTERMEDIATE dir under the capability dir is written straight THROUGH (bytes outside the project replaced), while a symlinked leaf is REPLACED and a symlinked capability root throws `ERR_FS_CP_DIR_TO_NON_DIR`. Skipping would be strictly worse than doing nothing (the copy writes through anyway while the backup omits the file), and backing up is impossible (`createBackup` refuses symlinked components; `copyFileSync` would save the link's TARGET). An ENOTDIR walk (a component below a regular file) is NOT unsafe — `cpSync` throws on that tree by itself — so it stays a skip, which is also what keeps a non-directory component out of the set `createBackup` consumes unwrapped. `add` also merges the capability's files into `pharn.records.json` (only extending an already-readable store; it never mints one), keyed by that SAME clone-derived list — never a walk of the destination, which used to sweep a user's own file inside a leftover capability dir into the store as pharn-written and let a later `update` read it as cleanly upgradeable instead of `modified`; the hashes are still taken at the DEST (`buildRecords`), so a record can never disagree with what landed. `CONSTITUTION.md` is **not** touched — `add` installs capability dirs only. `pharn update` re-resolves the **recorded archetypes** against the latest index and re-copies — drift-safely, see below.

**`pharn remove` addressing** (`commands/remove.ts`) is the inverse of `add`. `remove <name>` / `remove <role>:<name>` (no arg → an interactive picker over the installed capabilities) deletes that one isolated capability dir — addressed at the project's recorded `layout` (flat `pharn-review` / `pharn-pipeline/grillers/<name>`, OR the same under `pharn/`, via `configLayout` + `layoutPaths`) — and drops its `capabilities` entry. **No clone, no network** — everything is derivable from `config.capabilities` + the filesystem, so `remove.ts` imports no repo module at all; `archetypes` is never touched; `CONSTITUTION.md`/`memory-bank/` are **never** touched (they are not capability dirs). Removing an entry whose stored `source` is **literally** `'auto'` warns that `update` will reinstall it the next time it re-applies the install — at the latest the run that moves to a new pharn-oss version, or now with `--force` — and NOT necessarily on the next run: at the same version `update` may early-return, since nothing local re-opens it (the entry and its records are both gone); an **absent** `source` warns NOTHING (absence means provenance-unknown, and a false warning on a legacy manual add is worse than silence) — derived from the stored field only, so `remove` stays zero-network. Not-installed → exit 1, nothing written, listing the removable capabilities (the answer `pharn add bogus` gives; it used to be a warning and exit 0); a name installed in both roles → hard-fail (ambiguous). `remove` has no `--yes`, and the reason is per-path: the NAMED remove deletes without asking (no prompt to skip), while the bare picker's ONE confirm — listing the picks, default No — IS the destructive gate, so nothing may skip that either. **`remove`'s `ALLOWED_FLAGS` row is empty, so `pharn remove --yes` now exits 1** naming the flag. This SUPERSEDES the previous contract, which read: _"`--yes` stays a declared minimist boolean only because it is `update`'s flag; that is what keeps `pharn remove --yes` a harmless parse rather than an unknown-option refusal, and turning it into a refusal belongs to a per-command allowlist, not to the dispatch."_ That allowlist now exists (see the dispatch paragraph above), so the deferral is spent — but its reasoning still holds and is why the row is empty rather than `['yes']`: there is no confirm on the named path to skip, and the picker's one confirm may not be skipped. `--yes` is still declared globally, because the declaration list is DERIVED from the table and `update`'s row grants it. Before any delete (the picker: for the whole selection, before its confirm) `remove` refuses with exit 1 when a target dir's path crosses a symlinked component (`findSymlinkComponent`), since `rmSync` resolves ancestors. Every delete is a **strict child** of its role subtree — `safeChildJoin(safeJoin(cwd, subtree), name)` (`lib/validate.ts`), which, unlike `safeJoin`, never returns the base itself nor a deeper path — a second floor under the ingest-time name validation. `remove` also **prunes that capability's entries from `pharn.records.json`** (`pruneCapabilityRecords`), so it is no longer the one write path leaving records that describe bytes that are gone — the converse of the invariant `update` is pinned to. The prune is a **key-prefix filter over the store**, never an fs enumeration: a walk of the DEST dir finds nothing after the delete AND nothing before it on the "already gone" path — which is exactly where the stale keys are the only thing left to clean, so the store is the only place the answer still exists. It mirrors `add`'s `mergeCapabilityRecords` guard verbatim (`recordsBaseline(...) === null → return`): absent/corrupt/stale-stamped → the file is left byte-identical, **never** minted and never blessed (the baseline `note` is deliberately not surfaced — `update` is where an unusable store changes an outcome, and it is the command that names the reason). The trailing slash in `relDir + '/'` is load-bearing (`lenses/a11y` must not eat `lenses/a11y-extended`); nothing matched → the write is skipped entirely; and the `skillsVersion`/`commit` stamp is re-written from the CONFIG pair unchanged, since `remove` advances neither. **Before the first delete `remove` backs up what it cannot prove is pharn's** (`backupBeforeDelete` → `lib/removal-backup.ts` `removalBackupSet` → `createBackup`): inside the lock, after `assertConfigUnchanged`, it reads the records baseline ONCE (`readRecordsBaseline`, shared with the prune), walks each target dir (addressed through the same `capabilityDir` = `safeChildJoin` the delete uses, so the scan never reads more than the delete removes), and keeps only REGULAR files — a symlink is neither followed nor saved (`rmSync` deletes the link, not its target), a FIFO/socket/device is skipped (opening a FIFO blocks). A file is left out of the backup only when its key is in a USABLE store AND its `contentHash` equals the record; everything else — unrecorded, edited, or every file when the store is absent/corrupt/stale-stamped — goes to `.pharn-backup/<ts>/`, announced at creation (`Backed up N file(s) to <dir> before removing.`, `add`'s shape). Nothing to save → no backup dir. Any scan or backup failure (EACCES listing/hashing, a symlinked `.pharn-backup`, a copy error) throws `RemoveBackupError`, which `runRemove` reports like `ProjectLockedError` (exit 1) — nothing deleted, config and records untouched, a partly filled backup dir possibly left. The picker makes ONE backup for the whole selection, after its confirm. Order is backup → delete → prune → config (mirroring `add`'s records-before-config) — a benignity argument, not atomicity: each write is individually atomic (`lib/atomic-write.ts` — temp-then-`rename`, the temp created exclusively (`wx` = `O_CREAT|O_EXCL`) under `<target>.<pid>.<random hex>.tmp`, so a symlink a hostile checkout plants at a temp name is refused, never followed), but the PAIR is not a transaction, so a failed prune leaves the old status quo and a failed config write leaves an entry the next `update` restores. The role→subtree mapping is single-sourced in `capabilitySubtree` (`lib/layout.ts`), which every reader and writer uses; `remove`'s `capabilityRelDir` builds on it and is shared with `deleteCapabilityDir`, so the delete and the prune address the same directory by construction; both, with `capabilityDir` and `linkedComponent`, live in `lib/capability-dir.ts`, shared with `update`'s and `init`'s deletion of dropped capabilities. Both call sites prune — the named path with `[target]`, the picker ONCE with the full selection (one store write matching the one config write).

**`pharn uninstall` (`commands/uninstall.ts`) deletes only what the record store proves.** Offline like `remove` (no clone, no network, no repo module). A missing `pharn.config.json` → "PHARN is not installed here … Nothing was removed." exit 0 (a second run is harmless); otherwise `loadArchetypeConfigOrExit`. With no usable store (`recordsBaseline(...).records === null` — absent, corrupt, stale-stamped) it refuses, exit 1, nothing written, pointing at `docs/troubleshooting.md` "Removing PHARN by hand" (`pharn update` is not a remedy: its same-version early return never rebuilds an absent store). `lib/uninstall-plan.ts` → `planUninstall(root, records)` is the read-only classifier, one bucket per record key (the `models` key skipped): `outside` (fails `isInstallRootPath`), `unsafe` (a symlinked component in the PARENT chain → the whole run is refused), `absent` (incl. ENOTDIR), `unverifiable` (not a regular file — dir, FIFO, symlinked leaf — or unreadable/unstatable: kept), `edited` (`contentHash` ≠ record: kept), `delete` (`contentHash` = record). A file with NO record is never a candidate. The bound is orphan detection's own install-root predicate, `isInstallRootPath` (`lib/orphans.ts`, layout-agnostic — both layouts' surfaces — and pinned against a REAL `installCapabilities` run in both layouts by `tests/install-manifest.test.ts`), so an orphan whose record `update`/`init` carry (upstream stopped shipping it, or it sits at the layout the install moved away from) is deleted when unchanged and kept + listed when edited. It is why `uninstall` is the one consumer that DELETES by a record key: only after the predicate, through `safeJoin`, after the symlink walk — so a hand-edited `src/app.ts` key with a matching hash is `outside`, never deleted (named in the PLAN note). Flow: PLAN note (counts, kept files listed and capped at 10 through `escapeUnsafe`, the `outside` keys named, and always the line that `.claude/settings.json`, `.claude/settings.local.json` and every `.pharn-backup/` are left untouched) → confirm (default No; `--yes` skips; off a TTY without it → exit 1) BEFORE the lock → `withProjectLock(cwd, 'uninstall')`: `assertConfigUnchanged` → re-read the store and RE-PLAN (the pre-prompt plan is advisory) → `createBackup(cwd, ['pharn.config.json'])`, announced at creation → `unlinkSync` the `delete` bucket → `removeEmptyDirs` (deepest first, `rmdirSync` only — the kernel refuses a non-empty dir — climbing toward but never to the project root; a dir that cannot be removed blocks its ancestors and only the deepest are reported) → unlink `pharn.records.json` → unlink `pharn.config.json` LAST (the "installed" marker, so a failure part-way leaves a state a re-run finishes; each attempt backs the config up again). A failed unlink → `UninstallError` (exit 1) naming how many files were already deleted. It never writes `.claude/settings.json`: `hooksReferencing` (`lib/hook-wiring.ts`, reading both project settings files exactly as `diffHookWiring` does) lists, in a `HOOKS` note, entries whose command/args contain a recorded `.claude/hooks/*` path that passes `isInstallRootPath` and is gone after the run, rendered through `displayHook` — the one place PROJECT hook entries reach a terminal. `--force`/`--dry-run`/`--json` do not exist for it (P7).

**`pharn update` (`commands/update.ts`) is drift-safe by default.** **Planning is separate from writing, and `--dry-run` rides the planning half.** `lib/update-plan.ts` → `buildUpdatePlan` is the read-only planner both paths call (index parse → `mergeCapabilities` → install manifest → `planUpdate` → `decideModelsUpdate`, plus the withheld version / `pendingSkillsVersion` / `frozenCapabilities` / features-relocation / `abandonedLayout` derivations, the `removals` of dropped capabilities, and `diffHookWiring`); it never logs (the unknown-capabilities warning goes out through an `onUnknownWarning` callback so it still prints before any later throw) and returns `{report, apply}` — `report` is JSON-safe (plain data; `--json` projects it through `buildUpdateReport`), `apply` holds what only the writer needs (the manifest `Map`, records, `Set`s). `applyPlannedUpdate` (`commands/update.ts`) is the write half (backup → writes → records → config). `update --dry-run --json` is the same dry run as ONE JSON object (`schemaVersion: 1`, `lib/update-report.ts` → `buildUpdateReport`, a pure, explicit field-by-field projection of `UpdatePlanReport` — never a spread — through `serializeJsonReport` in `lib/json-report.ts`, the one serializer `serializeStatusReport` also delegates to): `status` is `planned` / `up-to-date` / `ahead-of-release` / `ahead-of-main` (the early returns carry `plan: null`), the `models` block and its record hash are deliberately omitted, `unknownCapabilities` is the structured twin of the warning prose (`UpdatePlanReport.unknownCapabilities`), and free text is capped and escaped like `status --json`. Under `--json` `runUpdate` calls no clack function (a silent spinner, `runNodePrereq('update', {json})`, `loadArchetypeConfigOrExit(cwd, {json})`, the proxy notice / `MIN_CLI` warning / unknown-capabilities warning via `logErrorPlain`, every failure via `reportFatalPlain` with stdout empty and exit 1 after the clone is cleaned up) and ends in a normal return after one `console.log`; `runUpdate({json})` without `dryRun` fails closed. The clone → `MIN_CLI` → plan phase is `fetchAndPlan`, shared by the text and JSON dry runs. **The real run plans BEFORE it asks (F-24).** After the early returns and the header note it downloads the clone ONCE (no lock), runs `planFromClone` (`checkMinCli` + `buildUpdatePlan`, the half `fetchAndPlan` shares with the dry run) and prints the snapshot's membership changes with the dry run's future-tense `reportCapabilityChanges` before the confirm, so a failed download, a `MIN_CLI` refusal or a `CapabilityRemovalError` exits 1 before the user is asked. The confirm is `Apply this update?` (`… and overwrite your changes?` under `--force`), adds `It deletes N capability director(y|ies).` and defaults to No when the snapshot deletes (a removal with `present`), else Yes; `--yes` still skips only it. Then `applyUnderLock`: `withProjectLock` (still AFTER the confirm — no prompt is ever held under it) → `assertConfigUnchanged` → an AUTHORITATIVE re-plan from the SAME clone (no second download; no warning callback) → `membershipDrift`, an exact equality over `membershipKeys` (every change's `reason role:name` plus `delete <dir>/` for each present removal) between the snapshot and the re-plan — any difference is a named refusal (exit 1, nothing written, both sides listed) — → `applyPlannedUpdate`. The clone is held across the prompt and removed in the `finally` before every exit (`cancelAndExit` included). The cost, accepted: a declined run, or one the lock refuses, has already downloaded the tarball; the TTY gate still precedes every network call. `update --dry-run` runs the node floor, the config load, source resolution, the ahead-of-source (release or `main`) and same-version early returns (reported, exit 0), the fetch, the `MIN_CLI` gate (refusal exit 1, via the same `checkMinCli`) and `buildUpdatePlan`, then prints a `PLAN` note plus the real run's `SKIPPED`/`CAPABILITIES`/`MODELS`/`HOOKS` renderers (tense-parameterized) and exits 0; it SKIPS the TTY gate, the confirm, `withProjectLock` and `assertConfigUnchanged`, and no write function (`createBackup`, `applyWrites`, `writeRecords`, `writePharnConfig`) is reachable from it — `tests/update-dry-run.test.ts` pins that with a whole-tree `snapshotTree` before/after and zero-call spies. It composes with `--force` and `--ref`; `--yes` is accepted and moot. The plan is a snapshot: the real run re-fetches and re-decides under its lock. It re-resolves the recorded archetypes and **unions** the result with the user's manual adds (`lib/merge-capabilities.ts` — the pure 9-row membership table: `next = resolve(archetypes) ∪ manual`; sticky manual; a manual entry gone from the index is dropped, its files left alone; a `source`-less legacy entry is inferred ONCE at merge time — in the resolved set → `auto`, outside it → `manual` — which is the ONLY place absence may be resolved). Every membership change is NAMED in a `CAPABILITIES` note (`added` / `dropped-unselected` / `dropped-gone` / `kept-manual`); zero changes print nothing. Resurrection of a removed capability is **reported, not prevented** (no tombstones). It then decides **per file** instead of re-copying wholesale: `lib/install-records.ts` holds `pharn.records.json` (a `contentHash` of every file an install wrote, hashed at the DEST, stamped with the config's `skillsVersion`/`commit` so a store left by another tool is detected and ignored); `lib/update-decision.ts` is the PURE 6-row table (`decideFileAction` + `planUpdate` — missing→restore, identical→no-op, equals-record→upgrade, else SKIP `modified`/`unrecorded`/`unverifiable`); `lib/apply-update.ts` executes the writes (dest-symlink refusal, parent `mkdir`, and an `ApplyError` carrying what was already written so those files are still recorded on a partial failure); `lib/backup.ts` copies every `--force` casualty to `.pharn-backup/<ts>/` BEFORE any original is touched. Records are written BEFORE the config, and a run that skipped anything **withholds** the `skillsVersion`/`commit` bump so the recorded version stays true and the next run still has work. `--force` overwrites the skip buckets and bypasses the same-version early-return. An INCOMPLETE install re-opens that early return too (`lib/missing-installed.ts` → `findMissingInstalled`, a local read-only lstat walk, no round-trip, computed only when `current && !force`): a `config.capabilities` entry whose dir is provably absent at `configLayout`, or a key of the usable (stamped) records baseline — `MODELS_RECORD_KEY` excluded; no usable store → the capability dirs only — whose path is provably absent; the first hit is named in the header note. "Provably" = every existing component is a real directory and the leaf is absent: a symlinked component (live or dangling — never followed), an ENOTDIR walk or a non-directory at a capability path is NOT missing, because the run could not write there and re-opening would never close. That keeps it BOUNDED: the opened run restores the path (`missing → restore`) or, when the new manifest no longer has it, prunes the key, and the next run early-returns. A capability `remove` dropped leaves NO local trace (entry and records both gone), so it is deliberately not a re-open signal — only the upstream index knows the archetypes select it, and the early return never fetches it. A records store that PARSES but is stamped for another install state (`recordsStampStale` in `lib/install-records.ts`, F-22 — `add` and `update` write the store BEFORE the config, so a torn run leaves one) re-opens it as well, named in the header note: the baseline ignores such a store, so without the re-open the next version bump read every differing file as `unverifiable`. BOUNDED the same way — the opened run (complete or withheld) writes the store stamped with the same `skillsVersion`/`commit` it writes to the config, so the next run early-returns. An ABSENT or `invalid` store never re-opens: nothing torn to repair, or a store the user could still fix that a re-run would overwrite. `add`'s records-before-config order stays: either order tears into a stamp mismatch, and this one never lets the config claim bytes the store does not describe. **Update deletes exactly one thing: the directory of a capability it drops from the config** (merge rows 5/7/9 — `dropped-unselected`, `dropped-gone`), because PHARN's commands enumerate capabilities FROM DISK (pharn-oss `count-lenses.mjs` walks the directories; `capabilities[]` is never read at run time), so a dropped-but-present directory kept running and, with no config entry, was unaddressable by `remove`. `buildUpdatePlan` derives `report.removals` (`CapabilityRemoval {cap, reason, dir, present, backups}`, first per `role:name`, never a frozen entry) addressed at `configLayout(config)` — where it was installed and how its records are keyed — through `lib/capability-dir.ts` (`capabilityDir` = `safeChildJoin`, `linkedComponent` = `findSymlinkComponent` with ENOTDIR → `null`), with `backups` from `removalBackupSet` against the same records baseline; a symlinked component or an unreadable file throws `CapabilityRemovalError` from the PLANNER (a named policy refusal in both the real run and the dry run, exit 1, nothing written). `applyPlannedUpdate`'s order is ONE `createBackup` over `report.backups ∪ removals[].backups` (notice `before overwriting.` / `before removing.` / `before overwriting and removing.`) → `deleteCapabilityDir` for each present removal → `applyWrites` → records → config: deletes BEFORE writes, because a delete failing after the writes would strand pharn writes no record describes (only `ApplyError` carries what was written), which the next run would skip as `modified`. Their records need no prune — `nextRecords` is manifest-keyed. The CAPABILITIES note names each directory (`directory deleted`, `… (N file(s) backed up first)`, `already gone`), the dry-run PLAN note lists `WOULD DELETE`, the JSON report carries `plan.capabilities.removals` (additive, ABSENT when empty — the `plan.orphans`/`plan.absentUpstream` convention, read as `?? []`), and the real run NAMES them before its confirm (F-24, below). Nothing else is ever deleted (a file upstream stops shipping, an abandoned layout tree) and `.claude/settings.json` is never touched. A re-run `init` deletes the directories of the capabilities it drops the same way (`lib/capability-removal.ts` is the shared plan — see the init paragraph). **Orphans** (`lib/orphans.ts` → `findOrphans`, F-12): a key of a USABLE records baseline that is outside the manifest, is an install path (`isInstallRootPath` — a membership test over both layouts' `layoutPaths` surfaces plus `.claude/commands/pharn-*.md` (not `pharn-dev-`) and `.claude/hooks/*.cjs`/`*.mjs` (not `*.test.*`; the install's own `isProductCommandFile`/`isInstalledHookFile`), one level deep; any other key is never read), is not inside a frozen capability's dir nor the dir of a capability outside the next membership (a DROPPED capability keeps the plain prune), and still has something on disk (`readDiskState`) is listed as `unchanged` (hash equals the record) / `edited` / `unreadable` (+reason) in an `ORPHANED` note (`orphanNoteLines`, ≤20 per group, real run and dry run alike) and in `--dry-run --json` as `plan.orphans` — present ONLY when non-empty, so the default bytes stay pinned. `buildUpdatePlan` returns the orphans' PREVIOUS records as `apply.orphanRecords`, which the records write spreads beside `frozenRecords` — so an orphan stays keyed (and listed by later runs and `status`) until its file is gone, and a path upstream re-ships upgrades from that record instead of an `unrecorded` skip. Orphan keys are disjoint from the manifest, so they never reach the 6-row table, the counts, `versionWithheld`, `pendingSkillsVersion` or the early return (which plans nothing, so it prints no note). A re-run `init` carries the same records (`runInstallArchetype`, against `reinstallBaseline` and its new selection). This is the ONE place a record key becomes a path, and only for a read (`lib/install-records.ts` header). `CONSTITUTION.md` (from `paths.docs` in `lib/install-manifest.ts` — flat: root; pharn layout: `pharn/CONSTITUTION.md`) is in the expected trusted-doc set and follows the same per-file table: missing→restore, still-at-recorded-hash→upgrade, locally modified→skip (`modified`); `add`/`remove` never touch it. It records the layout detected in the CLONE (closing the latent drift where bytes landed at `pharn/` paths while the config still said `flat`). A capability it KEPT (upstream ships it, this CLI cannot parse it) is recorded in the additive `frozenCapabilities` (`role:name`, sorted, omitted when empty), and while that list is non-empty the same-version early return is skipped, so every run re-fetches and re-checks it; an entry leaves the list only once none of its files was skipped. When a run withholds the `skillsVersion` bump SOLELY for `modified`/`unrecorded` skips it records `pendingSkillsVersion` (see `add` above). With `--force`, the backup notice prints the moment the backup exists, with its spinner stopped first (a line logged under a running clack spinner is glued to its frame and, in a narrow terminal, erased by its stop); a later failure repeats only the part-way warning and the pointer, on stderr.

**The `models` block is pharn-oss's** (schema and defaults: pharn-oss's `pharn/floor/check-model-config.mjs` and the block in its root `pharn.config.json`). Two things use it. Since pharn-oss 6.27.0, `/pharn-ship` and `/pharn-loop` READ `models.stages` at run time to pick the MODEL requested for the stage agents their routing policy routes (`ROUTE_POLICY` in pharn-oss's `stage-agent-core.mjs`; everything else, and `inherit` / `claude-*` ids, runs inline on the session's model); EFFORT is never routed. A person's direct `/pharn-<stage>` uses the command's static `model:`/`effort:` frontmatter, which the block is the SOURCE OF TRUTH held to (the checker's `agreement` mode) — and nothing in an installed project runs that check automatically. A routed model is a request, never proof of what ran. Editing a `/pharn-*` command's frontmatter makes that file `modified`, so `update` SKIPS it and withholds the `skillsVersion` bump; editing only `models.stages` causes no file drift (`update` keeps the block whole; a re-run `init` resets it). Every surface that prints the block says this (`modelsLabelLines`, `lib/model-config-format.ts`). The CLI owns no model/effort/stage rule of its own. **`lib/model-config.ts` is a pinned COPY of the checker's `validate`/`resolve` rules** (`PRODUCT_STAGES`, `MODEL_ALIASES`, `MODEL_ID_RE`, `EFFORT_LEVELS`, `checkModelsBlock`, `resolveStageModel`) — a copy, not a call, because the CLI never executes a file it installs (THREAT-MODEL §1; `status --strict` runs in CI on PRs, and at `init` the only checker is inside the untrusted clone). `tests/model-config-parity.test.ts` makes pharn-oss the one owner: it runs the vendored checker (`tests/fixtures/pharn-oss/check-model-config.mjs`, byte-for-byte, sha256-pinned with its upstream commit) over a corpus and compares every verdict, RED line and resolution with the copy's, reads the four sets out of the checker's source, and fails if the corpus stops reaching one of the checker's validate-path RED kinds. Never add a rule the checker does not have; the refresh procedure is in `docs/contributing.md`. When upstream widens its sets before the copy follows, a block using the new member is NOT applied and the rejection is named — never fatal (LIMITS §3e); upstream's `MIN_CLI` is the lever. `lib/upstream-models.ts` (`readUpstreamModels`) is the fetch-boundary read of the clone's root config (bounded to `MAX_UPSTREAM_CONFIG_BYTES`, never throwing: `absent` / `ok` / `invalid` with reasons). **`lib/models-update.ts`** holds the CLI's knowledge of its OWN pre-0.7.0 format (the 4-id alias map `opus-4-8→opus`, `sonnet-5→sonnet`, `fable-5→fable`, `haiku-4-5→haiku`; the two defaults it ever wrote, compared byte-for-byte as `JSON.stringify`), `convertLegacyModels` (top-level `default` → `stages.default` unless that is set or `stages` is not an object — then named as a leftover; old ids → aliases; everything else verbatim; own-property rebuilds so a `__proto__` key stays data), `needsModelsConversion`, and `decideModelsUpdate`, which CALLS `decideFileAction` with the block's hash (`modelsRecordHash`, stored in `pharn.records.json` under the non-path key `MODELS_RECORD_KEY` = `pharn.config.json#/models`, defined in `lib/install-records.ts`) as the file hash and a historical default fed in as proof of authorship — so the rows ARE the per-file rows: absent → restored; equal to pharn-oss's → ok; still pharn's → updated; else KEPT (`modified`/`unrecorded`/`unverifiable`), converted if old, its previous record carried; `--force` → `pharn.config.json` backed up, then replaced. Upstream absent/invalid → the user's block stays (converted if old). The block's outcome never withholds the `skillsVersion` bump (configuration, not bytes of a version), and `needsModelsConversion` re-opens `update`'s same-version early return so a current install is migrated too. `update` prints a `MODELS` note for every outcome but `ok`.

**`pharn status` (`commands/status.ts`) is strictly read-only** — it never writes, deletes, or overwrites (fixing is `update`/`add`). Two sections: a **version** check (installed `skillsVersion` vs the upstream `SKILLS_VERSION` file, plus an archetype + capability-count summary) and a **drift** check. Default clones the source the install follows (the tip of `@main`, or the newest verified release for `ref: "latest"`) once and reuses it for both; `--no-drift` skips the clone and uses `fetchRemoteSkillsVersion` for the version section only; `--strict` exits 1 on any outdated/modified/missing/unreadable/not-shipped-upstream finding or an unwired hook (CI gate, default exit 0). The DRIFT note's `NOT SHIPPED UPSTREAM` section is `absentInstallSurfaces` at the CLONE's layout (`detectLayout(repo.dir)`), not the recorded one; a recorded layout that differs from the clone's prints a separate advisory `LAYOUT` note (`pharn update` moves the install) and is deliberately NOT a `--strict` input. `--json` carries both as additive keys: `drift.absentUpstream[{surface, path}]` and top-level `layout: {recorded, upstream}` (`upstream` null under `--no-drift`). Cleanup runs in a `finally`, and every `process.exit` happens _after_ it. The pure (no I/O) engine is **`lib/diff.ts` → `diffInstalledCapabilities`**: it mirrors `installCapabilities` to derive the **expected** file set — the selected capability dirs + the fixed product surfaces, at the recorded `layout` — then `contentHash`-compares each against the project root, returning `{modified, missing, okCount}`. Every read is `safeJoin`-guarded (from `lib/validate.ts`). `.claude/settings.json` is user-owned (preserved at install) and excluded from the file diff — but its `hooks` block is compared by `lib/hook-wiring.ts` (`diffHookWiring`: exact-string set difference over `Event · matcher · command · args`, against the UNION of the project's `.claude/settings.json` and `.claude/settings.local.json` — what Claude Code merges; user-level settings are never read. Every read is size-capped and opened `O_NONBLOCK` (a FIFO is refused, not waited on); upstream's file is symlink-refused at every component, while a project file may be a symlinked FILE (read through, as Claude Code does) but never sit under a symlinked `.claude/`. Only upstream entries are displayed, each as the hook's own JSON — exec vs shell form visible, paste-ready — with every `terminalSafe`-class character and U+2028/2029 turned into a `\u` JSON escape and each line capped at 300 chars); upstream hooks wired in neither file print a `HOOKS` note in `status` (and fail `--strict`, via `hookWiringFails`, as does an unreadable project file) and in `update` (report only — `update` still never writes the file); hooks wired only in `settings.local.json` are named as `local-only` and do NOT fail `--strict`; the copied-verbatim trusted docs (including `CONSTITUTION.md` / `pharn/CONSTITUTION.md`), hooks, contracts, and floor checkers ARE compared. Drift is derived live from the clone, always against that source, never the pinned `commit`. `status`'s DRIFT section does NOT use `pharn.records.json`, so it is a report, not a preview: a file it lists as differing may be cleanly upgraded OR skipped — only `update` can tell those apart. `status` reads the store for ONE thing — orphans (`statusOrphans` in `commands/status.ts` → `findOrphans`, against the same expected set as drift, frozen excluded): an `ORPHANED` note after DRIFT, and `--json` `orphans` (`null` under `--no-drift`, without a usable baseline, or when `detectLayout(clone) !== configLayout(config)`, where every recorded path would read as orphaned). Orphans are NOT a `--strict` input (`strictFails` is unchanged): no pharn command can clear one, since `update` deletes only the directories of capabilities it drops — never an orphan. Orphans and removals are disjoint by construction: `findOrphans` skips every key under a capability outside the next `capabilities`, which is exactly the set `removals` deletes. A `MODELS` note (both paths, no clone needed) shows the `models` block resolved for every product stage (`(default)` marks a fallback) under the truthful label, says `pharn update` converts an old-format block, or lists the pinned copy's REDs through `terminalSafe`; it is NOT a `--strict` input — the block's verdict is pharn-oss's checker's. **`status --json`** emits ONE object (`schemaVersion: 1`) on stdout and nothing else: `runStatus` branches to `runArchetypeStatusJson`, which calls no clack function that writes to stdout, builds the whole report first (`lib/status-report.ts` → `buildStatusReport`, pure; `drift`/`hooks`/`unknownCapabilities`/`orphans` are `null` under `--no-drift`), and prints once through `serializeStatusReport` (`JSON.stringify`, then every `terminalSafe`-class character plus U+2028/2029 as a `\u` escape — `escapeUnsafe`, single-sourced in `lib/terminal-safe.ts`, lossless: it parses back to the exact string). Config errors use `loadArchetypeConfigOrExit(cwd, { json: true })` and fatal failures `reportFatalPlain` (plain stderr, stdout empty, exit 1). A `--strict` finding still prints the report and sets `process.exitCode = 1` (no `process.exit`, so a large piped object is flushed); `strictFails` is the ONE predicate both modes use, and `versionStatus` (`lib/version-status.ts`) the one ahead/outdated computation. The proxy notice goes to stderr under `--json`.

## Testing

Tests live in `tests/*.test.ts` (vitest, node env). `tests/helpers.ts` provides `stubProcessExit` (turns `process.exit` into a throwable `ProcessExit`), `useTmpDir`, and `CANCEL`. The lib tests build fake fetched-repos on disk to exercise copy/materialize without network. `tests/dist-smoke.test.ts` is the one suite that runs the SHIPPED bundle: it builds it with `scripts/build.mjs <outfile>` (the same options as `npm run build`, never a copy) into a temp dir laid out like the published package (`dist/index.js` beside a `package.json` copy, `node_modules` linked) and spawns it with `node` — so the required `Test` gate, which never runs `npm run build`, still sees a bundle-only regression (`src/version.ts`'s `require('../package.json')`, an unresolvable external). `tests/commands-integration.test.ts` is the one command suite that mocks no `src/` module: it runs the real `runInit --yes` / `runAdd` / `runUpdate --yes` / `runRemove` / `runStatus --json` / `runUninstall --yes` against a real temp project, with only the global `fetch` stubbed to serve a real codeload tarball (`codeloadArchive`, `tests/support/tar-fixture.ts`), so a bug BETWEEN modules the per-command suites mock apart (the layout-gate class) still fails `Test`. When changing behavior, update the matching test before touching code.
